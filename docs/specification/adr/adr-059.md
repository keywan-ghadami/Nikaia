# ADR-059: `access` Reads and `update` Writes, So No Lambda Is Handed Something Mutable

**Status:** Accepted · **Built:** yes — see §5
**Supersedes:** [ADR-039](adr-039.md) D10's `access` row — *"in place, large
values"*, whose block mutated through its parameter
**Related:** [ADR-057](adr-057.md) (what `Locked[T]` is; this is what a program
writes to reach one), [ADR-049](adr-049.md) (the one lambda form this keeps),
Part I 5.3 (that form), Part II 12.2 (the four doors)

## 1. Context

[ADR-039](adr-039.md) D10 gave locked data four doors, and two take a lambda.
`update` is settled by its own row — handed the old value, returns the new one.
`access` was not: its block mutates **through** its parameter (`to.balance += 100`),
and a lambda's parameter has no spelling that says it may be. The open question
was which spelling to add, or whether to let mutability arrive invisibly from the
callee's contract the way a parameter's *type* already does.

**Two facts, looked up rather than assumed, decide it.**

* **The rule that a reader sees `mut` is unbroken.** Everywhere a method changes
  a value, the binding says so — `let mut names` before `names.sort()`,
  `let mut rows` before `rows.push(…)`. Every program in this repository.
* **A parameter carries no `mut` at all**, and the grammar has exactly one place
  where a callee may change what it was handed: a method's receiver. That one is
  spelled — `&mut self`.

So an invisible answer would be the **first** place in this language where
something is changed and the line does not say so, and the visible answer means a
second lambda form, which is what [ADR-049](adr-049.md) was written to protect.

**And the question turned out to rest on a cost that is not there.** `access`'s
whole justification is that copying is too expensive — *"a list of ten thousand
entries is not copied to append one"*. Run:

```nika
fn grow(old: Vec[i64]) -> Vec[i64] {
    let mut v = old
    v.push(4)
    return v
}
```

```rust
fn grow(old: Vec<i64>) -> Vec<i64> {
    let mut v = old;
    v.push(4);
    v
}
```

That is a **move**: three words, whether the list holds ten entries or ten
thousand. `update` can already append without copying anything, in ordinary
Nikaia, with the mutation spelled by the word this language already has, in the
place it already has it. The door that needed a new spelling was earning nothing
that the door without one could not.

What `update` cannot do is **read** part of a large value: it must return the new
state, and `get()` copies. Asking a shared list for its length would copy the
list.

## 2. Decisions

### D1 — `access` reads in place and may not change what it is handed.

```nika
kasse.access fn(state) { state.len() }
```

It keeps its name and its purpose — in place, large values — and loses the
mutation. What it hands the lambda is the value where it lies, to **read**; what
it returns is what the lambda computed.

This is the one thing neither other door does, and it is why `access` stays
rather than going: without it, asking a ten-thousand-entry list for its length
copies the list.

### D2 — `update` is where locked data changes, and the old value is not mutable.

```nika
kasse.update fn(old) { old + 100 }

kasse.update fn(old) {
    let mut v = old
    v.push(entry)
    return v
}
```

`old` is an ordinary immutable parameter. Where the new value is made by changing
the old one, the program rebinds it and the word is visible on that line — which
is the same thing it writes everywhere else, and not a new rule.

### D3 — Therefore no lambda is handed something it may change, and there is nothing to spell.

The question this record was opened for does not get an answer; it stops being a
question. Part I 5.3's one lambda form is untouched, no parameter gains a
mutability marker, and the language keeps the property that a reader sees a
change where it happens.

**And it stays reversible in the direction that matters.** A spelling can be
added later, to `access` or anywhere else, without invalidating anything written
under this record — because nothing written under it mutates a parameter. The
other order would not have been: shipping an invisible mutability and requiring a
word for it later invalidates every lambda already written.

## 3. Consequences

**One row of Part II 12.2's table changes**, and the sentence naming the doors
that require a `sync` lambda keeps all of them: `access` still runs user code
while the lock is open, so it still may not pause, and reading is no weaker a
reason than writing.

**`get` and `set` are untouched**, including the reason they need no condition at
all: while the lock is open in either, no code of the user's runs.

**Two accesses to one lock keep their order, and `access` moves sides.**
[ADR-039](adr-039.md) D10 reasoned that `get` is a read and `set`, `update` and
`access` are writes, so that two `get`s are unordered under
[ADR-033](adr-033.md) D2 and the three writing forms stay ordered. `access` is a
read now, so **two `access`es of one lock are unordered too**, and the writing
forms are `set` and `update`.

**What it costs:** a program that changed a large value in place writes `update`
and one more line. That line is the change, said out loud.

## 4. What this does not decide

* **What a write across several locks is.** `access_all` names several at once,
  and the same reading applies to it — it reads. `update` writes **one**. So
  Chapter 12's own transfer between two accounts, which takes from one and gives
  to the other under both locks, has no door after this record. That is a
  consequence of D1 rather than an oversight of it, and it is left open rather
  than answered in passing: what such a door is called, and whether it hands a
  value back per lock, is a decision and not a footnote. Part II 12.2 carries a
  status note saying so, and `open-work.md` carries the entry.
* **Whether a lambda's parameter may ever be mutable.** This removes the only
  construct that needed it. If one arrives, the spelling is that decision's, and
  D3 says why nothing here forecloses it.

## 5. What is built

**All three decisions**, on top of [ADR-057](adr-057.md)'s two shapes.

`nikaia_std::lock` carries all four doors on both shapes: `get`, `set`, `access`
taking `&T`, and `update` taking `T` and returning one. The value sits in an
`Option<T>` so that `update` moves it out and back without a `Default` bound and
without unsafe code — and a lambda that fails leaves the lock **empty**, which is
reported as such rather than silently read as something else. `std.contracts`
describes all four, each `sync = "from(f)"` where it takes a lambda.
