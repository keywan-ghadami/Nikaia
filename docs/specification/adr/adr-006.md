# Architecture Decision Record (ADR) 006: Resource Cleanup under Implicit Async (The `Cleanup` Trait)

**Date:** 2026-09-05
**Status:** Accepted
**Context:** Nikaia promises RAII ("cleanup happens automatically, you cannot forget it" — Part I, 6.4, the stated reason there is no `defer`) *and* implicit async (every normal function can pause at I/O). These collide: real cleanup is often itself I/O — flushing a buffered file, rolling back a database transaction (`std::db` runs through an async sidecar per Part III, 17.2), sending a TLS goodbye — but a destructor in the Rust backend is a synchronous function that cannot contain a suspension point. Meanwhile the spec already promises cleanup in async situations: §6.4 guarantees drops during `throws` unwinding, and §12.4 promises that a losing `select` branch is "automatically cancelled **and cleaned up**". This ADR decides how cleanup that wants to pause is executed, where its errors go, and how program shutdown waits for it. Predecessor analysis: ADR-005 (whose D6 — no locks held across suspension — this design depends on).

---

## 1. The Three Death Paths (Normative Taxonomy)

A value dies on one of three paths, with different room to maneuver:

1. **Normal scope exit / `return`** — we are in a normal (pausable) function; pausing for cleanup is *possible* if the language can express it.
2. **Error unwinding (`throws`)** — likewise pausable context; same conclusion.
3. **Cancellation and panic** — the task is torn down from outside (a lost `select`, a supervisor restart) or dies of a bug. The teardown context *cannot* wait on arbitrary I/O (whoever cancels must not inherit an unbounded wait; panic unwinding cannot pause at all; Lite's `panic = abort` runs no destructors whatsoever).

**Rule derived from this:** on paths 1 and 2, cleanup may pause; on path 3, every design needs a synchronous fallback. Any proposal that answers only one half is incomplete.

## 2. Decisions

### D1: The `Cleanup` trait — pausable `cleanup` plus synchronous `drop`, compiler-inserted

A resource whose teardown performs I/O implements `Cleanup` instead of plain `Drop`:

```nika
impl Cleanup for BufferedFile {
    // Pausable teardown. May suspend, may fail.
    // Called automatically by the compiler at end of scope —
    // on normal exit AND during `throws` unwinding.
    fn cleanup(&mut self) throws IoError {
        self.flush()
    }

    // Synchronous last resort. Must not pause, must not fail.
    // Runs after cleanup(), or ALONE when cleanup() cannot run (path 3).
    fn drop(&mut self) {
        // release the handle, mark the connection unclean — nothing that waits
    }
}
```

**Mechanism.** What Rust user code cannot do generically — "insert `cleanup().await` on every exit path of a block" — the Nikaia driver does trivially during lowering (ADR-001/002 own the lowering; this is the same class of trick as the async state machines rustc builds). The `.nika` source shows nothing; the RAII promise of §6.4 ("you cannot forget it") is preserved intact.

**Precedent.** This is the semantics of C# `await using`/`IAsyncDisposable` and Python `async with` — stable, mainstream, and battle-tested — except that there the *user* must write the construct at every use site, while in Nikaia the compiler inserts it. rustc's own `async_drop` nightly experiment validates the direction but is too immature to build on directly (unlike `-Zpolonius=next`, its semantics are still in flux); the semantics belong to Nikaia and the driver generates the awaits itself. Plain `Drop` (Part I, 6.4) remains for the majority of types whose teardown is pure memory work.

### D2: A pausable-cleanup value must not die in a `sync` context

A `sync` function cannot pause, so no value whose type has a pausable `cleanup` may go out of scope inside one. This is checked statically and virally through the existing `sync` system — the same propagation discipline as `@detached` (ADR-005, Part I 5.4) — and reported in Nikaia vocabulary with the way out named (`NK2602`; return the resource to the caller, close it before entering the `sync` part, or use a non-buffering variant). Pleasant consistency: ADR-005 D6 makes `access`/`access_all` take `sync` lambdas, so it is *automatically* guaranteed that no async cleanup ever falls due while a lock is held.

### D3: Cancellation parks the cleanup with the runtime; panic gets only the sync fallback

**Cancellation (path 3a).** The canceller never waits on foreign I/O. When a task is cancelled (lost `select` per §12.4, supervisor restart per §12.8), the runtime **adopts the due `cleanup()` runs as its own detached cleanup tasks** ("parked cleanup"): the cancelled task is gone immediately; the cleanup proceeds in an orderly fashion; the runtime waits for all parked cleanups before the program exits (bounded by D5). This is structured draining, not fire-and-forget — no silent data loss. In Lite it is trivial (same event loop); in Advanced it is an ordinary task.

**Panic (path 3b).** During panic unwinding, pausing is impossible; only the synchronous `drop` fallback runs (Advanced: during task poisoning). In **Lite, `panic = abort` means no destructors run at all** — this pre-existing fact is now stated honestly next to the RAII guarantees in Part I 6.4 instead of being discoverable only in the profile table.

### D4: Cleanup errors throw normally — signatures tell the truth

Policy (a), chosen over "log and swallow" and over per-type opt-outs:

* The compiler-inserted `cleanup()` call is a real call site: if `cleanup` declares `throws IoError`, the enclosing function can now fail and **must declare it**. This is correct, not an annoyance: a buffered write *can* fail at flush, and hiding that is the decades-old C-`stdio`/Rust-`File` data-loss bug. The compiler explains exactly why the signature is needed ("this function can fail because closing `f` can fail") and where.
* If the value dies while an error is **already unwinding** (path 2), the cleanup error does not replace the primary error: it is attached as a **secondary error** to the primary one — a natural extension of the automatic error context of Part I 7.1.
* Anyone who wants to *handle* the error precisely calls `close()` explicitly (which consumes the resource and returns the error normally); the implicit path is for the happy path, the explicit path for targeted handling. After an explicit `close()`, no implicit cleanup runs.
* On path 3a (parked cleanup after cancellation) there is no caller to throw to: the error is reported through the runtime's error hook (default: logged with the resource's type and allocation site), consistent with the fact that the *cancelled* task's result is already discarded.

### D5: Shutdown draining with a deadline — guaranteed not to hang, guaranteed not to be cruel

When the program ends (main returns, or an orderly `exit`), the runtime enters a **drain phase**: it waits for all parked cleanups (and, per existing semantics, still-running detached tasks). The drain is bounded by a configurable deadline (`cleanup-deadline` in `nikaia.toml`, default generous: 30 seconds; `"0"` disables draining entirely for fire-drill exits). On expiry, remaining cleanups are cancelled — which triggers their synchronous `drop` fallback — and the program exits with a warning listing every resource that did not finish cleanly (type + allocation site).

**Why this cannot hang (termination argument):**
1. The deadline timer is driven by the runtime itself and does not depend on any cleanup making progress — it always fires.
2. Cancelling a cleanup at the deadline runs its synchronous `drop`, which terminates by construction (it cannot pause).
3. The classic deadlock source — "cleanup waits on a lock held by a suspended task" — is already eliminated by ADR-005 D6: locks are never held across suspension points, so every lock a cleanup needs is released at every pause. Remaining waits (dead TLS peer, slow disk, two cleanups waiting on each other's channels) are exactly what the deadline bounds.
4. Cleanups may themselves create resources; the cascade is bounded by the same global deadline, not by per-resource budgets.

**Honest limit (documented, not hidden):** hard-*blocking* foreign code (FFI that blocks the thread rather than pausing) in the Lite profile blocks the event loop and with it the deadline timer. This is the general, pre-existing FFI hazard of a single-threaded runtime — not specific to cleanup — and is mitigated by the sidecar pattern for known blocking operations (Part I, 8.4).

### D6: The Panic Hook — a last synchronous diagnostic moment, global per application

"Abort" (Lite) means no *unwinding* runs — it does not have to mean no code runs. The load-bearing fact: rustc's panic machinery invokes the registered panic hook **before** aborting even under `panic = abort` (documented behavior of `std::panic::set_hook`). Nikaia passes this moment through as `std::panic::on_panic` and fences it:

* **Scope: global, one per application.** Only the application (root package) may set the hook — a library calling `on_panic` is a compile error (`NK2604`). Rationale: the Rust model (single global hook) is proven; handler-chain semantics in the crash path is needless complexity. A library offering crash reporting exports a function the app calls *from* its hook.
* **Runs on every panic, both profiles:** in Lite immediately before the process abort (before the trap on WASM); in Advanced on the panicking worker before task poisoning. It receives a `PanicInfo`: message, file/line, stack trace (the panic-side counterpart of the automatic error context in Part I, 7.1). Supervisors (Part II, 12.8) receive their crash information from the same `PanicInfo`.
* **The hook must be `sync`** — mid-panic there is no runtime to pause on; the existing `sync` vocabulary makes the mistake impossible (third application of the mechanism, after ADR-005 D6 and D2 above).
* **Blocking I/O is exceptionally permitted, with a profile nuance.** In Lite the process is dying anyway — a synchronous dump write blocking the event loop costs nothing. In Advanced the process *survives* (poisoning), so the hook blocks one worker: acceptable for brief, rare crash reporting (the Crashpad/Breakpad model), but the spec instructs: keep the hook short, hand heavy reporting to a pre-started task or process. Documented pattern: open crash-case resources (file descriptor, preallocated buffer) **at startup**; the hook only writes.
* **Diagnosis, not cleanup.** The hook must not attempt to flush buffered files or salvage transactions: the objects may be broken in exactly the way that *caused* the panic — that is why destructors do not run on this path, and the hook must not reopen that decision through the back door. A panic inside the hook aborts immediately (recursion guard, as in Rust).

Consequence for the honesty note in Part I 6.4: "in Lite, a panic runs no destructors" becomes "…no destructors — but the panic hook runs, for dumps and crash reports."

## 3. Rejected Alternatives

* **Synchronous `Drop` that may block** (Rust's `std::fs::File` status quo): freezes the Lite event loop; is *unimplementable* on the WASM target (the browser forbids blocking the main thread); swallows errors. Disqualified by Nikaia's own default profile.
* **Fire-and-forget spawn inside `drop`**: no ordering guarantee (program may exit before the flush — data loss through the back door), errors land nowhere, and "the transaction gets rolled back eventually" is semantically wrong for `std::db`. Survives only as the *structured* variant in D3, with D5's drain making it lossless.
* **Explicit `close()` as the primary model** (today's async-Rust convention, e.g. tokio `shutdown().await`): honest but reintroduces exactly the forgettable cleanup duty that §6.4 abolished — a regression against "you cannot forget it". Kept as the opt-in for precise error handling (D4), not as the model.
* **Linear types** (compiler forces explicit consumption on every path): the cleanest error story in theory; in practice every early return, every `catch`, every `select` needs explicit handling — frontally contradicts the happy-path promise.
* **Building directly on rustc's `async_drop` experiment**: direction-confirming but semantically unstable; unlike `-Zpolonius=next` (a checker that accepts more correct programs, easily re-validated per toolchain pin), `async_drop` would define *behavior* — too risky to outsource. The driver generates the awaits itself.
* **Stackable/chained panic hooks** (multiple handlers with chain semantics): more flexible on paper, but ordering questions and failure-in-handler-N semantics add complexity to the one code path that must never surprise. The proven Rust model — one global hook, set by the application — wins; libraries integrate by exporting functions the app calls from its hook (D6).

## 4. Consequences

* Part I 6.4 is extended: `Drop` (sync, most types) and `Cleanup` (pausable teardown) side by side; the "why no defer" reasoning survives unchanged; the Lite panic honesty note is added.
* Part II 12.4's "cancelled and cleaned up" now has defined semantics (parked cleanup, D3).
* Part III gains the `cleanup-deadline` manifest key and NK26xx diagnostics (Appendix C).
* Part I 7.2 gains the panic hook (`std::panic::on_panic`, D6); the Appendix A panic table in Part III notes that the hook runs on every panic path, including Lite's abort.
* Function signatures can gain `throws` obligations from implicit cleanup (D4) — by design; the diagnostic must always name the resource responsible.
* The Borrow Contract Ledger (ADR-005 D3/D8) is unaffected: `Cleanup` changes *when* code runs at scope exit, not what borrows what.
* Open for later: whether `select` should offer an opt-in "wait for the loser's cleanup before returning" mode for transactional race patterns.
