# ADR-025: A Loop Can Fail, and the Rule Was Already Written

**Status:** Accepted
**Date:** September 10, 2026
**Target Version:** Nikaia 0.0.8
**Closes:** G17 (`examples/README.md`)
**Removes:** `fs::lines` and `fs::bytes` from Part III, 17.1
**Related:** [ADR-006](adr-006.md) D1/D4 and Part I 6.4 (a block's end may fail — the same
question, answered once already), [ADR-023](adr-023.md) D8 (nothing marks a failing call),
[ADR-008](adr-008.md) and Part I 6.6 (one value owns a buffer, another borrows views of it),
[ADR-009](adr-009.md) (which dissolved G4 rather than solving it),
[ADR-011](adr-011.md) D2 (the lowering is name for name),
[ADR-020](adr-020.md) (the ledger says what a caller cannot see)

---

## 1. Context

Part III 17.1 specifies four streaming functions and none of them exists:

```nika
pub fn lines(path: Path) -> Lines throws        // yields tethered &str, one per line
pub fn bytes(path: Path) -> ByteStream throws   // yields chunks as they arrive
pub fn lines() -> Lines throws                  // std::io - one line at a time, owned
pub fn bytes() -> ByteStream throws             // std::io - chunks as they arrive
```

Trying to build them was how this ADR started, and it turned out that the four are not one
problem. They are two, and only one of them is a question about the language.

### 1.1 What actually goes wrong

```nika
fn count_rows(path: &str) -> i64 throws {
    let mut n = 0
    for line in fs::lines(path) {
        n += 1
    }
    return n
}
```

Suppose the read fails at line three — a bad sector, a dropped NFS mount, a byte that is not
UTF-8. The loop has to get *something* from the stream. An iterator's step answers with two
cases, a value or an end. There are **three**: here is a line, there are no more, and *I could
not find out*.

Press three cases into two and "I could not find out" becomes "there are no more". Then
`count_rows` **returns 2, successfully**. No `catch` fires. The `throws` on the signature is
never reached. A ten-million-line file reports 2, and the caller cannot tell that from a
two-line file.

That is the failure this ADR exists to make impossible.

### 1.2 The specification already refuses this, in the next chapter

Part I 6.4 asks the identical question about the *closing* brace of a block. A resource's
`cleanup` runs there, nobody wrote the call, it appears in no signature — and it can fail. The
specification's answer is not subtle:

> **Cleanup errors are real errors.** If closing a resource can fail, the function that owns it
> can fail — Nikaia does not hide this (**silently losing data at close time is a decades-old bug
> class in other languages**).

And `NK2601` enforces it: *this function can fail because closing `f` can fail*.

So the language already decided what an implicit call that can fail does. It decided it once, for
one case, without noticing the rule was general.

## 2. The two walls

They are independent, and separating them is most of the work this ADR does.

### Wall A — `for` performs a call that no signature declares

Nikaia's error model has two anchors: a failure is announced at a **declaration** (`throws`) and
travels at a **call**. Both need something written.

`for line in xs { }` performs a step per turn. The programmer wrote no call, and the step is in no
signature. There is nowhere for `throws` to attach — which is exactly the shape of the closing
brace in 6.4, one line earlier in the same block.

### Wall B — an iterator may not hand out views into a buffer it owns

This one is not about failure at all, and it stands even after Wall A falls.

```nika
let data = fs::map(&path)      // `data` owns the pages
for line in data.lines() { }   // the iterator borrows them; each view hangs on `data`
```

works, because the views point into something the iterator does **not** own. `fs::lines(path)`
cannot do that. One call opens the file *and* yields views, so the iterator must own the buffer
and hand out references **into itself**. That is a lending iterator, and the language below cannot
express one: a step takes the iterator by mutable reference and cannot give back a reference
derived from it.

This is not a limitation Nikaia inherited by accident. It is why Rust's own `BufRead::lines()`
allocates a `String` per line, and why reading lines without allocating there means writing the
loop by hand.

**And it says something about the specified signature.** `fs::lines(path) -> Lines` with tethered
`&str` fuses two things Nikaia's ownership model deliberately keeps apart: one value owns a
buffer, another borrows views of it (Part I 6.6, ADR-008). The two-call form is not a workaround
for the one-call form. It is the model.

### 1.3 What the repository actually does

Nothing in it iterates lines. `1brc.nika` does not: it declares `@frame(boundary: "\n")` and folds
over the mapped pages, and the frame **is** "one record per line" — it never materialises a
sequence of lines at all. `access-log.nika` and `config.nika` are the same shape.

Nikaia's answer to *process a file line by line* is the grammar protocol, and it has been since
ADR-009.

## 3. Decisions

### D1 — An implicit call that can fail propagates, and the compiler makes you declare it.

Stated once, generally, instead of once per case:

> Where the language performs a call the programmer did not write — the `cleanup` at a block's
> end, the step of a `for` — a failure of that call **fails the enclosing function**, exactly as a
> written call would. The function must declare `throws`, and the compiler says which implicit
> call is the reason.

Part I 6.4 is the first case and is unchanged by this; iteration is the second. A third — an
operator that can fail, a conversion that can fail — is covered in advance rather than reopening
the question.

### D2 — Nothing marks the loop, for the reason nothing marks the call.

[ADR-023](adr-023.md) D8 tabulates the invisible control-flow events and refuses to mark one of
them, because *"a `?` on one line implies the lines without one are safe, and they are not"*. This
adds a fourth row to that table:

| event | marked? | decided in |
| :--- | :--- | :--- |
| a call may **pause** | no — there is no `await` | Part I, 8.1 |
| a block's end may **pause and fail** | no | ADR-006 D1/D4 |
| a call may **fail and return early** | no | ADR-023 D8 |
| a **loop's step** may fail and return early | no | this decision |

Swift writes `for try await line in …` and Zig writes `while (try it.next())`; both are the same
answer as D1 with a marker on it. Nikaia takes the answer and leaves the marker, because
half-visibility is what D8 rejected and a fourth unmarked event is more consistent than three
unmarked and one marked.

The cost is D8's cost, and it is the same cost: a reader of a diff cannot see it. The ledger
records it, and tooling can show all four.

### D3 — `fs::lines` and `fs::bytes` are removed from the specification.

Not deferred — **removed**. ADR-009 closed G4 by dissolving it, and this is the same move for the
same kind of reason:

* the specified form is the one Wall B forbids, and the form that works is
  `fs::map(path)` + `.lines()`, which exists and is what the examples use;
* the properties 17.1 promises them — tethered `&str`, no allocation per line, constant
  memory — are exactly the properties `fs::map` has, because they are properties of a mapping;
* and the language's own answer to line-oriented input is `@frame`, not a sequence of lines.

A file is seekable and mappable. Fusing "open it" and "walk it" into one call buys nothing here
and costs the separation the whole tethering model rests on.

**What replaces them in the specification** is a sentence saying so, pointing at `map`, and
pointing at `@frame` — because a reader looking for `lines` needs to be told where it went, not to
find a gap.

### D4 — `std::io`'s streams stay, because a pipe is genuinely different.

Standard input is not seekable and cannot be mapped: its bytes do not exist until they are read
(ADR-019 D1). There is no way to move the failure to the call, so Wall A is real here, and D1 is
what answers it.

Wall B is **not** an issue: 17.1 already specifies `io::lines()` as yielding *owned* text, for its
own reason — *"a stream's bytes are gone once consumed"* — so nothing borrows from the stream and
the lending problem does not arise.

`io::lines()` is therefore buildable, and this ADR builds it.

### D5 — `NK2701`: a loop whose step can fail, in a function that does not declare `throws`.

A new range, `NK27xx` — *implicit calls* — because that is what the family is, and `NK2601`
belongs to it in spirit while living in the cleanup range for historical reasons.

```text
error[NK2701]: this function can fail because reading the next line can fail
  --> count.nika:3
   |
 3 |     for line in io::lines() {
   |     ^ each turn of this loop reads from standard input, and a read can fail
   |
  help: declare the error:  fn count_rows() -> i64 throws
```

The shape is `NK2601`'s deliberately: it is the same rule, and two diagnostics for one rule should
read as one thing.

### D6 — The ledger says which types iterate fallibly.

A type contract gains `iterates = "throws"`. `std.contracts` carries it for `io::Lines`, and a
program's compiler reads it exactly as it reads `sync` and `signature` — the caller cannot see the
body, so the ledger is where the fact lives (ADR-020).

This is the third thing the ledger has been extended for and the second time the extension was one
key. That is the property it was designed around.

### D7 — Stage 0 lowers the propagation with the type checker's answer, not with a name.

The emitter needs to know whether a `for` iterates a fallible stream. It asks the type checker
([ADR-024](adr-024.md)), which infers the type of the iterator expression and looks it up in the
ledger — so `for line in io::lines()` and

```nika
let stream = io::lines()
for line in stream { … }
```

are the same to it, because `let` carries the type. Matching on the name `io::lines` would have
handled the first and quietly not the second.

The lowering itself is one line inside the loop, and it is the one a Rust programmer writes by
hand.

## 4. Prior art

The landscape divides on one axis: **what the language does with errors elsewhere.**

| language | answer | what it pays |
| :--- | :--- | :--- |
| **Go, classically** | the loop yields values; the error is asked for afterwards (`scanner.Err()`) | exactly the silent truncation of §1.1 |
| **Go, since 1.23** | `iter.Seq2[T, error]` | an unwrap per turn |
| **Rust** | `Item = Result<String>` | an unwrap per turn **and** an allocation per line |
| **Java** | `IOException` wrapped as `UncheckedIOException` | the checking itself |
| **Python, C#, Kotlin** | the exception propagates from the step | nothing is in the signature |
| **Swift** | `for try await line in …`, enclosing function `throws` | a marker on the loop |
| **Zig** | `while (try it.next()) \|x\|` | a marker on the loop |

Three are worth more than a row.

**Go's classic answer is the counter-example, in production.** `bufio.Scanner` stops at a line
over 64 KB by default and reports it only through `Err()`; a caller who does not ask sees a
shorter file. There are linters whose whole job is to demand that line. This is §1.1 as a
mainstream language's default, and Part I 6.4 already names the bug class.

**Java is the cautionary one.** Java has checked exceptions — failures at the declaration, like
`throws`. `Iterator.next()` declares no `IOException`, and Java could not reconcile the two: it
gave up the checking and made `BufferedReader.lines()` throw an *unchecked* wrapper. The language
that invented checked exceptions stopped at this exact wall.

Nikaia has an advantage Java did not: **`for` is a construct of the language, not sugar over an
interface users implement.** Java had to fit an existing `next()` signature. Nikaia gets to say
what `for` does, which is what D1 does.

**Swift is the closest relative** — declared failures plus a language-level loop — and it chose
propagation. Nikaia is Swift's answer without Swift's marker, and D2 says why.

The pattern: a language that *declares* failures and owns its loop arrives at propagation. A
language that carries failures as values arrives at unwrapping. A language that asks afterwards
gets the bug.

## 5. Considered and rejected

* **Treat a failed read as the end of the stream.** §1.1. Refused by Part I 6.4's own words about
  the same failure at the other end of the block.
* **The same, but the compiler forces the check afterwards** (Go plus a rule that cannot be
  forgotten). Fairer, and still wrong: the loop body has already *acted* on the truncated data —
  counted, summed, written rows to a report — before the check is reached. Propagation stops at
  the failure; a check afterwards stops after the damage. It also turns one failure into two
  program states a reader has to keep apart.
* **Make the item a value that may be a failure** (Rust, Go 1.23). Honest, and it puts an unwrap
  at the top of every loop over a stream — the shape Chapter 7 exists to remove, added back in the
  one place a program is most likely to be iterating something large.
* **Hand the loop body to the stream**: `fs::lines(path) fn { … }`. Wall A dissolves — it is a
  call, and `throws` covers it. But `break` and `return` out of the lambda need non-local return,
  which Kotlin had to introduce `inline fun` for; that is a large feature bought to avoid a small
  one, and it leaves the language with two looping forms.
* **Keep `fs::lines` and let it allocate a `String` per line.** It would work and it would be a
  quiet lie: the specification promises tethered views and no allocation, and a program written
  against that promise on a large file would find out in production. Removing the function is
  more honest than keeping a version of it that does not do what it says.
* **A lending-iterator protocol of Nikaia's own**, lowered to `while let` rather than to Rust's
  `for`. It would make `fs::lines` expressible and would break ADR-011 D2 — the lowering stops
  being name for name, and every `for` in the language starts depending on a protocol the target
  does not have. Worth revisiting when Stage 1 owns its own backend; not worth it to keep one
  function that has no caller.

## 6. Consequences

**A `for` is a fourth place a function can fail from**, and Part I 3.3 says so.

**`fs::lines` and `fs::bytes` are gone from Part III 17.1**, with a sentence saying where a reader
should look instead. The availability table loses their row for `wasm32-*` as well — the WASM
question they were the answer to comes back with the target, and will be answered by whatever
`std::fs` looks like there.

**`io::lines()` exists**, and it is the first thing in the repository that reads an unbounded
input in constant memory: no `read_to_string`, no buffer the size of the input.

**The ledger has a third kind of fact in it**, and the emitter reads the type checker's answers
for the first time — which is ADR-024's D3 paying off in a direction it did not predict: the
checker was built to report, and it turns out to be what tells the emitter what to emit.

**G17 is closed. G18 is not**, and is unrelated: named arguments with defaults (Part I 5.1) still
do not parse, which is why `fs::write` has neither `append` nor `create`.

---

## 7. What Stage 0 does today

* `NK2701` is reported, with the source line and a caret, in the shape `NK2601` specifies.
* `for line in io::lines() { … }` lowers to a loop whose step propagates.
* The type checker resolves the stream through `let`, so naming it first works.
* One binding per fallible loop. A stream of pairs does not exist in `std`, and a `for (a, b)` over
  one is rejected rather than guessed at.
