# ADR-004: One Lowering, Two Exits — `rustc_ast` Built Once, Printed or Driven

**Status:** Accepted · **Built:** D1, D2 and D4; D3's direct-driver exit is not,
and is measured as not worth building
**Related:** [ADR-003](adr-003.md) (Bridge-IR, which this consumes),
[ADR-001](adr-001.md) D4 (Stage 0 is a transpiler — D2 is what keeps that true),
[ADR-012](adr-012.md) (diagnostics, which need the generated source to be
readable), [ADR-021](adr-021.md) D9 and D14 (how a backend that is not here
refuses), [ADR-002](adr-002.md) D3 (which named the backend list D4 reorders)

## 1. Context

The executor turns Bridge-IR into a binary. Two things are wanted from it that
pull apart: the fastest path is to hand `rustc` an AST in memory and skip its
parser, while debugging the compiler needs the generated Rust as text a person
can read.

Doing both the obvious way means two backends — a string builder and an AST
builder — which is double the maintenance and guaranteed drift between what is
debugged and what is shipped.

## 2. Decisions

### D1 — There is one lowering, and it builds `rustc_ast`.

`BridgeModule` → `rustc_ast::Crate`, in a single pass. The mapping for a
construct — `BridgeLet` to `ast::Local` — exists in exactly one place.

Building the AST rather than concatenating strings also makes a syntactically
invalid program unrepresentable: the types refuse it, where a string builder
would emit it and fail later in a place that does not name the cause.

### D2 — Text is produced by printing that AST, not by a second code generator.

`rustc_ast_pretty::pprust` serialises the same `rustc_ast::Crate` back to Rust
source. Inspectable output is therefore a *view* of what is compiled, never a
parallel implementation of it.

This is what makes [ADR-001](adr-001.md) D4's "Stage 0 is a transpiler" cheap to
keep true, and it is the path that ships today: the executor prints the crate
and invokes `rustc` as a subprocess.

### D3 — The in-memory exit stays open, and costs nothing to keep open.

Feeding the same `rustc_ast::Crate` to `rustc_interface::run_compiler` skips
`rustc`'s parser. Because D1 already produces the AST, this is a different
*consumer* of it rather than a different backend, and can be added when the
subprocess cost is worth removing.

Not built. `rustc-executor` links `rustc_driver` for the AST types; the
compilation itself is the subprocess.

**Measured, and it is not worth removing.** Instructions retired under
callgrind, compiling the largest program the corpus lowers: the printed-Rust
round trip — print, write, re-lex, re-parse — is **2.77 M of 1 719 M, 0.161 %**,
and starting the process costs **8.3 M, 0.48 %**. Together **0.64 %**, falling
to 24.5 % only on a three-line program whose whole compile is 34 M. A program
of many files does not change this: every `.nika` file becomes a `mod` in one
Rust crate, so the fixed cost is paid once per program and its share *falls* as
a project grows. D3 becomes worth building when a program is split into several
Rust crates ([ADR-003](adr-003.md) D2's build graph), and not before.

**And it does not cost nothing to keep open, which this record had assumed.**
The crate D1 builds is print-only: every node carries `NodeId::from_u32(0)` and
`DUMMY_SP`, where rustc's parser writes `DUMMY_NODE_ID` and expansion asserts it
before assigning a real id. So the exit needs a node-id discipline and a
`SourceMap` in the lowering before `run_compiler` could accept the AST at all,
and a second route for [ADR-012](adr-012.md), whose diagnostics are translated
from `rustc --error-format=json` about a generated file that an in-memory
compile does not write. The method, the machine and the variance are in
[`docs/subprocess-cost.md`](../../subprocess-cost.md).

**And one thing the measurement found that was a defect rather than a cost: the
subprocess compiled at the wrong edition.** `execute` passed `rustc` no
`--edition`, so the printed crate was compiled at **2015** while the crate had
been interned and printed for 2021 — which is the edition D2's emitter writes
and the edition every test of the `rust` backend compiles at. A mismatch and not
a choice, because D2 makes the text a *view* of what is compiled: two statements
of one fact, where the interner's said 2021 and `rustc`'s said nothing. Both now
read one constant in `rustc-executor`. It changed nothing observable and that
was checked rather than assumed — the printed crate and the binary are
byte-identical before and after, and `bridge_backend.rs` compiles the same
printed text at both editions and compares, so the day something the bridge
carries *can* tell them apart is the day that test fails and says so.

### D4 — The bridge backend is optional, and `rust` is what a bare `nikaia` uses.

`nikaia --input x.nika` with no `--backend` lowers through the `rust` backend,
[ADR-001](adr-001.md) D4's Stage 0 transpiler. `bridge` is still here and is
still what carries Bridge-IR; it is chosen by name, and it is in a build only
when the `rustc-backend` feature is.

This displaces the default `bridge` that [ADR-002](adr-002.md) D3's backend list
assumed and that this record carried until now. Two reasons decide it:

* **The default compiled almost nothing.** Bridge-IR carries **1 of the 15
  corpus programs** — `bridge-ir` has no control flow to carry them with — and
  the `rust` backend carries all fifteen
  ([`docs/subprocess-cost.md`](../../subprocess-cost.md), the same measurement
  D3 rests on). A default is what a person gets without asking, and this one
  answered *I cannot* to fourteen programs in fifteen.
* **A bridge-enabled binary is not a relocatable binary.** It links
  `librustc_driver-<per-build hash>.so` with an **absolute RUNPATH into the build
  machine's rustup home**, and the hash in the soname differs per build, so a
  stable install has a differently named file and therefore the wrong one. Built
  without the feature it links only `libc`/`libgcc` and is self-contained. That,
  and not disk space — which is two megabytes either way — is why a Nikaia
  anybody can ship cannot have the bridge compiled in by default
  ([`docs/nightly-cost.md`](../../nightly-cost.md)).

Behind both: the bridge backend is the **only** consumer of `rustc_private` in
the workspace, and [ADR-003](adr-003.md) D1 is what keeps it that way, so it is
the only reason anything here needs a pinned nightly at all — the toolchain itself
is decided elsewhere. Making it optional is what lets an installation be an ordinary
stable-toolchain installation rather than a reduced one.

And the standing evidence that a default nobody measures is a default nobody
runs: while `bridge` *was* the default it panicked on its first interned symbol
and so failed on **every** input, undetected, because nobody had measured the
path that needed no asking for — which is what
[`docs/subprocess-cost.md`](../../subprocess-cost.md) found on its way to D3's
numbers.

**What this does not change, and the record would be misread without it.**
[ADR-003](adr-003.md)'s hub and spoke stands whole: a frontend targets Bridge-IR
and never `rustc_ast`, and D1's single lowering is still the one place a construct
is mapped. The bridge backend is **not deprecated** — it is the route the
language's own future compilation goes through, and D3's in-memory exit is the
same open option it always was. What changed is which backend a person gets
without asking, and whether every installation must carry one. Nothing at all
about which IR a frontend writes.

**A build without it refuses by name**, saying which feature and which toolchain
component would add it: [ADR-021](adr-021.md) D9's rule as D14 extends it.
Serving `rust` quietly under the name `bridge` would be worse than refusing.

**The cache is unaffected, and that was checked rather than assumed.** The
backend is already a dimension of the key ([ADR-021](adr-021.md) D5, D7), and
only the `rust` lowering is ever stored — the bridge hands its module to the
executor and consults no cache. So a bare invocation shares the one entry
`--backend rust` already used, which is the same lowering under two spellings,
and no `bridge` entry exists to be served to a `rust` build or the reverse.

**Not decided here, and visible now in a way it was not before.** The backend
this makes the default is not the printer D2 describes: `--backend rust` emits
Rust from the Nikaia AST in `crates/nikaia/src/emit` and never builds
`rustc_ast`, so D1's "exactly one place" and D2's "never a parallel
implementation" are claims about the Bridge-IR path and not about the path a bare
`nikaia` now takes. That was already true while `bridge` was the default; what
changes is which of the two a reader meets first. Whether the two converge — and
which direction they converge in — is a decision no record makes, and D4 does not
make it either.

Revisit when Bridge-IR can carry the corpus: the number in the first bullet is
the condition, and D3's exit is what would make the bridge worth having as a
default again.

## 3. Consequences

The `rustc_private` exposure is real and is confined to one crate: a nightly
that moves `rustc_ast` costs an update to the lowering mappings and nothing in
any frontend ([ADR-003](adr-003.md) D1).

Printed output is machine-formatted and carries no comments — Bridge-IR does not
transport them. So the generated Rust is readable but is not a source file
anybody edits, which is the intent: the `.nika` file is the source, and
[ADR-012](adr-012.md) is what makes an error point back at it.
