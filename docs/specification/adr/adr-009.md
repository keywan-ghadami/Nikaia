# ADR-009: Parallel Parsing — Frames, Monoid Folds, and Format Assumptions in the Grammar

**Status:** Accepted
**Date:** September 6, 2026
**Target Version:** Nikaia 0.0.8
**Related:** [ADR-007](adr-007.md) (grammar protocol, `fold`, deferred regex terminals),
[ADR-008](adr-008.md) (view states, container-level tethering), [ADR-005](adr-005.md) D5
(`sync` and scoped parallelism), [ADR-006](adr-006.md) (`Cleanup`)
**Closes:** gap **G4** in [`examples/README.md`](../../../examples/README.md) — by dissolving it

---

## 1. Context

G4 asked for "a spelled-out form for splitting a buffer at line boundaries into one chunk per
core". `1brc.nika` currently does it by hand:

```nika
let chunks = data.split_aligned(cpu::count(), "\n")   // [G4]
let summaries = chunks.par_iter().map fn: dsl Measurements from a .collect()
let mut totals = Summary::new()
for partial in summaries { totals.merge(&partial) }
```

Specifying `split_aligned` would close the gap and get the shape wrong. The user is being asked
to restate, as an argument to a chunking helper, something the **grammar already knows**: that a
measurement ends at `"\n"`. And they are asked to hand-write the split/parallel/merge pipeline
that follows mechanically from it.

The reference 1BRC implementations (sub-2s for 13 GB on a large machine) all rest on the same
class of trick: **format assumptions**, exploited at the byte level — the record separator can
be found without parsing, names are short, temperatures are `-99.9..99.9` at fixed width, there
are at most ~10⁴ distinct keys. Those assumptions are legitimate; the competition states them.
The question for a *language* is where they may be written down. Hand-written SWAR in user code
is not an answer for Nikaia: it is unreadable, unportable, and unverifiable.

**The grammar is the right place, because it is already the file's specification.** This ADR
decides which assumptions a grammar may state, what the compiler is then allowed to generate,
and what it must verify first.

## 2. Decisions

### D1 — `@frame`: a rule may declare itself a resynchronization unit — and the compiler verifies it.

```nika
@frame
rule measurement -> Reading = name:NAME ";" => temp:TENTHS "\n" -> { Reading { name, temp } }
```

`@frame` says: **an occurrence of this rule can be found from an arbitrary offset in the input,
by scanning to the next boundary — no parse state from earlier in the file is needed.** The
boundary is inferred from the rule's trailing literal (`"\n"` here); it may be given explicitly
(`@frame("\n")`) where the rule does not end in one.

**Not a promise the user makes — a property the compiler checks.** Resynchronization is sound
exactly when the boundary cannot occur *inside* a frame. The frontend computes the terminal set
reachable from the frame rule and rejects the marker when any reachable rule can consume the
boundary byte anywhere but at the end. The canonical failure is CSV with quoted fields: a
newline inside `"…"` means "split at the next newline" lands mid-record. That program gets a
diagnostic naming the rule that can swallow the boundary, not a data-dependent wrong answer at
3 a.m. Where the property cannot be decided (a boundary computed at runtime), the marker is
likewise rejected; there is no unchecked escape hatch in this version.

**Naming.** The pre-ADR sketch spelled this `sync rule measurement`. Rejected: `sync` already
means "pure CPU, cannot pause" (Part II 12.1, and the `access`/`par_iter`/scope rules built on
it) *and* names the resynchronization token of `recover(rule, sync)`. A third meaning on the
same keyword — one that reads as "this rule is a pure computation", which every rule trivially
is — would be the worst kind of overload. `@frame` joins the existing attribute vocabulary
(`@detached`, `@borrowed`).

### D2 — Parallel parsing is a frame plus a monoid: `par_fold`.

Splitting is only half of it. A parallel parse also needs to know how two partial results
combine. Both halves are declarations the user nearly writes already:

```nika
pub rule file -> Summary =
    par_fold(measurement, Summary::new, fn(acc, m) { acc.record(m) }, Summary::merge)
```

`par_fold` is `fold` (ADR-007 / upstream) plus a **merge**. It requires its item rule to be
`@frame`; without one the compiler says so and names it. Given both, the entire pipeline —
split, boundary repair, one accumulator per chunk, merge — is generated. `1brc.nika`'s `main`
loses the chunking, the `par_iter`, the `collect` and the merge loop; what remains is
`let totals = dsl Measurements from data`.

**Parallelism stays opt-in, and that is deliberate.** The compiler could infer that a `fold`
with an associative step may run in parallel, and must not: a merge over `f64` is *not*
associative, so the number of chunks would silently change the output. `par_fold` is the user
saying "results from different chunk counts are the same to me". `1brc.nika` earns it by
accumulating in `i64` tenths and converting to `f64` only at print time — which is why the
example does that, and now says so.

**Profile polymorphism.** Under Lite, `par_fold` degrades to a sequential `fold` — same
accumulator type, same merge, same result, no threads. This is the `spawn` pattern (Part II
11.2) applied to parsing, not a new mechanism, and it keeps a `par_fold` grammar compiling
unchanged for `wasm32-*`.

### D3 — The lowering: blind split, then boundary repair.

Normative, because the edge cases are where a chunked parser silently loses or double-counts
rows:

1. The input is divided into *n* equal byte ranges, *n* = `cpu::count()` by default. No scan.
2. Each chunk except the first advances to just past the first boundary at or after its start.
   Each chunk ends at the corresponding position of the next chunk's start, so every frame is
   owned by **exactly one** chunk — the worker that finds its *end*.
3. The final chunk runs to EOF. Input not terminated by a boundary still yields its last frame;
   input ending in a boundary yields no empty trailing frame.
4. A frame longer than a chunk is not an error: a chunk whose repaired start lands at or past
   its end contributes nothing and the owning worker parses through.
5. Errors carry absolute offsets, so a diagnostic from chunk 7 points into the file, not into
   chunk 7. Under `recover`, a chunk-local failure does not abort the others.
6. Chunk count does not change results (D2 makes that the user's assertion), and it is
   observable and overridable for benchmarking.

This is the reference implementations' trick — split blindly, repair the seam — with the
correctness conditions written down rather than left to the reader.

### D4 — Scanning is a specified complexity, not a hoped-for optimization.

Finding a boundary or a `until(";")` terminator lowers to a **word-at-a-time** scan: a `u64`
load, an XOR against the broadcast byte, the standard `(x - 0x01..) & ~x & 0x80..` mask, and a
trailing-zero count. This is portable SWAR — no target feature, no runtime detection, works on
`wasm32` and therefore under Lite. Target-gated SIMD (AVX2, NEON) is a *multiversioning* layer
on top, never the baseline, so a program's performance story does not fork by target.

The spec states the guarantee as complexity, not as instruction selection: **scanning for a
byte terminator never inspects one byte at a time.** Part II 10.6's design note already reserved
the room for this ("a parser may use SIMD matching specialized to its own syntax"); D4 turns it
into a requirement with an observable consequence. The same primitive removes the upstream
`recover` implementation's byte-by-byte skip (`winnow-grammar` `TODO.md` §2, an O(n²) worst
case) — one scan primitive, two callers.

### D5 — Fixed-width numeric parsing needs bounded repetition in the grammar, not guesswork.

The branchless integer trick ("load the bytes, ignore the point, fold the sign in with a shift")
is sound only where the field's width is bounded. Today `rule DIGITS -> i32 = d:digit+` says
*unbounded*, so a compiler that emitted the fixed-width path would be inventing a constraint the
grammar never stated. The fix is one piece of syntax:

```nika
rule TENTHS -> i32 = neg:"-"? whole:digit{1,2} "." frac:digit -> { … }
```

Bounded repetition `p{n,m}` is **not** in the pinned backend (`winnow-grammar` `f4955bc`
supports `*`, `+`, `?`, `count`, `fold`; the `[^;]+` character-class form does not exist either
— regex terminals are deferred by ADR-007). It is therefore recorded here as the upstream
feature request this work depends on, and as the *only* sanctioned route to fixed-width parsing:
the format assumption is written by the person who knows it, checked by the parser, and
exploited by codegen. Until it lands, `digit+` parses as it does today.

Ordinary branch elimination (`if neg.is_some()` becoming a conditional move) needs none of this
and is already LLVM's job; it is not a Nikaia feature.

### D6 — Hashing a view: derive the hash from the first bytes, never truncate the comparison.

A view key may be hashed from its first 8 bytes mixed with its length — the reference
implementations' integer-key trick, and sound as a *hash*. What several of them additionally do
— comparing only the first 8 or 16 bytes on a probe hit — is **not** sound: two stations sharing
a 16-byte prefix would merge silently. ADR-008 D4 already fixed equality on views as
content-based; this ADR states the split explicitly, because the tempting optimization is the
one that produces a plausible wrong answer rather than a crash.

The remaining lever is the map itself: Nikaia's `HashMap` stores entries in an open-addressed
table with no per-entry allocation, so a table of ~10⁴ short keys stays in cache. That is a
stdlib guarantee; it needs no language support and no user hint.

### D7 — Teardown of large read-only buffers may be skipped at process exit.

At 13 GB the kernel's work is not free on either side: faulting the pages in, and unmapping them
at exit. The reference implementations simply do not unmap — they exit the process. Nikaia
cannot do that behind the user's back in general (ADR-006 makes teardown observable, and
ADR-008 D8 ties a mapping's release to the last tether), but the narrow case is safe and worth
having: **a read-only mapping with no `Cleanup` and no user-visible effect may be left to the
kernel at process exit.** Nothing observable changes; only the exit path gets shorter. This is
the one place where ADR-006's "cleanup always runs" is relaxed, and it is relaxed by proof of
non-observability, not by a flag.

Prefaulting (populating the mapping in parallel with a first-touch pass) is left to the
implementation as a measured optimization; it changes no semantics.

## 3. What this makes of 1BRC

The user writes down the *format*: a measurement ends at a newline (`@frame`), summaries combine
(`par_fold(…, Summary::merge)`), a name runs to the semicolon, a temperature has one decimal.
Everything the reference implementations hand-code, the compiler now has grounds to generate:
the blind split and seam repair (D3), the word-at-a-time separator scan (D4), per-worker
accumulators with no shared state (D2), zero allocation and zero refcount traffic per row
(ADR-008), and — once D5's bounded repetition exists — the fixed-width temperature parse.

The part of `main` that G4 was about disappears.

## 4. Rejected / deferred

* **`sync rule` as the frame marker** — rejected, keyword collision (D1).
* **`split_aligned(n, "\n")` as the sanctioned form** — rejected. It asks the user to repeat
  what the grammar states and to write the pipeline that follows from it. A raw chunking
  primitive on `Bytes` may still be specified later for non-grammar uses; nothing depends on it
  now, so G4 closes as dissolved rather than implemented.
* **Silent parallelization of any associative-looking `fold`** — rejected (D2): float merges
  would make output depend on core count.
* **Inferring the frame boundary without a marker** — deferred. The analysis that *checks*
  `@frame` could often also *find* one, but a grammar that happens to be splittable today would
  then silently stop being parallel after an unrelated edit. An explicit marker fails loudly.
* **Truncated key comparison** — rejected (D6).
* **A user-facing SWAR/SIMD construct** — rejected. Hardware instructions live behind
  `dsl backend::…` (ADR-007 D6); the scan guarantee (D4) is what a parser author gets instead.

## 5. Open

* **The default hasher.** Rust's std map defaults to a DoS-resistant hash because a server
  hashing attacker-controlled keys is the common case; a compute workload pays for that on every
  lookup. Nikaia has both profiles in one language, so the choice cannot be made per profile
  without reintroducing the schism ADR-005 D8c closed. The likely shape — a fast non-cryptographic
  default plus a hardened constructor that `std::http` and friends use for untrusted keys — needs
  its own ADR with the threat model written out. Not decided here.
* **Chunk-count policy** beyond `cpu::count()` (NUMA, heterogeneous cores, an oversubscribed
  container's CPU quota).
* **`par_fold` over a stream** rather than a mapped buffer (`fs::lines` under Lite): splitting
  requires random access, so the parallel form is currently buffer-only.
