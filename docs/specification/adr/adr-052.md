# ADR-052: `T?` Is a Type, `null` Is a Word, and the `Some(…)` Is the Compiler's to Write

**Status:** Accepted · **Built:** the type, the word and the wrap — see §5
**Related:** Part I 2.3 (the rule this makes true) and 3.5 (`??`, which was
already built and had nothing to be built *on*), Part III 15.2 (the mapping, Rust
`Option<T>` to Nikaia `T?`), [ADR-051](adr-051.md) D1 (`null` joins the reserved
list), [ADR-024](adr-024.md) (the ledger, which writes `T?` and not `Option[T]`),
[ADR-028](adr-028.md) (why the wrap is decided in the checker and written in the
emitter), [ADR-010](adr-010.md) D1 (the fail-closed direction the wrap rule takes)

## 1. Context

Part I 2.3 says types are non-nullable by default and that a trailing `?` allows
the absence of a value. **Neither line of its own example was accepted**: `&str?`
was a parse error, and `null` was read as an ordinary name.

And the state was worse than "unbuilt", because Part I 3.5's `??` *was* built —
`a ?? b` lowered to `a.unwrap_or_else(|| b.into())`, an operation on an
`Option` in a language with no way to write one. So the only values it could be
used on came out of `std`, and the type the whole section is about could not be
named by a program.

## 2. Decisions

### D1 — `T?` is a type, and a trailing `?` is how it is written.

```nika
let strictly_string: String = "Hello".to_string()
let mut maybe_string: String? = null
maybe_string = "World".to_string()
```

It lowers to `Option<T>`, which is the mapping Part III 15.2 already wrote the
other way round. The `?` comes **last**, after the type's arguments, so
`Vec[i64]?` is a nullable list and `Vec[i64?]` is a list of nullables.

**`Option` is what it lowers to and not what it is called.** A diagnostic says
`String?`; `Option[String]` is a name no program can write, and a message that
used it would be a message about the generated file (Part III, C.1).

### D2 — The `?` is a flag in the AST and a wrapper in the type.

Two representations of one thing, on purpose.

In the AST it sits beside `is_view`, because **`&str?` is a nullable view** and
the two are independent: a wrapper there would have to be unwrapped by everything
that asks whether a declaration names a borrow.

In `contracts::ty::Ty` it is `Nullable(Box<Ty>)`, because every reader of a type
already recurses — so a wrapper is one arm per reader instead of a condition
inside each of them, and the compiler names the readers that forgot.

### D3 — A plain `T` stands where a `T?` is wanted. Nothing stands the other way.

This is the one widening the language has, and Part I 2.3 is what asks for it:
`maybe_string = "World"` hands a `String` to a `String?`. The other direction is
refused, because that is the whole point of the type being separate — and `??`
(Part I 3.5) is how a program gets from a `T?` back to a `T`.

### D4 — The `Some(…)` is written by the compiler, and the checker says where.

The language below needs the constructor. There is no `Some` in Nikaia and must
not be: a program says `maybe_string = "World"`, and a wrapper the programmer has
to write would make the type's whole purpose into paperwork.

**Whether the value beside the `=` is *already* nullable is a question about
types, and the emitter has none** ([ADR-028](adr-028.md)). So the checker records
the statements where a wrap is needed and the emitter writes it — the same
arrangement, for the same reason, as `shared_sites` ([ADR-040](adr-040.md) D1) and
the fallible loops ([ADR-025](adr-025.md) D1).

**Two ways a value is known not to be nullable already, and a type is only the
first:**

* its type says so — anything the checker worked out that is not a `T?`;
* **it is a literal**, which no literal ever is. That is not a convenience. A
  number has no type of its own on purpose (Part I 2.4), so `return 42` against a
  declared `i64?` answers *unknown* — and the type alone would leave the
  commonest case in the section unwrapped.

Everything else is left alone, which is the fail-closed direction
([ADR-010](adr-010.md) D1): wrapping a value that is already an `Option<T>` would
make an `Option<Option<T>>`, so the set never claims a wrap that is not needed.

### D5 — `null` has no type of its own, and is not refused for it.

`null` answers "a `T?` of it-does-not-say", so anything nullable fits it and
nothing needs wrapping around it.

**`let m = null` on its own is not refused here**, and that is C.4 rather than an
oversight: `let mut m = null` followed by `m = "hi"` is a correct program, and
this checker has no inference to tell it from the one where nothing ever says. So
`rustc` asks for the annotation, which is the honest answer — this compiler cannot
say what the value is the absence of, and neither can the program.

`null` is a **reserved word** ([ADR-051](adr-051.md) D1), which is what keeps the
other reading away: as a name it would be `NK1117`, and as a name something
declared it would be a different program.

## 3. Consequences

**Part I 3.5's `??` has something to be used on**, and needed no change: it
already lowered to `unwrap_or_else`, and the type it operates on is now writable.

**The ledger writes `T?`.** A signature comes back as `(id: i64) -> i64?` — the
program's own spelling, in the file a consumer reads.

**A `T?` crosses into foreign code exactly as its `T` does** ([ADR-045](adr-045.md)),
because that is what it lowers to: an `Option<T>` is `Send` when `T` is, and holds
one `T` or nothing.

**`(A, B)?` is deliberately absent.** Part I 2.3 does not write it, and a form the
emitter would have to invent a lowering for is worse built than unbuilt.

## 4. What this does not decide

* **`?.`, safe navigation** (Part I 3.5). It is the other half of that section and
  is unbuilt. The lowering is not the difficulty — `x.map(|v| v.field)` — it is
  that a field which is *itself* nullable needs `and_then` instead, or the result
  is an `Option<Option<T>>`; which of the two is right is a question about the
  field's declared type, so it goes through the checker like D4's wrap does.
* **The wrap at an argument.** D4 covers an annotated `let`, an assignment and a
  `return`, each of which the checker can name by the statement it stands in. An
  argument inside a call has no such key — expressions carry no spans — so
  `takes(42)` where the parameter is an `i64?` is not wrapped yet
  (`docs/open-work.md`).
* **Whether `null` is a value or the absence of one at run time.** It is `None`,
  and nothing in this record depends on there being a distinction.

## 5. What is built

**D1 through D5.** `T?` parses and lowers, `null` is a word, and the `Some(…)` is
written at an annotated `let`, an assignment and a `return`.

`crates/nikaia/tests/nullable.rs` **compiles** what it lowers rather than
comparing strings, because whether the wrap landed in the right place is settled
by the language below and reading the emitted text would only say that this
compiler agrees with itself. It covers Part I 2.3's own example, a nullable
result with the wrap at a `return`, a value that is already nullable not being
wrapped twice, the ledger round-trip, D3's rule in both directions, and a
diagnostic that says `i64?` and not `Option[i64]`.

**Not built:** `?.`, and the wrap at an argument. §4 has both.
