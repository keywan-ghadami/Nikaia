# ADR-003: Hub-and-Spoke — Bridge-IR and a Generic Orchestrator

**Status:** Accepted · **Built:** yes
**Supersedes, in part:** [ADR-001](adr-001.md) and [ADR-002](adr-002.md) — the
coupling to `rustc` internals only. What those records decide about the pinned
toolchain, the parser backend, the bootstrap stages and the cache key is
untouched; see the [supersession section](README.md#what-supersedes-what).
**Related:** [ADR-004](adr-004.md) (how Bridge-IR reaches machine code),
[ADR-011](adr-011.md) (the Nikaia-side lowering), [ADR-021](adr-021.md) (D2's
build cache)

## 1. Context

Building the prototype against `rustc` internals showed three costs. The
`rustc_private` APIs move on every nightly, so the whole *language frontend*
needed refactoring whenever the *backend* changed. Every future language would
have to re-implement the cargo-wrapping and compiler-bootstrapping layer.
And testing the parser meant starting the entire Rust compiler.

All three come from one mistake: the language and the machinery that compiles it
were the same program.

## 2. Decisions

### D1 — A frontend targets Bridge-IR, never `rustc_ast`.

`bridge-ir` is a pure-data crate: no `NodeId`, no interned strings, spans are
`Range<usize>` byte offsets, and it expects fully expanded code — macros are
gone before this point.

The stability guarantee follows from it having no compiler state to go stale: a
`rustc` change reaches the executor and stops there. A language designer never
touches a compiler data structure, and a frontend is tested by asserting on the
Bridge-IR it produces, with no compiler in the loop.

### D2 — CLI wrapping, caching and Cargo instrumentation live in a generic orchestrator.

`bridge-orchestrator` owns `RUSTC_WORKSPACE_WRAPPER` injection, incremental
build checks and the build switches, and offers a `LanguageFrontend` trait. A
language's CLI is a shim that instantiates it.

This is the part [ADR-002](adr-002.md) would have duplicated per language. What
the cache actually keys on is [ADR-021](adr-021.md).

### D3 — The waist is narrow on purpose, and the frontend does the creative work.

Bridge-IR carries what has a direct representation in Rust. A construct without
one is lowered in the *frontend* into constructs that do, rather than widening
the protocol.

A widened protocol is one the executor must implement and every other frontend
must ignore. Nikaia's own high-level constructs — `@detached`, a
`Shared[Locked[T]]` whose expansion follows a switch, implicit async — all reach the backend this way.

### D4 — Byte offsets are the frontend's responsibility, and are validated.

The executor maps `Range<usize>` into a `SourceMap`, so an offset the frontend
computed wrongly becomes an error reported at the wrong place — a diagnostics
bug with no visible cause. `bridge-ir` therefore validates that ranges lie
within the file.

## 3. Consequences

Data is transformed twice — Nikaia AST to Bridge-IR to `rustc_ast` — and that
compile-time cost is the price of the isolation. Adding a second language needs
a parser crate and nothing else.

The four crates live in one workspace rather than the two repositories this
record originally specified. The boundary is enforced by the dependency
direction instead: `bridge-ir` depends on nothing, and nothing Nikaia-specific
appears in it, in `bridge-orchestrator` or in `rustc-executor`.
