# ADR-010: Input Provenance — Where the Security Requirement Is Stated

**Status:** Accepted; **implemented** for the hasher (September 9, 2026)
**Date:** September 6, 2026
**Target Version:** Nikaia 0.0.8
**Implementation:** the sources are in `std`'s ledger ([ADR-020](adr-020.md)), the join is
`contracts::trust`, and `nikaia --trust` prints it. Measured at **26 %** of the flagship's
instructions ([ADR-011](adr-011.md) §4). What Stage 0's analysis is: one buffer, because
[ADR-008](adr-008.md) gives a compilation unit one input lifetime. D3's `trusted:` argument at
the source, D4's `@untrusted grammar`, and the D5 requirement that a build *fail* without an
entropy source are not built.
**Resolves:** gap **G8** (the default hasher), left open by [ADR-009](adr-009.md) §5
**Related:** [ADR-008](adr-008.md) (view provenance, container tethering), [ADR-005](adr-005.md)
D3/D8 (Ledger, determinism), [ADR-007](adr-007.md) (DSL protocol), [ADR-009](adr-009.md) D6
(view hashing)

## 1. Context — and a correction

ADR-009 §5 left the default hasher open and framed it as a profile problem: "Nikaia has both
profiles in one language, so the choice cannot be made per profile." **That framing is wrong,
and this ADR corrects it.**

The threat is hash flooding: an adversary who chooses keys can drive an open-addressed table
into quadratic behaviour. Whether the runtime is single-threaded has nothing to do with it. A
Lite HTTP server hashing attacker-supplied header names is exactly as vulnerable as an Advanced
one — arguably more so, because one event loop is one thing to stall. Conversely, an Advanced
compute job aggregating a data file the operator chose has no adversary in either profile. The
profile answers "which runtime", never "who supplied this data".

The real axis is **provenance**: where the keys came from. That is a property of the input, it
is known at the place where the input enters the program or where a DSL is applied to it, and it
is a decision the *user* must make at that semantic level — not a global default the language
picks on their behalf and not something inferred from the runtime shape.

Rust's std map hashes everything with a DoS-resistant function because Rust has no
whole-program provenance information: with nothing to distinguish the two cases, assuming the
worst everywhere is the only safe global default, and every compute workload pays for it.
Nikaia already tracks where a view points (ADR-008) and already solves whole-program contracts
(ADR-005 D3). It can therefore be exact instead of pessimistic — and pay for hardening only
where an adversary actually exists.

## 2. Decisions

### D1 — Trust is a property of sources, expressed as a two-state lattice.

`Trusted ⊑ Untrusted`. Every buffer entering the program carries one of the two. Values derived
from a buffer inherit its state; a container's state is the **join** of what goes into it, so a
map that receives one untrusted key is untrusted. The join is conservative in the safe
direction, always.

This rides machinery that exists. ADR-008 already ties every view to the buffer it points into
and records the result in the Borrow Contract Ledger; the trust bit travels the same edges,
lands in the same file, and is solved by the same monotone fixpoint — so ADR-005 D8's
byte-determinism, ban list and CI tests cover it unchanged. A two-element lattice adds no
solver, no new pass, and no new determinism surface.

**Barriers widen to `Untrusted`.** Where provenance cannot be established — a `dyn` boundary,
an FFI value, a Rust dependency's return — the state is `Untrusted`, never `Trusted`. This is
the opposite direction from ADR-008 D7's representation barrier, and deliberately so: there the
conservative answer is the wider representation, here it is the safer one. An analysis that
fails open is a vulnerability generator.

### D2 — The standard library classifies its own sources; the defaults follow the channel.

Users do not classify `std`. The library states, per source, who supplied the bytes:

| Source | Default | Why |
| :--- | :--- | :--- |
| `http` request line, headers, query, body; `net` sockets; IPC; WASM host imports | **Untrusted** | a remote peer chose these bytes |
| `fs` reads and maps, `cli::args`, `env`, compile-time data (`include`, literals) | **Trusted** | the operator chose these bytes |
| `db` result rows | **Untrusted** | second-order: rows may hold what a user stored earlier |

The `db` row is the interesting one, and it is why "trusted = local" would be too crude: stored
data is attacker-chosen data with a delay. Any source whose content can be influenced by
someone other than the operator is untrusted, whatever transport it arrives on.

### D3 — The user states the requirement at the source, in both directions.

The default is a default, not a verdict. The decision belongs at the semantic level, which is
the place the data enters:

```nika
// A service that processes files uploaded by strangers. Local path, hostile bytes.
let data = fs::map(path; trusted: false)

// An internal benchmark harness reading a fixture the test wrote itself.
let body = socket.read_all(; trusted: true)
```

Both forms use the existing named-parameter convention (Part III 17.1). Both are recorded in
the Ledger with their source location, which makes the security review of a Nikaia program a
grep over one generated file — every place trust was asserted, in one list, diffable across
commits — rather than an audit of every call site.

The same marker is available on a function parameter, so a library can state what it assumes
about data it is handed rather than inheriting the join of its callers.

### D4 — A grammar may declare a floor. This is the DSL's answer.

A grammar *is* the specification of an input format, and its author often knows the format's
threat model better than the person applying it. A grammar written for a wire protocol says so
once:

```nika
@untrusted
grammar HttpHeaders { … }
```

The effective trust of a parse is `join(grammar floor, buffer trust)`. A grammar marked
`@untrusted` therefore cannot be used in trusting mode by accident, no matter what buffer it is
pointed at — the DSL author protects every one of their users. A grammar with no marker takes
its trust from the input, which is the common case: `Measurements` in `1brc.nika` is neither
inherently safe nor inherently hostile, and the deployment site is what decides.

There is deliberately no `@trusted` floor on a grammar: a format cannot make its input safe.

### D5 — What the compiler does with it: choose the hasher, and nothing else.

| Effective trust | Hash | Rationale |
| :--- | :--- | :--- |
| `Trusted` | fast non-cryptographic hash, fixed seed | no adversary chooses these keys |
| `Untrusted` | keyed hash, per-process random seed | key choice cannot be aimed at the table |

Everything else about the map is identical in both cases: same open-addressed table, same
absence of per-entry allocation, same API, and — per ADR-008 D4 and ADR-009 D6 — the same
full-content equality. Trust never weakens a correctness property; it selects a hash function.

The profile does enter here, but only as an implementation detail of *how*, exactly as the user
put it: the compiler knows the profile and the stated requirement, and picks the code. It is
never the thing that decides *whether* hardening is needed.

**The random seed must be real.** On a target with no entropy source the build fails rather than
falling back to a fixed seed, because a keyed hash with a predictable key is the vulnerability
wearing the mitigation's clothes.

### D6 — Consequence: map iteration order is unspecified and may vary between runs.

Randomized seeding means the iteration order of an untrusted map differs from run to run. This
is stated in the spec rather than discovered: a program that needs an order asks for one (the
ordered-iteration form, gap G5). The compiler's own ledger-emitting paths are already forbidden
from iterating hash order at all (ADR-005 D8's ban list), so the rule the language enforces on
itself is the rule it teaches.

### D7 — The choice is visible, never a mystery.

`nikaia explain --trust` prints the provenance of every buffer and the hasher chosen for every
map, alongside `--tethers` (ADR-008 D6). Where a hardened map sits in a hot loop, a lint says so
and names the source that made it untrusted — so the answer to "why is this slower than I
expected" is one command, and the fix (state the trust, or copy the keys out of the untrusted
path) is in the message.

### D8 — Build the mechanism, decide only the hasher here.

Provenance is a taint lattice, and hashing is one consumer. The obvious second is **G7** (HTML
escaping at template holes): a hole fed untrusted text is precisely what the lattice describes.
That gap is *not* decided here, and one caution belongs on the record now — escaping at a hole
must stay **unconditional**, defence in depth, because a provenance analysis that silently
skips escaping on "trusted" data turns one wrong `trusted: true` into an XSS hole. Provenance
may add evidence and lints there; it may not switch escaping off.

Other plausible consumers (SQL parameterization, path traversal, log injection) are noted as
motivation for building this as a general mechanism rather than a hasher special case. Each
needs its own decision.

## 3. What this makes of the two examples

* **`1brc.nika`** maps a file named on the command line: operator-supplied, so `Trusted`, so a
  fast hash — the benchmark does not pay for a threat it does not have, and nobody wrote a line
  about hashing. Were the same program deployed to crunch uploads from strangers, the change is
  one named argument at the `fs::map`, and the Ledger records it.
* **`fortunes.nika`** (TechEmpower) hashes query parameters and header names from the socket:
  `Untrusted` by default, hardened without anyone remembering to ask, and the DSL for the wire
  format can pin it with `@untrusted` so that no later use can lower it.

The 1BRC-shaped program and the server-shaped program get different code from the same source
text, and the difference is derived from where the bytes came from — not from a profile flag and
not from a global default that is wrong for one of them.

## 4. Rejected alternatives

* **A global default (either one).** Fast-everywhere ships a DoS bug in every server written in
  the language; hardened-everywhere taxes every compute workload for an adversary that does not
  exist. The information needed to choose is available; refusing to use it is the actual
  mistake.
* **Per-profile defaults** (Lite hardened, Advanced fast) — rejected: it answers the wrong
  question (see §1), silently changes security properties when a library moves between
  profiles, and reopens the profile schism ADR-005 D8c closed.
* **A hardened constructor the user must remember** (`HashMap::hardened()`) — rejected as the
  primary mechanism. Security that depends on remembering is the model Nikaia exists to
  replace; the safe case must be what happens when nobody thought about it. The explicit form
  survives only as the override in D3, where the user is thinking about it by construction.
* **Pure inference with no user statement** — rejected: the compiler cannot know that a local
  file holds hostile uploads, or that a socket is a trusted internal peer. Inference sets the
  default; the user sets the truth.
* **Adaptive hashing** (start fast, detect pathological collisions, rehash keyed) — deferred,
  not rejected. It is attractive because it needs no provenance at all, but it makes worst-case
  latency data-dependent and complicates the table; revisit if measurement ever shows the keyed
  hash to be the bottleneck in a real server.

## 5. Risks

* **A wrong `trusted: true` is a silent vulnerability.** Mitigations: barriers fail safe (D1),
  `std` owns the source classification so the common cases need no user judgement (D2), every
  override is recorded in one auditable file (D3), and a DSL author can pin the floor beyond a
  user's reach (D4).
* **This defends against hash flooding only.** Other algorithmic-complexity attacks — quadratic
  parsing, backtracking, unbounded allocation from a length field — are untouched. The grammar
  protocol's own limits (bounded repetition, ADR-009 D5) are the adjacent lever; neither is
  claimed here.
* **Provenance is only as good as the source table.** Adding a `std` source without classifying
  it defaults it to `Untrusted` (safe) but may surprise; the table is part of the module's spec,
  not an implementation note.
