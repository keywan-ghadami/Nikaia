# ADR-012: Diagnostics — Reporting Errors in the File the User Wrote

**Status:** Accepted
**Date:** September 7, 2026
**Target Version:** Nikaia 0.0.8 (bootstrap compiler)
**Closes:** [ADR-011](adr-011.md) §4, "Spans"
**Related:** [ADR-001](adr-001.md) (Stage 0 is a transpiler), [ADR-011](adr-011.md) D2 (the
lowering is name for name) and D3 (one checker, upstream), [ADR-009](adr-009.md) D1 (the frame
check whose verdict this has to deliver)

---

## 1. Context

Stage 0 emits Rust and hands it to `rustc`. Everything that then goes wrong — `rustc`'s own type
errors and the parser backend's frame check alike — is reported against a file nobody wrote:

```text
error: `until(…)` in rule `NAME` can run through the boundary "\n" of frame `MEASUREMENT`
 --> measurements.rs:10:15
```

`measurements.rs` is generated. Line 10 is generated. The user has `measurements.nika` open.

ADR-011 D3 already refused the obvious-looking fix — re-implementing the frame check in Nikaia so
that it could be reported natively — because two implementations of "checked, never rewritten"
drift, and the drift that matters is Nikaia accepting a grammar the backend rejects. That refusal
left the error's *provenance* unsolved and named it as the open item. This ADR solves it, and it
solves it for every error at once rather than for the frame check alone: the frame check is one
diagnostic among many, and a mechanism that only fixed that one would leave every type error
still pointing into generated code.

---

## 2. Decisions

### D1 — The lowering emits a source map, and the map is the whole mechanism.

Emitting is a walk over the AST; while it walks, the emitter records which byte range of its
output each node produced. A diagnostic reported at an offset in the generated Rust is traded for
the `.nika` span that wrote those bytes.

This is the ordinary answer to this ordinary problem — it is what a JavaScript build tool does —
and it is worth naming what it buys over the alternative: **one mechanism for all error classes**.
The frame check, an unresolved name, a borrow error, a type mismatch in an action block, a future
lint from the backend: each is a byte offset, and each maps back the same way. A second checker
would have solved exactly one of them.

### D2 — The map is derived, never stored.

The lowering is deterministic, so the map is recomputed from the `.nika` file whenever it is
needed rather than written next to the `.rs` and kept in step:

```sh
cargo build --message-format=json | nikaia --input measurements.nika --explain
```

`--explain` re-runs the emitter internally to rebuild the map, then translates what it reads on
stdin. There is no artifact to version, no format to document, and no way for the map to be stale
with respect to the source it describes — the two are the same file.

### D3 — Positions are corrected; messages are not.

The text of a diagnostic is passed through unchanged. This is not laziness, it is ADR-011 D2
paying out: because the lowering is name for name, `NAME` and `MEASUREMENT` in the backend's
message *are* the user's rule names, and `no method to_digit on char` is about the `d.to_digit()`
they wrote. The sentence was already about the Nikaia source; only the position was wrong.

Correcting a position is a lookup. Translating a text would be a second compiler — the same
argument that ADR-011 D3 made about the check itself, applied to what the check says.

### D4 — The innermost span wins, and the granularity is stated.

Nodes are recorded as they are emitted, innermost first, so a lookup takes the first range that
contains the offset. What is recorded: items, grammar rules, every grammar pattern, and
statements. Expressions are not; a type error inside a statement is reported on that statement.

That is a real limit and it is here rather than in a footnote: `let x = f(g(y))` blames the whole
`let`. Expression spans are the obvious next increment and need no new mechanism — one more
`from()` per expression node — but they are not claimed today.

### D5 — An unmapped diagnostic says so.

Not every byte of the output comes from the source: the preamble, the `use` lines, the binding
supplied for a bare `par_fold` (ADR-011 D5). An error reported there has no Nikaia span, and it
is reported against the generated file with that stated:

```text
error: measurements.rs:3: <message> (no Nikaia source maps to this)
```

Guessing the nearest line would be worse than admitting the gap, because the nearest line is
frequently unrelated and a user cannot tell an invented position from a real one.

### D6 — Spans come from the parser backend, not from a scheme of Nikaia's own.

`winnow-grammar` already offers span injection: a rule written `-> T @=` gets `_span`, the byte
range it matched, in scope of its action block. Every node that carries a span in the Nikaia AST
gets it from there. No offset arithmetic, no second stream, and no way for a span to disagree
with what the parser actually consumed.

### D7 — Nikaia is a filter over rustc's JSON, not a build system.

`--error-format=json` is a stable, documented interface that gives file, line, column and byte
offsets; nothing is scraped out of rendered text. Nikaia reads it on stdin and writes diagnostics
about the `.nika` file, which composes with whatever drives the build (`cargo`, a script, later
the orchestrator of ADR-003) instead of replacing it.

## 3. What this makes of the corpus

`tests/fixtures/broken_frame.nika` writes `until(";")` under a `@frame(boundary: "\n")` — a name
without a semicolon in it would run past the newline and swallow the next record, which is exactly
what makes cutting the input at newlines unsound. `crates/nikaia/tests/diagnostics.rs` lowers it,
compiles the emitted Rust with the same `rustc` that built the test, and asserts that what comes
back is reported at the pattern in the `.nika` file:

```text
error: broken_frame.nika:15:11: `until(…)` in rule `NAME` can run through the boundary "\n" of
frame `MEASUREMENT`; add the boundary as an alternative of the terminator so the scan stops
there: `until(… | frame_end)`
  15 |         s:until(";")
                 ^^^^^^^^^^
```

The test is the pipeline, not a simulation of it: the frame check runs where it really runs, in a
proc macro during `rustc`'s macro expansion, and the assertion is on the line number a user would
read.

---

## 4. Rejected alternatives

* **Re-implement the checks in Nikaia so errors are native.** Rejected in ADR-011 D3 and not
  reopened. It answers one error class, costs a second implementation of a specification, and the
  failure mode is silent divergence. A map answers all classes and cannot diverge from anything.
* **Write the map next to the generated file.** Rejected in D2: an artifact that can go stale, a
  format to version, and a second thing to keep in the build. Determinism makes it unnecessary.
* **Rewrite the messages into Nikaia's own vocabulary.** Rejected in D3. It would be a second
  compiler's worth of knowledge, kept in step by hand, to improve sentences that are already
  correct.
* **Marker comments in the emitted Rust** (`// nikaia:17`) instead of a map. Rejected: it changes
  the text that gets compiled, does not survive rustc's own spans into macro expansions, and
  gives line granularity where byte ranges are free.
* **A line map rather than byte ranges.** Rejected: the frame error points at a pattern, and a
  line map would blame the whole rule when the emitter can be exact for the same effort.
* **Parsing rustc's rendered output.** Rejected: `--error-format=json` exists precisely so that
  nobody has to.

---

## 5. Risks

* **The map is only as good as the emitter's discipline.** A node emitted without recording its
  span silently loses precision rather than failing. Mitigation: the tests assert specific
  mappings (the frame attribute, the offending pattern), so the paths that matter are pinned;
  a general "every node is covered" check is not attempted and would be worth having.
* **Statement granularity flatters some errors** (D4): a long statement reports one position for
  everything inside it. This gets better with expression spans, not with a different design.
* **Only rustc's diagnostics are covered.** Linker errors, panics from a proc macro, and anything
  cargo says on its own account are outside the JSON stream this reads.
* **A generated construct with no origin maps to its enclosure.** The `folded:` binding of
  ADR-011 D5 belongs to the rule it was synthesised for, and an error blaming it lands on that
  rule. That is the right answer available; a synthesised node has no truer one.
