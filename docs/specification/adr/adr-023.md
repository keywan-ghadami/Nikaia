## 1. Context

Chapter 7 specifies `throws` and `catch` and then stops. Everything a program needs in order to
actually fail is missing:

* **Nothing raises an error.** `throw TimeoutError("Too slow!")` appears exactly once in the
  specification (Part II, 12.4) and is defined nowhere. It is not in the parser either — there is a
  `kw_throws` for the declaration and no `throw` expression, and no `.nika` file uses one.
* **Nothing declares an error type.** `IoError`, `NetworkError` and `TimeoutError` occur only in
  prose, in the spec and in the ADRs. The one error type that exists is `ParseError`, and it belongs
  to `winnow-grammar` rather than to Nikaia.
* **`catch` binds the error to the name `error`.** [ADR-013](adr-013.md) D3 decided this and
  attributed it to "Part I, 7.1". 7.1 says only *"the error is available for inspection"* — the name
  appears nowhere in the chapter. The decision was made, in an implementation ADR, and then credited
  to a specification that had not been updated. `examples/access-log.nika` and `examples/json.nika`
  both depend on it.
* **Every example writes untyped `fn main() throws`.** 7.1 only ever shows
  `throws IoError, NetworkError`. Eight programs written against the specification converged on a
  form the specification does not offer.
* **A postfix `?` is used in three places, in two different meanings.** `examples/fortunes.nika`
  writes `all.fetch(db)?` and `postgres::connect(…)?`, both meaning *propagate*. Part II, 10.1 writes
  `-> { u8::from_str_radix(d, 16)? }` inside a grammar action, where there is no enclosing function
  to propagate to and it means *fail this rule*. The language has `?` as a nullable marker, `?.`,
  `??`, and a postfix `?` for optional elements inside a grammar — and no postfix `?` on an
  expression. That the one specification occurrence calls a Rust function by its Rust name is a fair
  indication of where the habit came from. D8 and D9.

This is not a gap that can wait, because three shipped mechanisms already rest on it:
[ADR-006](adr-006.md) D4 gives a function a `throws` obligation from a resource's implicit cleanup;
[ADR-020](adr-020.md) records `throws` in the ledger and ships it with `std`; Appendix C reserves the
`NK26xx` range for it. All three refer to a model that Chapter 7 does not finish describing.

**A note on what decides this.** Nothing below is settled by what the bootstrap compiler can lower
today. Where the two differ, §8 says so — the arrangement [ADR-013](adr-013.md) D7 and
[ADR-020](adr-020.md) already use, so that a weaker stage is never mistaken for the specified thing.

## 2. Decided

### D1 — `throws` carries no type list; the error set is inferred and recorded in the ledger

In source, `throws` is bare. What a function can fail with is **inferred whole-program** and written
to `nikaia.contracts`.

The argument is [ADR-005](adr-005.md) D3's, unchanged: the error set is *derived truth* — it follows
from the body — and derived truth in source code is an invitation to go stale. It is the same reason
borrow contracts are inferred rather than annotated, and it lands in the same file.

Two further reasons specific to errors:

* **The ledger already answered a narrower version of this question.** [ADR-020](adr-020.md) records
  `throws` as a boolean. The file whose entire purpose is to say what a caller must know about a body
  it cannot see already decided that "can it fail" belongs there. Recording *with what* is the same
  entry, widened.
* **A type list collides with [ADR-006](adr-006.md) D4.** A function acquires `throws` implicitly,
  because a resource it holds can fail at close. With a type list the author would have to name a
  type they never mentioned — and that type would change when they swapped a buffered file for an
  unbuffered one. That is precisely the action at a distance the ledger exists to narrate.

**The cost, stated rather than hidden.** Without a declared set, a `catch` cannot be checked against
a signature; it is checked against the inferred set. Adding a `throw` deep in a callee can therefore
make a distant `catch` non-exhaustive. This is the same failure mode ADR-005 D3 faced for borrows,
and it gets the same answer: the ledger diff narrates the cause chain — what changed, which contract
moved, which caller broke — under an `NK24xx` code.

**Why the reflexive objection does not apply.** Checked exceptions are remembered as Java's mistake.
They failed there because every type had to be written **by hand**, with no inference and no
ergonomic subsumption, so people wrote `throws Exception` or swallowed the error. The idea is older
than that failure — CLU (1975) introduced it with Liskov's argument that the exception *is* part of
the interface — and both halves survive: the interface should carry it, and writing it by hand kills
it. Inference plus a ledger is the combination Java did not have.

### D2 — `throw` exists

An error is created and raised with `throw`. Without it only `std` could fail and user code could
only propagate, which [ADR-006](adr-006.md) D4 already contradicts by handing functions failure
obligations they did not ask for.

`throw` inside a `catch` block re-raises; no separate construct.

### D3 — An error type is an enum, and it carries payload

`NotFound` without the path it did not find is a message that costs a round trip to the user to
become useful. The enum is what the language already has for "one of a fixed set of things"
(Part I, 4.4), and `match` over it is checked for completeness.

The alternative — Zig's, where an error is a bare value with no data — was considered on its merits
and rejected in §4.1.

### D4 — Exhaustiveness and extensibility live on different axes

They do not collide, because two different sets are involved:

| axis | closed or open |
| :--- | :--- |
| the variants **within** one error type | **closed** — `match` over them is exhaustive, and adding one is a breaking change, correctly |
| the set of error **types** arriving at a `catch` | **open** — inferred, and it grows when a callee gains a failure |

A `catch` matches with the patterns Part I 3.4 already defines: *"a path with `::` in it names a
variant, and a bare name binds."* `IoError::NotFound(path)` is a longer path and needs no new kind of
pattern. What the compiler supplies is the type of `error` — the sum over the inferred set at that
point.

**The residue, named.** Behind a `dyn` call or an FFI boundary the compiler cannot see the set, so
exhaustiveness there degrades to "and anything else". This is the same residue
[ADR-005](adr-005.md) D3 accepts for trait methods (the contract is the join over implementations)
and [ADR-010](adr-010.md) accepts for provenance (conservative at `dyn`/FFI). Consistent, and it
means "exhaustive" is never a claim about the whole program.

### D5 — No classification codes

An error is not given a stable numeric or symbolic classifier alongside its type. `error.code ==
io::NOT_FOUND` would be the enum again, in a weaker form: unchecked by the compiler, unable to carry
the payload, and a permanent API commitment the moment anyone matches on it. The enum is the
classifier.

The job that codes do in other languages — *let the programmer find the place* — is done here by D6,
and done better, because the answer is the place rather than a token that has to be looked up.

### D6 — An error knows where it was raised, and there is a short form of that a person can read out

Part I 7.1 already promises that file, line and stack trace are attached automatically. D6 adds the
projection that makes the promise usable across a support desk:

```
what the user sees:   Something went wrong.  (NK-2C7)
what the developer:   nikaia explain NK-2C7
                      net::fetch_config · site 2 · IoError::NotFound
                        at release:    net.nika:212
                        in your tree:  net.nika:238
```

Four properties, each load-bearing:

1. **The key is source-derived, not positional.** Module path, function, which raise site within that
   function, and the variant raised. This is [ADR-005](adr-005.md) D8's ban-list rule applied to a
   second kind of key: *"Internal counter IDs as ledger keys — not stable across runs … Keys are
   source-derived: module path + name + signature hash."* A line number would move under an edit
   above it; this does not.
2. **A developer two features ahead does not have to check out the release.** The table ships the
   line as it was; the tool resolves the key against the tree in front of you. Where the site no
   longer exists it says so instead of pointing at whatever now occupies that line.
3. **No log and no service is required.** The table is a build artifact shipped beside the binary,
   like a debug symbol file, and `nikaia explain` resolves it offline. This is the whole point: a
   team with no log aggregation gets from a screenshot to a source line. The moment a lookup in a
   log is required, a correlation identifier would be the better tool (§7).
4. **Which build is context, not identity.** Because the key is stable across builds, the same raise
   site keeps the same mark across releases — so occurrences aggregate for free. The application
   reports its own version next to the mark; the mark itself does not have to carry it.

The **derivation** is a language property, because it needs the source map [ADR-012](adr-012.md)
already builds. Whether a mark is *shown* is the application's decision, per
[ADR-018](adr-018.md).

### D7 — The default rendering of an error is short and safe; detail is asked for

`{error}` in an interpolated string yields the message and, where the application asks for it, the
origin mark. It never yields the stack trace.

`error.full()` yields everything. (This document first wrote `{error:full}` and claimed it needed no new syntax; [ADR-036](adr-036.md) D4 shows why that was wrong, and why a method call needs even less.) The original argument: Part I 2.5 already says what follows
the first colon in a hole describes *how* to write the value, and [ADR-013](adr-013.md) D6 already
implements format specs in holes.

The rule is that the form you get without thinking is the form that is safe to put in front of a
stranger. [ADR-018](adr-018.md) established the underlying constraint — an error message is written
for the operator, which is why a failing handler answers with a generic body and logs the rest — and
D7 is that constraint made true of the default rendering rather than of one call site in `http`.

### D8 — There is no postfix `?`

`throws` propagates on its own (Part I, 7.1: *"it 'bubbles up' to the caller automatically"*), so an
operator that marks propagation marks nothing. `all.fetch(db)` and `all.fetch(db)?` would mean the
same, and a character that means nothing is a character to trip over. Rust needs `?` because
propagation there is explicit; here there is no `match` being abbreviated.

**The decisive argument is that implicit async already answered this question, in the other
direction.** A Nikaia program has three invisible control-flow events:

| event | marked? | decided in |
| :--- | :--- | :--- |
| a call may **pause** | no — there is no `await` | Part I, 8.1 |
| a block's end may **pause and fail** | no — nothing marks it | [ADR-006](adr-006.md) D1/D4 |
| a call may **fail and return early** | this decision | — |

Two of the three are deliberately unmarked. Marking the third is **worse than marking none**: a `?`
on one line implies the lines without one are safe, and they are not — every one of them may pause,
and the closing brace may fail. Half-visibility is misleading visibility. Marking all three would be
`async`/`await` with extra steps, which is the bet the language exists to refuse.

**There are four now.** [ADR-025](adr-025.md) D2 added a loop whose step can fail, and took this
argument rather than a marker — Swift writes `for try await line in …` and Zig `while (try
it.next())`, and both are the same answer with a sigil on it. The table above is the shorter version
of the one there.

Three supporting reasons:

* **It is named as the enemy.** The README's list of ceremony that costs a generator its context
  budget reads "`async`/`await` plumbing, lifetime annotations, `Arc::clone` dances, **error-
  propagation chains**", and its example is annotated "no `async`, no `await`, no `.unwrap()`".
* **The character is already carrying four jobs**: `String?` (nullable), `?.` (safe navigation),
  `??` (coalescing), and, inside a grammar, a postfix `?` for an optional element. The fifth would
  collide with the fourth in the same file, because action blocks hold ordinary expressions.
* **One way to say a thing.** [ADR-022](adr-022.md) removed `fn:` this week for the same reason.

**The honest cost.** After this, the source no longer distinguishes a call that can fail from one
that cannot, and a reviewer reading a diff in a browser has lost that. The ledger records `throws`
per function ([ADR-020](adr-020.md)) and tooling can show it for all four events rather than one —
but not in a pull request. That is the price, and it is real.

`examples/fortunes.nika`'s two uses are removed. The third occurrence is not an expression, and is
D9.

### D9 — A grammar action may fail, and the commit point decides what that means

A rule has two halves that fail differently. **The pattern says what is well-formed**, and its
failure is defined: backtrack, or past a commit point, stop. **The action says what is meaningful**,
and its failure had no definition at all. Every non-toy grammar lives in the gap between them —
`digit+` matches `99999999999999999999` and it is not an `i32`, `digit{2} "-" digit{2}` matches
`31-02` and it is not a date, `"\\u" hex{4}` matches `\uD800` and it is not a scalar value.

Nikaia has two failure disciplines meeting at that point: a PEG failure means *try the next
alternative*, a `throws` failure means *unwind to the nearest `catch`*. An action block is ordinary
Nikaia, so it can raise the second inside the first's machinery.

**The decision: the commit point already draws this line, and Part II 10.1 already says so.**

> *"Once the parser passes a commit point, it stays in this branch — **a later failure is an
> error**, not a reason to silently try the next alternative."*

It says *a later failure*, not *a later pattern failure*. So:

* **before `=>`** — a failing action fails the match, exactly as a failing pattern does. The parse
  backtracks and tries the next alternative.
* **past `=>`** — the error leaves the parser as the Nikaia error it is, with the type D3 gave it,
  the payload, and the origin mark of D6, and reaches the `catch` beside the `dsl … from …`.

Four reasons this is the answer rather than a clever one:

1. **It is not a new concept.** `=>` exists to separate "try something else" from "this is wrong".
   Applying it to one more kind of failure adds nothing to learn.
2. **It settles the side-effect problem for free.** Backtracking over a failed action is dangerous
   because *earlier* actions in the sequence already ran, and commit points are already how a
   grammar author makes that safe. `par_fold`'s accumulator becomes a checkable rule: an
   accumulating rule must be committed.
3. **The backend has both modes already.** `winnow` distinguishes a backtracking error from a cut
   one, and Nikaia's `=>` is passed straight through to `winnow-grammar`'s (`Pattern::Cut`,
   `crates/nikaia/src/emit/mod.rs`). Nothing is invented, one thing is routed.
4. **It gives the author the choice without new syntax** — which is what a separate spelling
   (PEG.js's `expected()` versus `error()`, ANTLR's semantic predicates) buys at the cost of a
   second construct.

**This is not a marker, and the distinction matters** because [ADR-025](adr-025.md) D2 has just
refused one. `=>` does not say *that* something can fail; it says *where backtracking stops*, which
is a grammar concept that predates this decision and means the same as before.

**Where the pattern can say it, the pattern says it.** ADR-009 D5 already requires a width bound in
the grammar (`digit{1,2}`) so that `TENTHS` *rejects* a three-digit temperature rather than parsing
one and checking afterwards. An action validates only what a PEG cannot express.

**Three things this settles on the way:**

* **What the error is before the commit point.** Its message becomes the expectation text and the
  payload is dropped. Nothing is lost that anyone sees: a speculative alternative's error is
  discarded, and only its position survives into the furthest-failure ranking the corpus work rests
  on (`docs/error-corpus.md`).
* **Two positions, one error.** A failing action inside a `par_fold` piece has a position in the
  input (ADR-009 D3: in the whole file, not in the piece a core held) *and* an origin mark in the
  program (D6). Both are reported, because they answer different questions — where in the data, and
  where in the code. [ADR-012](adr-012.md) already carries two locations for a backend diagnostic.
* **`recover(…)` does not catch it.** Recovery resynchronises after a *syntax* failure; a semantic
  error that has passed a commit point is precisely what should not be skipped to the next sync
  token. ADR-009 already refuses `recover` inside a frame for a neighbouring reason.

**Following [ADR-025](adr-025.md), which answered the same question for loops:** the fact that a
rule can fail is recorded in the ledger, like `sync`, `throws` and `iterates` before it (D6 there),
because a caller of a published grammar cannot see the body; and Stage 0 lowers it by asking the
**type checker** whether the action block can fail ([ADR-024](adr-024.md)), never by matching a name
(D7 there). ADR-024 D8 fits without strain: an action still answers to its rule's return type, and
its failure runs beside that type exactly as a function's does.

**What this hands to another ADR.** A grammar evaluated at compile time with a failing action fails
the *build*, and under [ADR-026](adr-026.md) D1 the evaluator receives bytes and returns bytes — so
a failing action's payload has to cross that boundary as data. That is ADR-026's Q1, not this
document's.

## 3. What payload may cost, and where it may not land

D3 says errors carry data. That has a price, and the price has a place it must not reach.

**The threshold is architectural, and it is 16 bytes.** On x86-64 a returned value of up to two
words comes back in registers; beyond that the caller allocates stack space and passes a hidden
pointer, and every call pays a memory round trip. The question is therefore not how wide an error
is, but whether the returned `Result` stays under the threshold.

**The discriminant is what pushes it over, not the payload.** The success and error values overlap —
they are a union, not a concatenation — so the width is `max`, not the sum. But the tag is
additional, and alignment rounds it up to a whole word:

```
8 bytes of error + 1 byte of tag  →  align 8  →  16 bytes
```

For a function that returns nothing and can fail — the most common shape there is — "returns
nothing" becomes two registers. One byte of tag doubles the return value.

### D10 — The error representation is pointer-sized, and the success path pays no memory round trip

This is a cost guarantee in the sense [ADR-009](adr-009.md) D4 already uses, where word-at-a-time
scanning is *"a specified complexity rather than a hoped-for optimization"*. It is normative, not
aspirational.

What it means concretely: an error value occupies one word whether or not its variants carry data.
The compiler picks the encoding per type — all-empty variants are the tag itself and never allocate;
a payload that fits (a view, a number) is packed in; anything larger is boxed, and *that* is the one
place an allocation happens. Rust's own `io::Error` is the existence proof: eight bytes holding
either an errno, a static message, or a pointer to a boxed payload.

Two consequences worth stating:

* **A program whose errors carry nothing pays exactly what a program whose errors carry paths pays.**
  The objection this decision answers is that everyone should not fund the richest case.
* **[ADR-008](adr-008.md) is the reason the common case does not allocate.** A path that came from a
  buffer travels in the error as a **view**, not a `String`. No allocation, and the buffer outlives
  the error by construction. The honest cost is the usual one for tethers — a view into a 13 GB
  mapping pins 13 GB — with the usual escape, `.to_owned()`.

**What remains, and is not payload's fault.** A `throws` call has to test and branch on return in
order to propagate: one predictable branch per call. That cost belongs to checked errors, not to
payload — Zig pays it too, with its two-byte errors. The only design that removes it is unwinding
(§6).

## 4. Open for later

One question this document does not answer — a choice between two encodings that **both satisfy
D10**. [ADR-006](adr-006.md) ends the same way, and is Accepted. The second, what an automatic
stack trace costs, was answered by [ADR-036](adr-036.md) and is kept below with its number, because
it also corrected two things this document had got wrong.

### 4.1 — Where does the success/failure decision live?

Two places, and both satisfy D10.

**A — in the value.** A tag, ideally swallowed by a niche: if the error representation has a bit
pattern that cannot occur, the discriminant hides in it and the pair stays one word. This is what a
Rust backend gives us, and it is what `Option<NonNull<T>>` does today.

**B — beside the value.** The status travels out of band and the return value is untouched.

The instinct behind B is usually stated as "use the carry flag", and in that literal form it is not
reachable by a compiler back end: LLVM does not model CPU flags as values across calls — nearly every
instruction clobbers them — so it would take inline assembly at every call site, which costs more in
lost inlining than the flag saves.

**The realistic form of B exists and is in production.** LLVM's **`swifterror`** attribute passes an
error in a designated register (`r12` on x86-64, `x21` on ARM64), leaving the return value alone;
Swift has shipped on it for years. There is no tag, no widening, and the check is a test on a
register that is already there.

**Interoperability is an argument for A, and it is not a concession.** A boundary is exactly where
calling conventions get translated — the claim that an internal convention would be "viral" across
the Rust boundary is wrong, and a shim at the edge is the ordinary arrangement. But a shim has to
exist at every crossing, and a representation that *is* Rust's needs none. As long as Nikaia's value
proposition includes dropping into an existing Rust stack (Chapter 15, and the roadmap's interop
line), sharing the convention is a feature and not a compromise.

The counterweight is that the interior grows: [ADR-014](adr-014.md) moves `std` into Nikaia module by
module, so the share of calls that never cross the boundary rises over time. B gets more attractive
as that proceeds, which is the reason to record it properly now rather than close it.

**Open:** commit to A permanently, or keep B as a direction for a backend that controls its own
calling convention.

### 4.2 — What an automatic stack trace costs — **answered**

Closed by [ADR-036](adr-036.md): **28 300 instructions per error**, sixteen times the whole of a
program that raises twenty thousand. An error does not capture a trace unless `NIKAIA_TRACE` asks,
and the absence is stated rather than silent.

The measurement also corrected D7 of this document. It said `{error:full}` needed no new syntax
because a hole may carry a format spec — but a spec is passed through to the language below, which
has no `full`, so it would have needed a special case in the emitter. `f"{error.full()}"` needs
nothing, because a hole holds an expression and a call is one.

And it corrected an assumption this document did not make explicitly but would have:
`Backtrace::capture()` captures when `RUST_BACKTRACE` is **unset**. The obvious implementation is
the expensive one, by default, on every program — which deduction reaches "it costs something"
about, and never reaches.

## 5. Prior art

* **Zig — inferred sets, no payload.** `!T` means "the error set is inferred", and the compiler takes
  the union across the call graph; a `switch` over a known set is exhaustive; sets coerce into
  supersets. This is D1 and D4, shipped and running. Where it stops is D3: a Zig error is a `u16`
  with no data, so details come back through out-parameters or diagnostic structs, or are lost.
  Payload proposals have been discussed for years and have not landed. The most common repair in
  practice is that the *caller* already holds the context and writes it into the message itself —
  which both of our examples do — and it breaks exactly when the error travels far, which is what
  propagation makes common.
* **Java — checked exceptions, by hand.** The failure mode that gives the whole idea its bad
  reputation, and the reason is specific: no inference. See D1.
* **CLU (1975) — where it came from.** Liskov's argument that the exception belongs to the interface.
  Still right, and still not an argument for writing it out.
* **Swift — untyped, then typed.** `throws` was untyped for a decade; typed throws arrived in Swift
  6.0 (2024), motivated by constrained and embedded contexts where an existential error box means an
  allocation. A data point against D1 that should be remembered rather than filed away: if Nikaia
  ever takes `wasm32` or embedded seriously, this argument returns.
* **Rust — `io::Error`.** The packed representation D10 points at.
* **Common Lisp — conditions and restarts.** The one idea in this space nobody has copied: the
  handler runs *before* the stack unwinds, and a deep function can offer "retry", "use this value",
  "skip" while the caller chooses. Philosophically the closest relative this project has, given a
  diagnostics culture built on "say what went wrong and offer a way out". See §6 for why it is not
  taken.

## 6. Considered and rejected

* **Unwinding (zero-cost exceptions).** It is the only design that removes the per-call branch of §3
  entirely: the success path costs literally nothing, and a failure costs a table lookup and a stack
  walk. Rejected on three decisions already made: Lite builds `panic = abort`, `wasm32` supports
  unwinding only partially, and [ADR-006](adr-006.md) built the whole `Cleanup` design on `throws`
  tearing down *predictably*. Recorded here because it is the correct answer to "the happy path
  should pay nothing", and someone will propose it again.
* **Conditions and restarts.** Rejected against implicit async rather than on taste: a restart means
  resuming at the raise site after the handler decided, and Nikaia's raise site may sit behind a
  suspension point with a `Cleanup` obligation between it and the handler
  ([ADR-006](adr-006.md) D1). What "resume" means there has no cheap answer.
* **An out-of-band status in the carry flag.** The literal reading of the P0709 / syscall-ABI idea.
  Not rejected as an idea — §4.1 keeps its realistic form — but rejected as a *mechanism*, because
  LLVM does not carry flags across calls. Two related claims are worth correcting where they are
  often repeated: **P0709 is a 2018 proposal that has not been adopted** into any C++ standard, and
  the carry-flag technique **does not come from Zig**, which uses ordinary tagged values; it comes
  from syscall ABIs (Linux x86-32, the BSDs, MS-DOS INT 21h).
* **A per-task slot for the payload** ("the error is an integer, the details live at a fixed
  address"). Feasible in principle, since the runtime owns every task
  ([ADR-005](adr-005.md) D5). Rejected because [ADR-006](adr-006.md) D4 requires a cleanup error to
  be attached as a *secondary* error to a primary one that is already unwinding: two live errors, one
  slot.
* **A bounded inline payload with a fixed budget.** Arbitrary on its own — a path can be 4096 bytes.
  Subsumed by D10, which packs what fits and boxes what does not, without the author having to know
  where the line is.

## 7. Consequences

* **Part I, Chapter 7 is rewritten**, and gains what it never had: how an error type is declared, how
  one is raised, what `catch` binds and what its block means, and the rendering rule of D7. The name
  `error` becomes specified rather than credited.
* **The ledger's `throws` entry changes shape.** [ADR-020](adr-020.md) writes `throws = true`; under
  D1 it becomes the inferred set. That is a change to a shipped artifact — it affects
  `std.contracts`, what a published package distributes, and what `--locked` compares — and it
  belongs in the change that makes it, not as a side effect.
* **A new build artifact:** the origin-mark table of D6, shipped beside the binary. It is a
  projection of the source map [ADR-012](adr-012.md) already produces rather than a second source of
  truth, and per [ADR-021](adr-021.md) D13 anything it reads is a cache key dimension.
* **Appendix C gains `NK24xx` for the non-exhaustive `catch`** narrated from a ledger diff, alongside
  the existing contract-change entry. Per the catalogue's own rule, each new code arrives with its
  reproduction test.
* **Eight examples stop being wrong.** Untyped `throws` becomes the specified form rather than a
  convergent accident, and `{error}` gains a definition. `examples/fortunes.nika` loses its two
  postfix `?` under D8, and says in a comment why nothing replaces them.
* **Part II, 10.1's `HEX` rule is rewritten under D9.** It is the only place in the specification
  that shows an action failing, which is why the question had gone unasked; its `?` goes, and
  whether the rule wants a commit point before it becomes a thing the grammar author says.
* **A gap this ADR deliberately does not close.** [ADR-018](adr-018.md)'s generic 500 leaves the user
  with nothing to quote when they complain. D6's origin mark says *where in the code*; it does not
  say *which run*, and for a service with more than one process the second question is the one an
  operator asks. That identifier belongs to the **unit of work** — a request, a task, a job — and not
  to the error, because an error that mints its own identifier next to an incoming trace identifier
  produces two numbers to join instead of one. Nikaia is unusually placed to do it properly, since
  the runtime owns every task in both profiles ([ADR-005](adr-005.md) D5) and propagation across
  suspension points is the part that breaks elsewhere. It waits on the runtime binding — and folding
  it in would make everything decided above wait with it, which is reason enough to keep the two
  apart.

## 8. What Stage 0 does today

Recorded so that the current stage is never mistaken for the specification, the arrangement
[ADR-013](adr-013.md) D7 and [ADR-020](adr-020.md)'s `inference` header already use.

| | specified above | Stage 0 |
| :--- | :--- | :--- |
| `throws` | untyped, set inferred into the ledger | untyped, lowered to `Result<T, Box<dyn Error>>`; the ledger records a boolean |
| `throw` | exists | not in the parser |
| error type | enum with payload | none; every error is `Box<dyn Error>` |
| `catch` | binds `error`, matches over the inferred set | binds `error`, matches nothing |
| representation | pointer-sized, D10 | whatever `Box<dyn Error>` is |
| origin mark | D6 | the source map exists ([ADR-012](adr-012.md)); no table, no `explain` |

Two of these are more than absence. `Box<dyn Error>` was chosen as a placeholder and says so in the
emitter — *"because Nikaia's own error types are not lowered yet"* — and it gives up exhaustiveness
entirely, which is the opposite of D4. And the niche packing D10 wants requires the emitter to know
that a value *cannot be zero* — which the checker of [ADR-024](adr-024.md) cannot tell it, not
because it is missing but because of what it is: D1 there says it reports only what is written down,
and nowhere in a Nikaia source is that property written. Until something records it, the encoding is
whatever `rustc` picks. Neither fact constrains the decisions above.
