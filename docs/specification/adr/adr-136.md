# ADR-136: A Number Literal May Be Written `1_000_000`, `0xFF`, `0b1010` or `0o17`, and the Digits It Was Written In Are a Spelling

**Status:** Accepted · **Built:** no — see §5
**Date:** September 19, 2026
**Target Version:** Nikaia 0.0.18
**Related:** [ADR-060](adr-060.md) (a literal no use constrains takes the first type that holds it), [ADR-043](adr-043.md) D5 and [ADR-063](adr-063.md) (a constant that fits, `NK1116`), [ADR-048](adr-048.md) (the numeric surface), Part I 2.2 and 2.4

## 1. Context

`let n = 1_000_000` is two statements: the number `1` and a name `_000_000`
that nothing declares, which is `NK1117`. `0xFF` is the number `0` beside a
name `xFF`. The grammar is scannerless, so a separator and a radix prefix are
not syntax errors — they are a misparse, which is the class
[Part III C.1](../30-nikaia-tooling.md) is about and the class `NK1117` was
built to report rather than hand to `rustc`.

The forms are Rust's and the lowering is verbatim, so nothing here is
expensive. One question is the owner's.

**Does a hexadecimal literal carry a width?** `0xFF` is eight bits written
out, and a reader may take that as *a `u8`*. Or the radix is a spelling and
`0xFF` is `255`, which takes the first type that holds it exactly as `255`
does ([ADR-060](adr-060.md)).

## 2. Decisions

### D1 — The four forms are `1_000_000`, `0xFF`, `0b1010` and `0o17`.

An underscore may stand between digits and nowhere else: not first, not last,
not beside the radix prefix. `0x`, `0b` and `0o` are lower-case, and the
digits after `0x` may be either case. A float takes the separator too —
`1_000.5` — and no radix prefix, because a hexadecimal float is a shape
nobody writes.

### D2 — The radix is a spelling, and a literal is a value.

`0xFF` is `255`. It takes the first type that holds it, which is
[ADR-060](adr-060.md)'s rule unchanged, so `let mask = 0xFF` is an `i32` and
`let mask: u8 = 0xFF` is a `u8`. A literal that fits nothing is
`NK1116`, which is the refusal it already gets in decimal.

**Because the alternative makes the width invisible.** If `0xFF` were a `u8`,
then `0x0FF` would be a `u16` and `0xFF + 1` would overflow where `255 + 1`
does not — a type that depends on how many zeroes somebody typed. What a
reader wants from `0xFF` is the *bits*; what they want from the type is the
declaration, and this language has one place for that.

### D3 — The separator is not in the value, anywhere.

`1_000` is `1000` to the checker, to the ledger and to the constant fold. It
does not survive into a diagnostic's text either: a message about
`let n = 1_000` names `1000`, because that is the number, and naming the
spelling back at a reader who wrote it says nothing.

## 3. Consequences

* `NK1117`'s standing example — *the `_000` of `1_000` is a name* — stops
  being true, which is the point. Its help loses that clause.
* `0xFF` and `0b1010` mean what every neighbouring language means by them.
* **What it costs:** the lexical rule for the four forms, the fold reading
  them, and one clause off a help text.

## 4. What this does not decide

* **A suffix**, `1u8` or `1i64`. A literal takes its type from its use and
  the declaration is where a type is written; a suffix would be a second
  place.
* **A digit separator in a `char` escape or in a string**, which is not a
  number.
* **A hexadecimal float.**

## 5. What is built

Nothing. `1_000` is `1` beside the name `_000`, and `0xFF` is `0` beside
`xFF`. The order of work:

1. the lexical rule for the separator and the three prefixes, with the
   underscore's position refused;
2. the constant fold reading them, so `NK1116` and `NK1118` answer about the
   value;
3. `NK1117`'s help losing the `1_000` clause, and a test per form.

`docs/open-work.md` carries it.
