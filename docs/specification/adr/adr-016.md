# ADR-016: The UTF-8 Check Is Divided, Not Skipped

**Status:** Accepted
**Date:** September 9, 2026
**Target Version:** Nikaia 0.0.8 (bootstrap compiler)
**Closes:** [ADR-015](adr-015.md) §3, "UTF-8 validation is serial"
**Related:** [ADR-008](adr-008.md) (views), [ADR-011](adr-011.md) D4 (the profile chooses the
`Parallelism` and nothing else), [ADR-014](adr-014.md) D2 (`fs::map` is a memory mapping)

---

## 1. Context

Two numbers from [ADR-015](adr-015.md) did not sit comfortably next to each other: the Advanced
profile parses 8 million rows in 0.19 s, and `fs::map` validates the file as UTF-8 first, serially,
at a rate that would cost ~7.6 s on 1BRC's real 13 GB input. The reconciliation is only that these
are two file sizes — at 105 MB the same check is ~60 ms, and it is *inside* the 0.19 s, about a
third of it. Nothing was hidden, but nothing was divided either.

So the question is fair and has two halves. Why is the check there at all, and why is it that
slow?

---

## 2. Decisions

### D1 — The check stays, because it is what makes a view a `&str`.

`fs::map` hands the parser a `&str` over the mapped pages, and every slice the grammar cuts out of
it — every station name in 1BRC — is a `&str` into those same pages (ADR-008: `&` is a view
marker). Removing the check does not make the program slightly less careful; it makes
`str::from_utf8_unchecked` over bytes nobody controls, and every view after it undefined behaviour
in code the user wrote safely.

That is not an argument from principle. Built with the check removed, the flagship prints

```text
{Hamburg=12.0/12.0/12.0, \xffBad=3.0/3.0/3.0}
```

for a file with one stray byte in it — a station name that is a `&str` and is not UTF-8, formatted
without complaint, on the far side of a `Deref` that promises otherwise. The check is load-bearing.

What *may* eventually skip it is an assertion the user makes, in the shape the language already has
three times over (`@frame(…, unchecked)`, `fs::map(…; trusted: false)`, `dsl backend::x86`) — a
hatch the source opens, recorded, not a default the runtime picks. D4 says why that is not worth
building yet.

### D2 — The check is chunked at character boundaries, and reports the earliest failure.

`fs::map` cuts the mapping into one piece per core and validates the pieces in parallel. A cut
walks forward off a continuation byte (`10xxxxxx`), at most three times, so every piece begins
where a character begins: no sequence is split, and no piece can accept a truncation the piece
before it left behind. A piece that fails contributes `chunk_start + valid_up_to`, and the answer
is the **minimum** — so a rejected file names the same byte however many cores looked at it, which
is the same promise ADR-009 D2 makes about the fold ("chunk count does not change results").

Below 1 MiB the check runs in one piece, because waking the pool costs more than the check does.

Four tests in `crates/nikaia-std/src/fs.rs` hold it to `std::str::from_utf8` as the oracle: a
multi-byte input larger than the threshold; a corruption at every cut ±8 bytes and at a stride
coprime with the character width, each compared to the serial verdict *and offset*; one break per
chunk, to check that the first is the one reported; and the small-input path.

### D3 — The profile does not reach into `std`, and does not here either.

An obvious objection: Lite means `Parallelism::Off`, so should `fs::map` validate on one core under
Lite? No — and it could not, because ADR-011 D4 says nothing but the DSL driver reads the profile.
A profile is a runtime, not a dialect. What the profile governs is the *fold*: whether the input is
cut into pieces whose results are then merged, which is the thing ADR-009 D2 had to prove does not
depend on the chunk count.

The UTF-8 check has no result to merge. It returns the same verdict and the same byte offset on one
core and on sixty-four (D2), so how many cores ran it is not observable in the program — it is a
library function doing the fastest correct thing, which is what a library function is for. The
measurement below shows both profiles getting faster, and that is the honest consequence: Lite is
sequential *parsing*, not a vow of single-threadedness taken by every function a program calls.

---

## 3. The measurement

8 million rows (105 MB, ~1.5 % of bytes multi-byte), 4 cores, release, best of five. `no check` is
the same program with the validation deleted — not a candidate, the floor.

| | `--profile lite` | `--profile advanced` |
| :--- | ---: | ---: |
| serial check (ADR-015) | 0.57 s | 0.19 s |
| **chunked check** | **0.52 s** | **0.14 s** |
| no check at all | 0.51 s | 0.13 s |

The check alone, measured on its own over the same file: **63.7 ms serial (1.7 GB/s) → 16.5 ms on
four chunks (6.6 GB/s)**, a clean 3.9×. Projected onto 1BRC's 13 GB: ~7.6 s → ~2.0 s on four cores,
and it now divides by the core count like everything else.

**What is left to gain by removing it entirely is 10 ms** — 2 % of Lite, 7 % of Advanced — against
the output in D1. That is the answer to "why not switch it off": after dividing it, there is
almost nothing left to switch off.

Instructions per row are **unchanged at 659** (callgrind, 200 000 rows): chunking moves work
between cores, it does not remove any. Deleting the check gives 629, so the check is 30 Ir/row —
**4.5 % of the instructions and 11 % of the time.** That gap is the whole story of why it costs
what it costs: it is not arithmetic, it is a second pass over 105 MB of memory, and the parse then
walks the same bytes again.

### Why 1.7 GB/s and not 10

Measured against an ASCII-only twin of the same file — every `ü`, `ã`, `Ü` folded to its ASCII
letter, same length, same rows:

| input | `std::str::from_utf8` |
| :--- | ---: |
| ASCII only | **10.3 GB/s** |
| the real file (1.5 % of bytes multi-byte) | **1.7 GB/s** |

std's validator has an ASCII fast path over machine words, and a single non-ASCII byte drops it
back to the per-character path. 1BRC's station names are `São Paulo`, `Zürich`, `Ürümqi` — a
multi-byte character roughly every 68 bytes, which is often enough that the fast path never gets
going. So the rate this ADR started from was never "the cost of validating UTF-8"; it was the cost
of *this* validator on data that keeps interrupting it. Worth recording, because it is also the
reason a SIMD validator would help here far more than the 6× the table suggests, and D4 is about
not reaching for one yet.

## 4. What was rejected, and what is deferred

* **Switch the check off by default** — rejected in D1. 10 ms against the `\xff` above.
* **A `simdutf8`-style validator.** It would plausibly beat the chunked check on one core. It is a
  new dependency in `std` for 10 ms of a 140 ms program, and the chunked check already gets 3.9×
  with fifteen lines of `std` and no new trust. Reconsider when the check is again the largest
  thing left.
* **`fs::map(path; trusted: false)`'s sibling — an assertion that skips the check.** ADR-010's
  hatch is about *hashing*, not encoding, and the two should not be conflated under one keyword
  because they authorise different things: one says "I accept a slower hash", the other says "I
  accept undefined behaviour if I am wrong". A hatch for the second is worth exactly the 10 ms it
  saves, which is to say: not yet.
* **Fuse the check into the piece — the one that is actually right, and deferred.** Under Advanced
  the driver already cuts the input and hands each piece to a thread. Validating a piece on the
  thread that is about to parse it would be parallel *and* cache-hot: one traversal instead of two,
  which is where the 11 %-of-time-for-4.5 %-of-instructions gap lives. It needs the parser backend
  to take bytes and produce text — the byte-views question — and that is a language-level decision
  about what a view *is*, not a change to `fs.rs`. It is the same door the 1BRC top-league analysis
  arrived at from the other side.

---

## 5. What is still not true

* **The check is still a separate pass.** D4's last item is the fix and it is not built.
* **`sync` is still unchecked** (ADR-011 §4).
* **A 13 GB run has never been made.** Every figure here is measured at 105 MB and projected; the
  projection assumes the rate holds, and page-fault behaviour at 13 GB is not something a 105 MB
  file can tell you.
