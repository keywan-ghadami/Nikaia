# ADR-134: `/* … */` Is a Comment, It Nests, and It Is Not a Doc Comment

**Status:** Accepted · **Built:** no — see §5
**Date:** September 19, 2026
**Target Version:** Nikaia 0.0.10
**Related:** [ADR-120](adr-120.md) (a grammar's vocabulary page), Part I chapter 2 (a comment)

## 1. Context

A comment began with `//` and ran to the end of the line, and that was the
only form: `/* … */` did not parse. A line comment is enough for a sentence
beside a statement and not for commenting out a block of code while
debugging, for a paragraph above a function, or for a note inside an
argument list — the three places a reader reaches for `/* … */` and finds
it in C, Rust, JavaScript and every language between.

## 2. Decisions

### D1 — `/*` opens a comment that `*/` closes, across lines, anywhere whitespace may stand.

A block comment may stand wherever whitespace may: between any two tokens,
inside an argument list, inside a `grammar { … }` block, across as many
lines as it needs. It is whitespace to the parser, as a line comment is.
A `/*` inside a string literal is text, not a comment; a `//` inside a block
comment is comment, not a second comment.

### D2 — Block comments nest.

`/* a /* b */ c */` is one comment that ends at the second `*/`, as in Rust:
a block of code that already holds a block comment can be commented out
without hunting for the inner close. An unclosed block comment is a parse
error reported at the `/*` that opened it — the place the reader must fix,
not the end of the file where the parser gave up.

### D3 — `/** … */` and `/*! … */` are block comments and nothing more.

The language has no doc comment ([ADR-126](adr-126.md)'s page says the same
of `///`), and this record does not add one by the back door: a comment
that begins with two stars is a comment. What a doc comment would be — a
sentence the ledger carries and the prompt bundle reads — is a decision of
its own, in `docs/open-decisions.md`.

## 3. Consequences

* Code can be commented out, and a paragraph can stand where a paragraph
  belongs.
* Nothing changes for the emitter: a comment is not carried into the
  generated Rust today, and a block comment is not either.
* **What it costs:** one lexical rule beside `COMMENT`, with the nesting
  count and the error at the opening.

## 4. What this does not decide

* **Doc comments**, and what carries them.
* **Whether comments are carried into the generated Rust**, which the
  emitter does not do for any comment and which a reader of the generated
  code may one day want.

## 5. What is built

Nothing. `/*` is a parse error. The order of work:

1. the lexer's `BLOCK_COMMENT` beside `COMMENT`, nesting, and the error at
   the opening;
2. a test with a nested block comment inside an argument list, and one
   with `/*` inside a string.

`docs/open-work.md` carries it.
