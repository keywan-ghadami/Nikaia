# ADR-037: Two Switches — Which Machine, and How Much of Your Code Runs at Once

**Status:** Accepted · **Built:** D1–D5; D6's verdict but not its expansion,
because `Shared` has none — see §5
**Related:** [ADR-009](adr-009.md) D2 (a `par_fold` with no parallelism is a
sequential fold), [ADR-016](adr-016.md) D3 (why the compiler's own threads are
not the user's), [ADR-033](adr-033.md) (the overlapping D2 bounds),
[ADR-021](adr-021.md) D5 (both switches are cache-key dimensions),
[ADR-005](adr-005.md) §1 Group B and §5.3 (the check D6 changes the input of),
[`docs/rc-or-arc.md`](../../rc-or-arc.md) (the measurement D6 rests on)

## 1. Context

Two questions have to be answered before a program can be built, and they are
independent:

* **Which machine?** WebAssembly has no threads and traps rather than unwinds;
  a 64-core server has threads and a stack to unwind. That decides what `std`
  can offer and what a panic does.
* **May the user's code run concurrently at all?** A service that wants one
  event loop and a compute job that wants every core are the same language on
  the same machine, and the difference is a deployment choice.

Answering them with one switch forces the two to travel together, and they do
not: a single-threaded service on a 64-core machine is a real thing to want, and
so is a compute job that uses every core it can find.

## 2. Decisions

### D1 — `target` names the machine.

| target | passed to the backend | threads available |
| :--- | :--- | :--- |
| `x86_64-linux` *(default)* | `x86_64-unknown-linux-gnu` | yes |
| `wasm32-unknown` | `wasm32-unknown-unknown` | no |

The target decides what `std` can offer — whether `fs::map` exists at all — and
what a panic does: unwind where the machine unwinds, trap where it traps.

It decides **nothing about what a program means**. The same source compiles for
every target and prints the same bytes, which is asserted by a test over every
example rather than promised in prose.

A target the toolchain cannot build for yet fails with what is missing. It never
emits code for a different machine.

### D2 — `user_parallelism` says whether the **user's** code may run concurrently. It is yes or no.

| value | meaning |
| :--- | :--- |
| `no` *(default)* | nothing the user wrote ever runs concurrently |
| `yes` | it may, and the runtime decides how widely |

**Not a count, deliberately.** *How many* threads or cores serve a `yes` is a
scheduling question, and the answers belong to the machine and the moment: a
number in the source would be a promise the language cannot keep on hardware it
has not seen, and it would have to be re-tuned for every deployment it survives.
The program says what it permits; the runtime says how far it goes.

That also removes a question this would otherwise have owed an answer to. With a
number, a `par_iter` the user wrote and the statement overlapping the compiler
chooses would both draw on it, and something would have to say which yields.
With a permission there is nothing to divide.

What it governs: the expansion of `Shared` (D3), `par_iter`, `spawn`,
`task::scope`, freedom from data races, the structural `Send` check, and the
statement overlapping of [ADR-033](adr-033.md).

**The word `user` is load-bearing.** The compiler is not bound by this switch;
only the program is. `fs::map` may validate UTF-8 on four cores at
`user_parallelism = no`, and the runtime may hand a blocking call to a sidecar,
because neither runs code the user wrote and neither is observable — the check
returns the same verdict and the same byte offset on one core and on sixty-four
([ADR-016](adr-016.md) D3).

The line is therefore exact and testable:

> The compiler may use as many threads as the target has, for as long as **no
> code the user wrote runs concurrently**. The moment it does, it is user
> parallelism and D2 bounds it.

### D3 — `Shared` expands from `user_parallelism`, not from the target.

`no` gives `Rc`; `yes` gives `Arc`.

> **D6 narrows this.** The count is atomic at both settings now, so the sentence
> above is no longer the expansion. What survives is everything else in this
> record: `Shared` is written by hand, for the reason below, and the choice is a
> property of the program rather than of the machine.

This is a property of the *program*, not of the machine: a program that never
runs its own code concurrently cannot race with itself, whatever the machine
underneath could do. So a single-threaded service on a 64-core box pays no
atomic, which a switch keyed on the machine could not express.

`Shared` itself stays written by hand. It is not an ownership annotation of the
kind the language refuses — a lifetime annotation changes nothing observable,
and sharing changes **when a value is cleaned up** ([ADR-006](adr-006.md)).
Inferring it would move a destructor silently.

Whether the *choice between `Rc` and `Arc`* could be made per value rather than
per build is a real question and is not answered here: it is the same question
as "what crosses a thread boundary", which [ADR-033](adr-033.md) leaves open.

*(**Evidence, not an answer.** The question above was tried and measured rather
than argued, and it is still open. `Rc` and `Arc` differ in nothing a program can
observe except speed and `Send`-ness — the cleanup happens at the same point, which
is what this record's own reason would have forbidden. The atomic count costs
**+9 ns per clone-and-drop pair** on a 4-vCPU shared VM: ×3.40 where a loop is
only the count, ×1.01 where ~70 ns of other work sits between the clone and the
drop, ×1.00 where the handle is read and not cloned, and an order of magnitude
(×11 to ×17 over three runs) where four threads share one count — which is the
case a per-value choice cannot reach, because a count four threads touch has to
be atomic. Method, machine, spread, the prototype
(`contracts::sharing`, `nikaia --sharing`), the three hard cases and the four
places the analysis has to answer "atomic" because it cannot decide are in
[`docs/rc-or-arc.md`](../../rc-or-arc.md). Nothing here is decided by it.)*

*(**D6 answers it, and the evidence above is what answered it.** The
representation comes off the switch entirely: one count, atomic, at both
settings.)*

### D4 — Both switches are cache-key dimensions and neither reaches the ledger.

They change the emitted code, so a key without them would serve one build's
artifact to another ([ADR-021](adr-021.md) D5 and D7).

They stay **out** of `nikaia.contracts`. Borrow structure, tether state, trust
and the error set are identical whatever the machine and whatever runs at once,
so one ledger serves every combination ([ADR-005](adr-005.md) D8). Anything that
did depend on a switch would double the churn and put a build-time choice into a
file that ships with a package.

### D5 — Both live in the manifest, and the CLI overrides for one build.

`nikaia.toml` carries them, because they are properties of a project rather than
of an invocation, and a committed value is one a reviewer sees. `--target` and
`--user-parallelism` override for a single build, which is what a benchmark and
a bug hunt need. The same shape [ADR-033](adr-033.md) D8 gives `ordering`.

### D6 — `Shared` expands to an atomic count at **both** settings. This narrows D3.

D3 stands except for one row of its table: `no` no longer gives `Rc`. `Shared[T]`
is an atomic count whatever `user_parallelism` says, and the rest of D3 is
untouched — `Shared` is still written by hand, still for the reason D3 gives
(sharing changes *when* a value is cleaned up, [ADR-006](adr-006.md)), and the
verdict of the structural `Send` check still never consults the switch.

**The reason is one sentence.** A `Shared` whose expansion moved with the switch
had to be refused a thread crossing at *both* settings — because the verdict is
about a type and may never consult the switch ([ADR-005](adr-005.md) §1 Group B,
§5.3) — and that made Part II 12.2's `Shared[Locked[i32]]` counter, the program
the switch exists to serve, unwritable; one representation costs a measured
**+9 ns per clone-and-drop pair** and buys the crossing back.

That number is the whole price, and [`docs/rc-or-arc.md`](../../rc-or-arc.md) §3
is where it was measured: ×3.40 where a loop is only the count, ×1.01 where
~70 ns of other work sits between the clone and the drop, and **×1.00 where the
handle is read and never cloned** — the atomic is a per-clone cost and not a
per-use one. The expensive case is the contended one, an order of magnitude
(×11 to ×17 over three runs), and no choice can avoid it: a count several threads
touch has to be atomic.

**What it costs in the compiler is one row of a table.** `Shared` moves out of
`contracts::send`'s `MayNot` case into its container list, where it is answered
by what it holds — so `Shared[Locked[i32]]` is still not *permitted* to cross,
for the **lock's** sake rather than the count's, and that half is D3's second
question and is not answered here.

**One thing follows that is worth stating rather than discovering.** `Shared` was
the only type the records made non-crossable, so after this **no type answers
`may not`**: `NK2501` and `NK2502` are built and fire on no program this language
can write. The arm stays, because the reason it exists has not gone away — a type
whose expansion still moves with the switch has to take the worse of the two
settings — and `Locked` is the candidate. ADR-005 §5.3's "nothing in the language
is refused today" was a sentence about `Shared` being unbuilt; it is now a
sentence about there being nothing to refuse.

*(**Not built, and this decides what it will expand to rather than what it
does.** `Shared` has no expansion: there is no `Rc::new` and no `Arc::new`
anywhere in the emitter, and no constructor for one in the grammar. What this
changes **today** is what `contracts::send` concludes about the type, which is
real and is asserted by tests. The emission it prescribes is a promise about the
day `Shared` is built, and D3's own per-build sentence was the same kind of
promise.)*

## 3. Consequences

Freedom from data races is a property of the **program** rather than of a build
mode. At `user_parallelism = no` nothing the user wrote runs concurrently, so
nothing the user wrote can race — on any machine.

A library compiled at `no` and used in a program at `yes` is the case the
structural `Send` check exists for: it runs under both settings so that a
library cannot turn out to be un-compilable where it is used.

That check is built, and [ADR-005](adr-005.md) §5 is what it does — it is Group B's
third member and that record is where it was decided. Two things about it belong
here, because they are about this switch:

* **The verdict never consults the switch, and may not.** A value may cross a
  thread only if it may cross *any* thread, so a type whose expansion is safe at
  one setting and not at the other may not cross at either. A check that read
  `user_parallelism` would answer differently at the two settings, which is the
  whole failure the paragraph above describes.
* **The severity does.** At `no` nothing the user wrote runs concurrently, so the
  emitter writes no task and a crossing into one does not happen in that build:
  refusing it would refuse a program that compiles, so it is reported as a lint
  (Part III C.3, `NK2501`). A crossing into a **foreign** runtime's thread is not
  bounded by this switch — D2's "user" is load-bearing — so it is refused at both
  settings ([ADR-038](adr-038.md) D7, `NK2502`).

D3's open question is now the one thing standing in front of `Shared`: if the
choice between the two reference counts stays per build, a `Shared` may not cross
a thread at all, because the verdict is not allowed to depend on the build. That
is a decision to make with `Shared` and not before it.

*(**D6 made it, and it is the paragraph above that forced the shape of the
answer.** The choice does not stay per build, so a `Shared` crosses. The verdict
is still not allowed to depend on the build and does not — which is why the
answer had to be one representation rather than a switch the check could read.
What is left standing in front of Part II 12.2's counter is `Locked`, and that is
D3's second half.)*

## 4. What follows for the overlapping

At `no`, D2 decides the case [ADR-033](adr-033.md) left ambiguous, and decides
it wholesale. Overlapping puts each of two statements inside its own closure and
runs the pair on two threads, and both closures are code the user wrote — so at
`no` the analysis still answers *whether a pair may overlap*, and nothing acts
on the answer. `--overlaps` says which setting made its report hypothetical,
rather than reading as a promise the emitter is not keeping
([ADR-033](adr-033.md) §8.2b). At `yes` the same pair overlaps.

The switch is not "does this build have threads". It has a second one at `no`
too: Part I 8.4's Runtime Sidecar takes blocking I/O off the event loop, and is
safe precisely because no user code runs there. What `no` forbids is that
anything **you** wrote is in flight twice.

*(**[ADR-033](adr-033.md) D10 narrows this section**, and it narrows it using its
last sentence. "Overlapping puts each of two statements inside its own closure"
was true of the only vehicle there was; a pair of file reads handed to the
runtime ([ADR-038](adr-038.md) D3) has no closure in it, so at `no` something
does act on the analysis's answer now. D2 itself is untouched — nothing the user
wrote is in flight twice — and the word `user` is what makes the distinction,
which is the half of this record D10 leans on rather than displaces.)*

## 5. What is built

All five of D1–D5, and **the half of D6 there is anything to build**. `--target`
and `--user-parallelism` on the CLI, `[build]
target` and `[build] user-parallelism` in `nikaia.toml` with the flag
overriding for one build (D5), both in the build-cache key and neither in
`nikaia.contracts` (D4), and `Build::overlaps_user_code()` consulting both
switches before an overlap is emitted. *(Two methods since
[ADR-033](adr-033.md) D10: `overlaps_user_code` for the vehicle that carries the
program's own code, `overlaps_operations` for the one that carries only
operations — one question per name, because they have different answers at
`no`.)*

§3's structural `Send` check is built too, as [ADR-005](adr-005.md) §5 describes
it. `user_parallelism` reaches exactly one line of it — the severity — and
nothing in the analysis itself, which is asserted by a test that runs the same
program at both settings and compares the verdict rather than the exit code.

**D6 is built as far as it can be.** `Shared` is in `contracts::send`'s container
list, so the check answers it by what it holds; `crates/nikaia/tests/send.rs`
asserts that at both settings, and the walk's own tests keep the `may not` arm
and its sentences whole while no type produces one. The **expansion** is not
built and neither was D3's: there is no `Rc::new` or `Arc::new` in the emitter and
no way to construct a `Shared`, so a `Shared` reaches the compiler only as a
declared type. What D6 changes today is a verdict; what it prescribes is what the
emitter will write.

**Not built:** `wasm32-unknown` is a name the CLI accepts and then refuses with
what is missing behind it — `std` reaches for a memory mapping and a thread
pool, and neither exists there. A specification is a promise about later; a
compiler that emitted x86-64 for it would be making a different kind of claim.
