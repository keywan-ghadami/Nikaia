# ADR-033: Program Order Is a Guarantee Where It Is Observable

**Status:** Accepted, **provisional and unmeasured** — see §7
**Date:** September 11, 2026
**Target Version:** Nikaia 0.0.9
**Changes:** the language's execution model; the ledger gains `touches`; `nikaia.toml` gains
`ordering`
**Related:** [ADR-005](adr-005.md) (ownership is inferred and invisible — this is that, extended
past memory), [ADR-010](adr-010.md) D1 and [ADR-027](adr-027.md) D2 (an analysis that claims a
property fails closed), [ADR-020](adr-020.md) (the ledger says what a caller cannot see),
Part I 8.1 (async by default, no `await`), Part II 12.2 (`access` and the lock rules)

---

## 1. Context

Nikaia writes I/O in direct style: `let a = fs::read("x")` pauses, and the next line does not run
until `a` is there. Within one task the order is exactly the written order, always. That is the
whole of the current model, and it means this costs twice what it needs to:

```nika
let a = fs::read("x")     // 40 ms
let b = fs::read("y")     // 40 ms
return a.len() + b.len()  // 80 ms, for two things that never met
```

`b` does not depend on `a`. A CPU issuing two independent loads would overlap them without being
asked. The compiler can see the independence — it is the same dataflow analysis it already runs
for `sync`.

### 1.1 The objection that was raised first, and why it was the wrong caution

The obvious answer is: *let the compiler reorder where it is harmless, as a CPU does.* The
obvious objection is that a CPU may do this and a compiler may not, because a CPU

1. knows the **whole** dependency graph — registers and the addresses it tracks;
2. has operations that are **mutually effect-free** except through memory it tracks;
3. can **roll back** — speculate, then retire or discard.

and for I/O none of the three holds. The dependency graph lives in the world, not the program;
the effect *is* the point; and no packet ever came back.

That argument is correct about **today's** effect vocabulary, and that is its weakness. Nikaia
knows exactly one thing about `fs::write`: *it is I/O and it may pause*. Two writes to different
files are indistinguishable — not because I/O is unknowable, but because nobody wrote down what
each call touches.

> The ordering problem is not a safety property of parallelism. It is a **resolution problem of
> the effect system.**

A pure language may evaluate in any order because nothing can collide. The only reason for
sequence is effect, and two effects collide only when they touch the same thing.

## 2. Decisions

### D1 — Program order is a guarantee where it is observable, and only there.

The written order is what a reader relies on and what the compiler must honour **wherever the
difference can be seen**. Where it cannot be seen, the order is not a promise the language ever
meant to make; it is an artefact of writing one line under another.

### D2 — Every operation declares what it **touches**. Disjoint touches are unordered.

Not "does it do I/O" — *what does it reach*:

```text
fs::write(path, data)     touches  file(path)      write
fs::read(path)            touches  file(path)      read
println(x)                touches  stdout          write
counter.access fn { … }   touches  counter         write
net::post(url, body)      touches  endpoint(url)   write
```

And one rule:

> **Two operations whose touch sets are disjoint have no order between them.
> Everything else keeps the order it was written in.**

Two reads of the same resource are also unordered — reads do not collide, which is the same rule
a CPU applies to two loads.

### D3 — This is the borrow checker, extended past memory to the world.

Nikaia already answers *who may touch this, and may they change it* for memory, completely and
invisibly: no lifetime annotations, ever ([ADR-005](adr-005.md)). `&` and `&mut` are exactly
*read* and *write*; what is missing is only that a file, a socket, `stdout` and a `Locked` value
are not in the set of things that can be pointed at.

That is the argument for this decision over any other spelling of it. It is not a new mechanism
bolted to the side. It is the mechanism the language already rests on, applied to a larger set of
things — and the reason the answer can stay inferred and unwritten, which everything else in
Nikaia's design depends on.

### D4 — Unknown touches mean **touches everything**, so unknown means ordered.

A function whose touch set the compiler cannot determine — a foreign call, a library with a thin
ledger, anything reached through `unsafe` — is treated as touching every resource. It therefore
orders against everything and stays exactly where it was written.

This is [ADR-010](adr-010.md) D1's polarity for a third question, and it is what makes the
decision adoptable at all:

* a program compiled against a ledger that says nothing behaves **exactly as it does today**;
* parallelism appears only where somebody wrote down enough for it to be provable;
* nothing breaks in between, and no program is ever made wrong by a contract that is missing.

`std.contracts` growing is the mechanism by which programs get faster. That is the same shape as
[ADR-028](adr-028.md) and [ADR-031](adr-031.md), where writing a contract down is what let a
caller earn `sync`.

### D5 — Only unconditional operations, and only with a bounded degree.

**No speculation.** `if x { read(a) } else { read(b) }` starts one of them. Running both to save
latency would burn a request that was never wanted, which is the opposite of the thing this is
for. Only operations that are certainly going to run may be overlapped.

**Bounded concurrency.** A loop over ten thousand files must not open ten thousand descriptors.
The degree is bounded by the runtime, configurable, and part of this decision rather than a
detail after it. Unbounded parallelism is not generosity toward a machine.

### D6 — Errors and observable effects surface in program order.

If two overlapped operations both fail, the error that surfaces is the one whose operation comes
**first in the written program**, regardless of which failed first in time. Anything else would
make a diagnostic depend on a race.

`println("a")` followed by `println("b")` prints `a` then `b` — not by a special case, but
because both touch `stdout`. That is the test of whether a model like this is worth having: it
must deliver the obvious without an exception for it.

### D7 — `seq` says an order the compiler cannot see.

Two calls whose resources look disjoint and are not — different URLs, one service behind them:

```nika
seq {
    benachrichtige(kunde)
    protokolliere(vorgang)
}
```

More expensive to write, rare, and visible at the place it matters. That is the distribution this
whole decision is for: **the default is the fast and safe thing; the exception costs.**

*(The keyword is provisional. It needs to read as "in this order, whatever you think", and `seq`
is a placeholder for a word chosen later.)*

### D8 — `ordering` in `nikaia.toml`, and it can be turned off.

```toml
# How strictly the written order is taken (ADR-033).
#   "effects" (default) — two operations that touch disjoint things may overlap
#   "strict"            — the written order, always; the analysis is not applied
ordering = "effects"
```

`strict` is not a debugging aid to be removed later. It is the escape for a program whose author
does not want this, and for the case where a bug in the analysis has to be ruled out in the
field. A semantic default that cannot be switched off is a decision imposed rather than offered.

## 3. What one concept replaces

| question | today | under D2 |
| :--- | :--- | :--- |
| data dependency | dataflow analysis | the same rule |
| order of output | implicit in sequence | both touch `stdout` → ordered |
| no pausing while locked (12.2) | its own rule, enforced through `sync` | both touch the lock → ordered |
| race conditions | "impossible, Lite is single-threaded" | structurally impossible in **both** profiles |

The last row is the one worth reading twice. Nikaia's freedom from races rests today on the Lite
profile being single-threaded — which is why it is a property of a *profile* rather than of the
language, and why a program can mean different things under `--profile=advanced`. Under a touch
model it is a property of the language. The profile divergence does not disappear, but it loses
its worst instance.

## 4. What this costs

**A fourth invisible inference, on top of three.** This is the criticism this repository has had
levelled at it — that derived truth lives outside the source, the ledger becomes the real
program, and the reader is left with a surface. It applies here more strongly than anywhere
else, because this one changes *when things happen* and not only what is permitted.

The honest distinction, and the reason to accept it anyway: the three before it buy properties
you never see. Borrow inference buys safety you cannot observe; `sync` buys a permission you
never notice. **This one buys wall-clock time on the first program anyone writes.** An invisible
analysis whose effect can be measured is a different proposition from one that must be believed.

**Debugging changes.** A program whose operations overlap is harder to reason about at a
breakpoint. Mitigated by `ordering = "strict"` (D8), which makes any such question answerable by
re-running.

**The ledger grows again.** `touches` is the fourth column after `sync`, `throws` and `borrows`,
with the same failure mode as the others: a wrong entry is wrong for every consumer.
[ADR-028](adr-028.md) D5's rule holds — an entry exists because a program asked for it, and never
speculatively.

## 5. Considered and rejected

**Mark the parallelism** (`async let`, Swift's answer; `also` in an earlier draft of this ADR).
One word at the definition, join at first use. It is safe, small, and it was rejected on the
project's own terms: it makes the fast path the one you have to ask for, and leaves the default
slower than it needs to be. A language that is generous with machine time by default cannot ask
to be told each time.

**Mark the barriers, as a CPU does.** Reorder by default, write a fence where it matters. A CPU
can afford this because its reordering is *provably equivalent* and therefore unobservable.
Nothing about I/O reordering is provably equivalent, so this would require auditing every
sequence for an ordering that is not there — the exact cognitive load the language exists to
remove, relocated.

**Infer `touches` from bodies rather than writing it.** `std`'s bodies are Rust, and the compiler
does not read Rust. Same case as [ADR-020](adr-020.md) D5. Where a body *is* Nikaia, inference is
possible and is the natural extension later.

**A coarse "is this pure I/O" bit instead of named resources.** Cheaper, and it cannot order two
writes to the same file. Any model that gets `println`/`println` wrong is not worth having (D6).

## 6. Status: nothing of this is built

To be exact, because this file is a decision and not a report:

* the ledger has no `touches` column;
* `nikaia.toml` has no `ordering` key;
* `seq` does not parse;
* the emitter lowers statements in order and has no notion of a dependency graph;
* `task::scope` and `select`, which the runtime side would build on, are also not implemented.

**The first increment that would do something end to end**, and the one to argue about before any
code: two unconditional `fs::read` calls in a row, with disjoint literal paths, lowered to a
concurrent join. It requires `touches` for exactly two `std` functions, the dependency check
between two statements, and one emitter change. If that cannot be made to work cleanly, the rest
does not deserve to be attempted.

## 7. On accepting this without a measurement

This repository's own rule is that **a staging decision enters the compiler only together with a
measured crossover** (`docs/staging-candidates.md` §6), and it has twice overturned an intuition
that looked obvious. That rule is not being followed here, deliberately, and it is worth saying
why rather than quietly making an exception.

The rule is about **optimisations** — choices between two implementations of the same meaning,
where measurement is the only honest arbiter. This is a **semantic** decision: what a program
*means* when two lines stand next to each other. There is no benchmark that decides that, and the
programs that would exercise it do not exist yet, because the language cannot yet express them.

What is owed instead, and recorded here as a debt:

1. **The measurement happens** once there is an application large enough to carry it — how much
   unconditional, independent I/O real programs actually contain. If the answer is "almost none,
   real programs are chains", this decision was wrong and `ordering = "strict"` becomes the
   default rather than the escape.
2. **Until then the status line at the top of this file stays as it is.** Provisional and
   unmeasured is what it is, and a later reader should not have to reconstruct that.
