# Architecture Decision Record (ADR) 005: Borrow Model & Lifetime Strategy

**Date:** 2026-09-05
**Status:** Accepted
**Context:** Nikaia promises "Ownership without the pain" while compiling through the Rust toolchain (ADR-001/002: Rustc Driver Pattern, pinned to an exact nightly per release). Rust surfaces ownership through lifetime annotations and borrow-checker errors — exactly the cognitive load Nikaia exists to eliminate. This ADR defines, case by case, which lifetime/borrow situations are (A) already solved by rustc, (B) solved by the Nikaia driver automatically, (C) impossible to express in safe Rust and therefore require a Nikaia language construct, and (D) genuine user bugs that require nothing but a first-class error message. It records the resulting decisions D1–D8.

---

## 1. The Four-Group Taxonomy (Normative)

Every borrow/lifetime situation a Nikaia program can produce falls into exactly one group. The compiler strategy per group is normative for all future feature work: before a feature involving references is specified, it must be classified here.

### Group A — Solved silently by rustc (no Nikaia work required)

These are guaranteed by the pinned toolchain (`nightly-2026-01-01` at the time of writing) and must be preserved by the code generator:

| Case | Mechanism in rustc |
| :--- | :--- |
| Transient borrows in straight-line code (borrow ends at last use, not block end) | NLL (Non-Lexical Lifetimes, stable) |
| `list.push(list.len())` and similar read-during-mutating-call patterns | Two-phase borrows (stable) |
| **Borrows held across I/O suspension points** (`let s = &cfg.name; fs::read(p); use(s)`) | `async fn` lowering: rustc builds self-referential state machines via `Pin` internally. Nikaia's implicit async inherits this for free. |
| Single-input-reference signatures returning borrows (`fn f(&self) -> &str`) | Lifetime elision rules |
| Sane capture defaults for returned opaque types; async closures | Rust 2024 edition, `use<..>` precise capturing (stable) |

**Spec consequence:** These are written into the spec as *guarantees* (Part I, Chapter 6.5), not left implicit.

### Group B — Solved by the smart driver (automatic, no user-visible syntax)

1. **Cross-function borrow-contract inference** with the **Borrow Contract Ledger** — see D3. Signatures like `fn longest(a: &str, b: &str) -> &str` need lifetime annotations in Rust; Nikaia infers them whole-program and persists the result in a generated file.
2. **The Polonius case** (conditional return of a borrow, the `get_or_insert` pattern): rejected by the stable borrow checker, accepted by the next-generation checker available on nightly as `-Zpolonius=next`. Depending on a `-Z` flag is normally reckless; **for Nikaia it is legitimate because ADR-001 §1.3 already pins every release to one exact nightly build.** The flag is enabled, tested against exactly that snapshot, and shipped as part of the toolchain. Fallback if the alpha regresses: frontend desugaring of the known patterns onto entry-style APIs.
3. **Send/Sync divergence between profiles**: `Send`-ness of task state is checked structurally **in the frontend, under both profiles** (Advanced rules run as a hard error in Advanced and as a default-on lint in Lite), so a library developed under Lite cannot silently be un-compilable under Advanced. Errors use Nikaia vocabulary, never trait names.
4. **Codegen details**: automatic `Box::pin` for recursive functions under implicit async; `use<..>` capture control; 2024-edition temporary-scope rules.

### Group C — Inexpressible in safe Rust: Nikaia language constructs required

1. **Stored slices / self-referential data** → **Tethered Slices** (D4).
2. **Scoped tasks borrowing from the parent** → profile-split soundness rule (D5).
3. **Lock guards across suspension points** → `sync`-lambda rule for `access` (D6).

### Group D — Genuine user bugs: no technology helps, only diagnostics and APIs

**Aliasing violations** — mutating a collection while iterating it, two exclusive borrows of the same structure — are not lifetime problems. The code has a real bug (iterator invalidation is undefined behavior in C++ and a runtime surprise in Python). No borrow-checker successor changes this. Nikaia's answer is two-fold:

1. **Standard-library design as the primary fix**: for every known aliasing anti-pattern there is a named, safe API (`retain`, `drain`, `entry`, `swap(i, j)`, index-based loops). This is a stdlib design principle (Part III, Chapter 17).
2. **The diagnostics contract** (D7): the error explains the bug in plain language and the fix-it points at the exact API.

## 2. Decisions

### D1: Nikaia source code contains no lifetime annotations. Ever.

There is no lifetime syntax in the grammar and none will be added. All lifetime knowledge lives in the compiler and in the generated Borrow Contract Ledger (D3). This is a headline language guarantee.

### D2: The four-group taxonomy above is the normative strategy.

Every reference-related feature must be classified into A/B/C/D during specification.

### D3: Whole-program borrow-contract inference, persisted in the Borrow Contract Ledger

**Mechanism.** Nikaia never compiles against unknown Nikaia binary signatures — all `.nika` sources are present, and Rust dependencies bring explicit signatures. The driver therefore:

1. creates one region variable per reference position in every signature,
2. collects subtyping constraints from function bodies,
3. solves them over the call graph (SCC-wise, fixpoint for recursion),
4. emits minimal explicit lifetimes into the generated `TokenStream`.

This is the same region inference rustc performs inside a function, lifted across function boundaries (precedent: MLKit region inference).

**The Ledger (`nikaia.contracts`).** Rust deliberately refuses to infer signatures from bodies because it creates action at a distance: editing a callee's body changes its signature and surfaces an error at a caller three modules away. Nikaia solves this not with in-source annotations (rejected, see §3) but with a **generated, committed file** that records the inferred contract of every function whose signature involves borrows, and every tethered struct field (D4). On each build the compiler:

* infers fresh contracts and **diffs them against the ledger**;
* **unchanged** → fast path: callers of unchanged contracts are not re-checked (the ledger doubles as an incremental-compilation cache key, like `nikaia.lock` does for compile-time I/O);
* **changed, all callers still valid** → the ledger is updated automatically and the build proceeds (auto-resolve); the change is noted in build output;
* **changed and a caller breaks** → the error message is built *from the diff*: it names the function whose contract changed, the body edit that caused it, and the caller that can no longer hold the result — with concrete fix-its. This is the ledger's core purpose: turning "spooky action at a distance" into a narrated cause-and-effect chain.

**Trait methods.** Dynamic dispatch requires one contract per trait method, not per implementation. The ledger stores the trait-method contract as the join (most caller-restrictive union) of all implementations; adding an implementation that broadens the contract produces a ledger diff and, if callers break, the same narrated error.

**Distribution.** The ledger ships with published packages, so downstream builds get stable contracts and the same diff-based errors across package upgrades.

**Properties.** Human-readable, deterministically ordered, committed to version control (recommended, like a lockfile), records the toolchain hash to detect inference drift across compiler versions.

### D4: Stored borrows are Tethered Slices (resolves the struct-lifetime question entirely)

Safe Rust cannot express self-referential data (a struct holding a buffer *and* a slice into it), and no stabilized or foreseeable feature changes that. Nikaia's rule:

> **Transient = borrow, stored = tether.** A slice used within a call tree remains a true Rust `&str`/`&[u8]` (zero cost, Group A). A slice that *escapes* — reaches a struct field, a `@detached` lambda, or a `return` beyond its buffer's frame — is lowered by the driver to **(buffer handle, offset range)**: a `Shared` reference-count on the buffer plus a `Range<u32>`, not a Rust reference.

This is the `bytes::Bytes` model, and the precedent matters: **the async-Rust ecosystem itself abandoned reference slices for stored data and standardized on `Bytes`**, because borrows and detached tasks do not mix. Nikaia promotes that proven semantics from library convention to language semantics.

Properties:

* **Deterministic** — reference counting, no GC (rejected alternative "implicit clone on conflict" — see §3).
* **Cheap** — one `Rc`/`Arc` per *buffer*, not per token; `Shared` already maps to `Rc` in Lite and `Arc` in Advanced, so tethering rides the existing Unified Types mechanism.
* **Strictly better UX than a borrow error**: instead of "the borrow checker forbids using this token after the buffer is gone", the guarantee becomes "the buffer *cannot* die while a token lives".
* **The boundary is drawn by the compiler**, not the user. An error occurs only when the buffer is not `Shared`-capable.

**Consequence for B3 (struct lifetime parameters):** With tethering, the driver never needs to emit user-visible `struct Foo<'a>` and users never see lifetime-parameter errors. The question "should Nikaia expose struct lifetime parameters?" is thereby closed: **no** — not as a v0.x restriction, but permanently, because the tether covers the use case.

**Note (future optimization, not scheduled):** A third option exists — unsafe self-referential codegen à la rustc's own generator lowering (the driver controls all access patterns and could prove the invariants itself, eliminating the refcount). This is recorded as a possible optimization avenue if tethering is ever measured to be too costly in hot paths. It is explicitly *not* part of the current design.

### D5: Scoped-task borrowing is sound per profile, and the spec must say so

`task::scope` with implicit borrowing in an *async* context is notoriously unsound in Rust (the "Leakpocalypse" family: a cancelled scope cannot synchronously stop children running on other worker threads while their borrows point into the dying stack frame; this is why tokio has no safe async scope and `async_scoped` demands unsafe or blocking). The profile analysis saves the feature in exactly the places it is needed:

* **Lite: sound.** Single-threaded means no child runs *simultaneously* with cancellation. The runtime is Nikaia's own: it owns all child futures, and scope teardown synchronously collects children before the parent frame dies. Preconditions recorded as spec requirements: Nikaia exposes no `mem::forget` equivalent, and task futures are exclusively runtime-owned, never user-owned values.
* **Advanced: sound only for `sync` children.** A blocking compute scope (the rayon model — `join` waits before the frame dies) is sound and covers the actual use case, data parallelism — consistent with §12.6 where `par_iter` already demands `sync` closures. **Async children with borrows in the Advanced profile are removed from the spec**; async children use the existing `@detached` semantics (implicit move, results via the handle).

Because this is a restriction users will hit without any Rust background, the spec text and the diagnostics (D7) must explain it without jargon — in terms of "a background task may outlive the things it looks at", with the fix stated in the error itself.

### D6: No suspension point while a lock is held — enforced at compile time via `sync`

§12.2's rule "no I/O while holding a lock" is Rust's "a `MutexGuard` must not live across `.await`" in Nikaia words. Instead of a runtime reentrancy panic as the primary mechanism, the rule is made static using a keyword the language already has:

> `access` and `access_all` require a **`sync` lambda in both profiles.**

Consequences: "no suspension while borrowing locked data" is a compile-time guarantee; the Lite/Advanced semantic divergence of `Locked[T]` shrinks; a runtime error class disappears from the happy path. The runtime reentrancy check (Lite) and lock poisoning (Advanced) remain as defense-in-depth backstops — e.g. against reentrant `access` on the same lock through a chain of `sync` calls, which `sync` alone does not rule out (manual lock nesting is separately rejected per §12.3, with `access_all` as the sanctioned form).

### D7: The Diagnostics Contract — a raw rustc error is a compiler bug

The Rustc Driver Pattern (ADR-001) allows more than span mapping: Nikaia registers its **own diagnostic emitter** and intercepts every rustc diagnostic before it reaches the user. Normative requirements:

1. For every borrow/ownership/lifetime rustc error class (E0382, E0499, E0502, E0505, E0506, E0597, E0716, …) there is a Nikaia translation with Nikaia vocabulary, Nikaia spans, and a concrete fix-it. Nikaia diagnostics carry `NK`-prefixed codes (catalogued in Part III, Appendix C).
2. Ledger-diff errors (D3) additionally narrate the *cause chain*: which body edit changed which contract, and which caller broke.
3. **An untranslated rustc error reaching the user is classified as an internal compiler error** ("this is a Nikaia bug, please report"), never as acceptable output. This inverts the burden of proof and makes diagnostic quality testable: the error catalogue *is* a test suite.
4. Diagnostics for the Group C/D restrictions (D4–D6, aliasing) must be understandable **without any Rust or systems-programming background** and must state what the user should do next (clone, `Shared`, `retain`, mark `sync`, move data in) — worked examples are part of the spec (Part I §6.8, Part II §12.7, Part III Appendix C).

### D8: Contract inference is byte-deterministic — the ledger is a pure function of (source tree, toolchain)

**Requirement.** Given the same source tree and the same pinned toolchain, `nikaia build` produces a byte-identical `nikaia.contracts` on every machine, every run, with any thread count. This is the "canonical output" level (the `Cargo.lock` standard) — deliberately *not* mere semantic equivalence, and deliberately *not* full bit-reproducibility of all build artifacts (a worthwhile long-term goal, but the ledger requirement must not be coupled to it).

**Why this is cheap: the mathematics cooperates.** The inference solves a monotone subset-constraint system over a lattice; by Kleene/Tarski such a system has a **unique least fixpoint**. There is no "solver luck" — the inferred *result* is identical regardless of solving order. Nondeterminism can therefore only enter through implementation details, all of which are known and documented failure modes from rustc's and the reproducible-builds project's history. Canonical serialization costs a sort over the ledger entries — milliseconds even at 100k functions. There is no performance trade-off that would justify a weaker level.

**Why byte-level, not semantic (facts):**
1. Byte equality makes verification a one-liner (`git diff --exit-code nikaia.contracts`) with no custom comparer that could itself have bugs. This is why the ecosystem converged on canonical bytes for committed generated files (`Cargo.lock`, `package-lock.json`, `go.sum`, `gofmt`).
2. Semantic-only determinism still produces VCS churn and merge conflicts unless the writer canonicalizes anyway — at which point the canonicalizer exists but its benefit is discarded.
3. rustc tried both worlds: its historical nondeterminism bugs (HashMap iteration order leaking into symbol ordering and output) ended in a binding dev-guide rule mandating deterministic ordering, not in semantic comparers. That lesson is already paid for.
4. Byte determinism is falsifiable in CI (see below); semantic determinism is not testable at comparable cost.

**Sub-decisions:**

* **(a) Parallel solving: allowed.** The requirement is "output is a pure function of the input", not "single-threaded". The unique least fixpoint plus canonicalization at write time makes thread count irrelevant; the CI test varies thread count to enforce this.
* **(b) Stability across toolchain versions: explicitly NOT required.** Requiring it would freeze inference improvements forever. Instead the ledger records the toolchain hash (D3); when a ledger diff is caused solely by a toolchain bump, the compiler says so explicitly ("contract changes caused by the toolchain update, not by your code") — the narration machinery absorbs the case instead of prohibiting it.
* **(c) Profile neutrality: required.** There is exactly **one** ledger, valid for Lite and Advanced. This works because borrow structure and tethering are identical in both profiles (`Shared` merely switches `Rc`/`Arc`; the contract is unchanged). Profile-dependent checks (`Send`-ness, D7/B3) deliberately stay *out* of the ledger. Without this rule the churn doubles and the profile schism returns through the back door.
* **(d) A violation is a compiler bug**, handled with the same severity as the Iron Rule of the Diagnostics Contract (Part III, Appendix C): a failing determinism test is a red build, never a flake to re-run.

**Ban list for implementers** (every item is a documented real-world nondeterminism source):

| Banned in any ledger-emitting code path | Reason / precedent |
| :--- | :--- |
| Iterating an unordered hash map to produce output | Rust's `HashMap` uses per-process randomized SipHash seeds; historically nondeterminism source #1 in rustc, banned by its dev-guide (use ordered structures or sort at emit). |
| Consuming directory listings in filesystem order | `readdir` order differs across filesystems (ext4/APFS/NTFS); a top cause listed by reproducible-builds.org. Sort all source-tree walks. |
| Internal counter IDs as ledger keys | Not stable across runs; rustc invented `DefPathHash` for exactly this. Keys are source-derived: module path + name + signature hash. |
| Absolute paths, timestamps, hostnames, environment values in the file | Standard reproducibility leaks. Paths are project-relative; no timestamps. |
| Locale-dependent sorting | Sort by byte order (code points), never by collation. |
| Thread-arrival order influencing names or numbering | Parallelism is allowed (a); derived names must come from source identity, never from scheduling. |

**CI enforcement (definition of done for the inference engine):**
1. **Double-build test:** run inference twice on the same tree — once with default threads, once with a different thread count (e.g. `-j1` vs `-jN`) — and compare the two ledgers byte-for-byte.
2. **Cross-OS test:** run the same comparison across at least two operating systems (Linux and macOS at minimum, covering the `readdir`/filesystem-order class).
3. Cost: one extra inference pass per CI run, no codegen. A mismatch fails the build per (d).

**Recorded engineering judgment:** the design risk is not the mathematics but multi-year discipline — any new emit path can smuggle in a hash-map iteration. The CI tests exist precisely to turn such a slip into an immediately red build instead of a creeping annoyance. With them, D8 is sustainable indefinitely; without them, no determinism level can be guaranteed.

## 3. Rejected Alternatives

* **Implicit clone on conflict** (compiler silently clones when borrows collide): rejected. Non-deterministic performance characteristics; incompatible with "No GC, deterministic resource management". Nikaia never inserts a clone the user didn't write — the diagnostics *suggest* clones, the user decides.
* **In-source borrow annotations** (e.g. `pub fn longest(a: &str, b: &str) -> &str @from(a, b)`): rejected in favor of the ledger (D3). Rationale: keeps D1 absolute (zero lifetime-adjacent syntax in code); the contract is derived truth, so it belongs in a generated artifact; and a persisted, diffable contract gives *better* break-explanations than a hand-written annotation, which can merely mismatch.
* **User-visible struct lifetime parameters**: rejected permanently — subsumed by Tethered Slices (D4). Lifetime parameters are viral (every collection, every `Shared[...]`, every trait impl inherits the constraints), and their error messages are precisely what Nikaia exists to prevent.
* **The full Rust lifetime model with hidden inference only** (no tether, no ledger, reject whatever inference cannot prove): rejected — it preserves every hard error from Rust while removing the syntax needed to fix them.

## 4. Consequences & Open Questions

* The frontend gains a region-inference engine and a diagnostic-translation layer; both are substantial but are the direct price of the "Ownership without the pain" promise, and both are enabled (not blocked) by the driver architecture.
* Determinism of contract inference is settled by D8 (byte-deterministic canonical ledger; ban list; CI double-build and cross-OS tests) — no longer an open question.
* Ledger merge conflicts in version control resolve like lockfile conflicts: regenerate via `nikaia build`.
* `-Zpolonius=next` is an alpha; each toolchain bump re-validates it against the error-catalogue test suite, with entry-API desugaring as the documented fallback.
* Tethering cost (one refcount per buffer) is expected to be negligible; if hot-path measurements ever contradict this, the unsafe self-referential codegen noted in D4 is the escape hatch to evaluate first.
* Related but out of scope here: synchronous `Drop` vs. cleanup that needs I/O under implicit async — decided in [ADR-006](adr-006.md) (the `Cleanup` trait, parked cleanup, drain deadline).
