# ADR-019: The Build Cache Is Ours, and the Lockfile Is Its Key

**Status:** Accepted
**Date:** September 9, 2026
**Target Version:** Nikaia 0.0.8 (specification), 0.0.9 (orchestrator implementation)
**Related:** [ADR-002](adr-002.md) §1.2 (`nikaia.lock` as a deterministic cache key),
[ADR-003](adr-003.md) §1.2 (the orchestrator owns caching and profile management),
[ADR-005](adr-005.md) D6 (the contract ledger as an incremental-compilation cache key),
Tooling Spec [§13.1, §13.5](../30-nikaia-tooling.md)

---

## 1. Context

The specification promises fast builds in three separate places and has never said how they are
made fast. `nikaia.lock` is described as a "deterministic cache key" for compile-time I/O
(ADR-002 §1.2); the `nikaia.contracts` ledger is described as doubling as an incremental cache key
(ADR-005 D6, Tooling Spec §13.5); the orchestrator is described as the component that performs
"hash-based incremental compilation checks" (ADR-003 §1.2). Three descriptions of caching, no
single statement of what is hashed, what invalidates what, or where anything is stored.

None of it exists in code. `bridge-orchestrator/src/lib.rs` is fifty lines that print the Bridge IR
and end at `// TODO: Call rustc-executor`; nothing calls it. There is no hash, no digest, no
lockfile reader, and no artifact store anywhere in `crates/`. This ADR is written *before* that
component is built, because a cache key is the one thing that cannot be extended later without
invalidating everything that came before it — and because the two ways to get a key wrong are both
silent.

The question that prompted this was whether to adopt an external compilation cache (`sccache`).
The answer is no, and the reason is not that it works badly. It is that it caches the wrong layer:
it memoizes `rustc` invocations, while the expensive and repeated work in a Nikaia build is macro
evaluation, grammar expansion and lowering — all of which happen *before* `rustc` is reached, and
none of which `rustc` ever sees. A cache that we own, keyed on inputs we already record, covers
that work; a cache bolted underneath it cannot.

---

## 2. Decisions

### D1 — There is no external compilation cache. Caching is the orchestrator's job.

No `sccache`, no `RUSTC_WRAPPER` cache layer, no second caching system to configure and keep in
step. The orchestrator (ADR-003 §1.2) is already the documented owner of build caching; this ADR
makes that ownership exclusive rather than shared.

Cargo's own fingerprinting continues to cover the *Rust* workspace, and is not something we
replace or wrap. It is measured in §4 and it works.

### D2 — One committed file records everything that determines a build.

`nikaia.lock` holds, per entry:

* SHA256 of every external file read at compile time (ADR-002 §1.2's asset hashing),
* SHA256 of every `.nika` source that took part,
* resolved dependency versions,
* the **exact toolchain version actually used**, and
* the **Nikaia compiler's own version**.

Anything that determines the output belongs in this file. Splitting the record — assets here,
toolchain there — produces a lockfile that cannot answer the only question a lockfile exists to
answer: *does this build the same thing for you as it does for me?* If an external asset or the
toolchain is left out, the answer is no and the file does not know it.

### D3 — The compiler's own version is part of the key.

This is stated separately because it is missing from every prior description of `nikaia.lock`, and
it is the most dangerous omission available. `crates/nikaia/src/emit/mod.rs` is a pure function
from source to Rust — which is what makes caching sound at all (D7) — but it is a function *we
edit*. The same input, the same toolchain and a changed emitter produce different output. Without
the compiler version in the key, the cache serves artifacts from the previous emitter and the
build is silently stale.

The failure lands only on compiler developers and never on users, which is precisely why it would
survive a long time undetected.

### D4 — Declaration and record are different files.

`nikaia.toml` *declares* what the project requires; `nikaia.lock` *records* what was resolved and
used. This is the `Cargo.toml`/`Cargo.lock` relationship, and adopting it resolves the drift that
would otherwise appear between three places that all name a toolchain: `rust-toolchain.toml`
(ADR-001's single source of truth for this repository), the `toolchain =` field in
`nikaia.contracts` (Tooling Spec §13.5), and the lock. A constraint and a measurement can coexist;
two constraints cannot.

### D5 — Build-time choices enter the key but are never written to the lockfile.

The profile (`lite`/`advanced`), opt-level and backend are decisions made at invocation time, not
facts about the inputs. They are hashed into the cache key and never persisted, because a lockfile
that records them is rewritten every time a developer switches profile — producing a committed
diff that carries no information and conflicts between developers who build differently.

The profile **must** be in the key. It is not optional: `Profile::Lite` and `Profile::Advanced`
lower the same source to different Rust (ADR-009's `par_fold` degradation). A key without the
profile hands back one profile's artifact for the other, and the test that exists to detect exactly
that class of divergence — `the_profiles_agree_on_every_example` in
`crates/nikaia/tests/examples.rs` — would compare an artifact against itself and pass trivially.
A cache is allowed to make a test faster. It is never allowed to make a test vacuous.

### D6 — One key per translation unit, never one key over the file.

The key for a unit is the hash of *that unit's* inputs: its own source, the assets it reads, the
toolchain and compiler identity, and the build-time choices from D5. It is not the hash of
`nikaia.lock` as a whole.

Hashing the whole file is the easy implementation and it destroys the property the cache exists
for: one changed asset would invalidate every unit in the project. Smart invalidation is not an
optimization layered on afterwards — it is a consequence of choosing the key's granularity
correctly the first time.

### D7 — Every dimension of the key is enumerated explicitly.

A key may be wrong in two directions, and both are silent:

* **Too much in the key** — absolute paths, file modification times, ambient environment variables,
  a build timestamp. The key then varies when nothing meaningful changed, and the cache never
  hits. This looks like a cache that is merely useless.
* **Too little in the key** — D3's compiler version being the standing example. The key then fails
  to vary when something meaningful did change, and the cache serves the wrong answer. This looks
  like a miscompilation.

The rule that follows: the key is assembled from an explicit, reviewable list of dimensions.
Nothing is captured incidentally, and nothing that determines the output is left to be remembered.

For git dependencies, hash *content*, not the revision. `docs/handoff.md` records what the
alternative costs: Cargo fingerprints the `winnow-grammar` git dependency on its commit, so local
edits to the checkout are silently inert and `cargo clean -p` does not help. That is a bug to
learn from, not to reproduce.

### D8 — Artifacts live in a content-addressed store, outside the repository.

`target/nikaia/cache/`, addressed by the D6 key, git-ignored. The lockfile records inputs; the
store holds outputs. Because the key is derivable from the lockfile plus the D5 choices, the store
needs **no index of its own** — the absence of a second bookkeeping structure is the point, since a
cache index that can disagree with the lockfile is a cache that can be wrong.

The precondition is determinism, and it already holds: the lowering is deterministic, which is why
`--explain` rebuilds the source map from source rather than storing it
(`crates/nikaia/src/main.rs`, ADR-012).

### D9 — Cranelift is a supported option for development builds, not the default.

The claim in ADR-002 §1.1 that `nikaia build` uses `-Z codegen-backend=cranelift` for "sub-second
development iterations" was inherited from a superseded ADR and never measured. It has now been
measured (§4): Cranelift is fully compatible with this workspace — including the `rustc_private`
dylib linkage that was the plausible blocker — and buys approximately one second on an incremental
rebuild and nothing at all on a full build. At `opt-level = 0` the build's cost is in the
dependency graph and the proc-macro crates, not in code generation.

So: documented, tested, switchable — and off by default, because making it the default would
oblige every contributor and CI job to install a toolchain component that this ADR's own numbers
cannot justify. The switch is `[profile.dev] codegen-backend` with Cargo's `-Zcodegen-backend`,
not `RUSTFLAGS`: it is scoped to a profile instead of to every invocation in the shell.

This decision is to be revisited when a single crate in the workspace becomes large enough for
codegen to dominate its rebuild. The numbers in §4 exist so that the revisit is a measurement and
not an opinion.

**Related defect, recorded here because this ADR is what noticed it:** `--backend cranelift` and
`--backend llvm` are accepted by the CLI today and silently do what `--backend bridge` does — the
backend list in `crates/nikaia/src/main.rs` is a comment, and nothing matches those strings. Either
implement them or reject them with an error. Accepting a flag and quietly doing something else is
the worst of the three options, and it is the one currently shipped.

## 3. Consequences

**What this buys.** A single answer to "what determines this build", in a single reviewable file.
Invalidation that is proportional to the change rather than total. A cache that covers macro
evaluation and lowering — the work that is actually repeated — instead of only the `rustc` call at
the end.

**What it costs.** Disk, in two ways. Dimensions coexist rather than share (§4): `cargo clippy`
maintains its own artifact set alongside `cargo build`'s, and each combination of build-time
choices occupies its own entries in our store. This is the correct trade and it should be stated
plainly rather than discovered: the cache is larger so that it is never wrong and never thrashes.
The store needs an eviction policy eventually; this ADR does not specify one.

**What it does not decide.** The lockfile's concrete syntax; the hash function's framing details;
how the store is garbage-collected; whether `nikaia.contracts` (ADR-005) merges into `nikaia.lock`
or stays a separate ledger. Those follow the implementation in `bridge-orchestrator` and belong in
the ADR that reports it.

## 4. Measurements

Taken on `nightly-2026-01-01`, this workspace, `dev` profile.

**Cargo already keys its cache per dimension, and dimensions never evict one another.**
Same target directory throughout:

| Step | Crates recompiled |
| :--- | :--- |
| `cargo build` (cold) | 61 |
| then `cargo clippy` (cold) | 56 |
| then `cargo build` | 0 |
| then `cargo clippy` | 0 |
| touch a source file, then `build` → `clippy` → `build` | 2 → 2 → 0 |
| `RUSTFLAGS` set → unset → set again | 61 → 0 → 0 |

Clippy's 56 crates on its first run are not waste and not a collision: it maintains a parallel
artifact set rather than reusing the build's. Dimensions **coexist**; they do not **share**. Steady
state costs nothing, which is the property D7 is protecting.

**Cranelift compatibility** (component `rustc-codegen-cranelift-preview`, not currently listed in
`rust-toolchain.toml`):

| Test | Result |
| :--- | :--- |
| Trivial crate | passes |
| `check_rustc.rs` — `rustc_private` with `rustc_driver`/`_interface`/`_session`/`_span`, built *and run* | passes |
| Full workspace, including proc-macro crates | builds |
| `cargo test --workspace` | 51/51 pass |
| Binary output vs. LLVM build | identical |

| | LLVM | Cranelift |
| :--- | :--- | :--- |
| Full cold build | 26s | 25s |
| Incremental after touching `emit/mod.rs` | 2s | 1s |

Reproduce with `rustup component add rustc-codegen-cranelift-preview` and
`RUSTFLAGS="-Zcodegen-backend=cranelift" CARGO_TARGET_DIR=/tmp/t cargo test --workspace`.
