# ADR-013: Running the Flagship — `std`, Methods, and What Stage 0 Refuses to Infer

**Status:** Accepted
**Date:** September 7, 2026
**Target Version:** Nikaia 0.0.8 (bootstrap compiler)
**Closes:** the fold-adapter question left open by [ADR-011](adr-011.md) D2, and most of
[ADR-011](adr-011.md) §4
**Related:** [ADR-011](adr-011.md) (the Stage 0 lowering), [ADR-012](adr-012.md) (diagnostics),
[ADR-009](adr-009.md) D2 (`par_fold` is a frame plus a monoid), [ADR-008](adr-008.md) (views)

---

## 1. Context

`examples/1brc.nika` has been the project's flagship since 0.0.7 and has never run. ADR-011 got
its grammar onto the parser backend and named the rest: `impl` blocks, `throws`/`catch`/`??`,
string interpolation, and the `std` names the program calls. This ADR is that rest, and the
measure of it is not that the constructs parse — it is that the file compiles and prints what the
benchmark asks for, which `crates/nikaia/tests/one_brc.rs` now checks by running it.

Two questions had to be answered rather than deferred, and they are the reason this is an ADR and
not a changelog entry: **where the meaning of `fs::map` lives**, and **when the compiler may
adapt a method it was handed**.

---

## 2. Decisions

### D1 — Nikaia's `std` is a crate, not a table inside the emitter.

`fs::map`, `cli::args`, `HashMap`, `digit_value` and the list operations live in
`crates/nikaia-std`, and a program that imports anything from `std` gets
`pub use nikaia_std::prelude::*;` in its preamble. The names then resolve as written.

The alternative was a substitution table in the emitter: `fs::map(x)` prints as
`std::fs::read_to_string(x)`, and so on. Rejected, because it makes the semantics of the standard
library into strings inside a printer — unreadable, untestable, and impossible to document. As a
crate, `fs::map` is a function with a doc comment saying exactly what it guarantees and what it
does not yet do:

> Part III, 17.1 calls for a memory mapping, and that is what this type exists to become […]
> Today it reads the file into memory instead — the same interface, the same guarantee about the
> text outliving the views, and a different cost. `memmap2` is the change, and it is a change to
> this file alone.

That paragraph is the honest state of `fs::map`, and it is in the place a reader would look.

**One name had to change.** `d.to_digit()` cannot be a method: Rust's `char` has an inherent
`to_digit(radix)`, an inherent method wins over a trait method, and a call that resolves to the
wrong thing is worse than a name that reads differently. It is the free function `digit_value(d)`,
and the reason is written where the function is.

### D2 — The fold adapter is a lookup in the program's declarations, and it took `impl` blocks to make it one.

ADR-011 D2 refused to thread a fold's accumulator by inferring from the shape of the step's body,
because `acc.record(m)` and `acc.merged(m)` are the same shape and mean opposite things. It said
the answer waits until the compiler lowers `impl` blocks and knows the receivers. It does now:

```nika
par_fold(MEASUREMENT, Summary::new, fn(acc, m) { acc.record(m) }, Summary::merge)
```

`record` is declared `fn record(&mut self, m: Reading) sync` — it takes its subject by mutable
reference and returns nothing, so the accumulator has to be threaded, and the emitter writes
`|mut acc, m| { acc.record(m); acc }`. A method that returns a new accumulator is left exactly as
written. `Summary::merge` names its type, so the merge is looked up precisely and the declared
argument decides whether the other summary is passed as a view: `|mut a: Summary<'a>, b| { a.merge(b); a }`.

A method name that two `impl` blocks disagree about is left alone rather than resolved by
preference — the emitted code then fails to compile, which is the right outcome for an ambiguity
the compiler cannot settle.

### D3 — `throws`, `catch` and `??` lower to what they already mean.

* `throws` → `Result<T, Box<dyn std::error::Error>>`. `Box<dyn Error>` because Nikaia's own error
  types are not lowered yet; the `?` the DSL driver needs works against it, and every error keeps
  its own type behind it. A `return` inside such a function carries the `Ok`, and a function that
  returns nothing ends in `Ok(())`.
* `catch` → a `match`, with the error bound to `error` as Part I, 7.1 says.
* `??` → `unwrap_or_else(|| fallback.into())`. The `into()` is there because the fallback is
  written as the value it stands for, not as the type the option holds.

A lambda's `return` leaves the lambda, so it never carries the enclosing function's `Ok`.

### D4 — The anonymous constructor is `new`, and the call site says which form it is.

Kap 4.2's `pub fn(…) -> Type` has no name; Rust has no such thing, so it is emitted as `new`.
`Type(positional)` is a call to it; `Type(named: value, …)` is the struct literal. The two are
told apart by requiring the named form's first field to carry a value — otherwise `Stats(x)` would
read as a struct with one shorthand field. This is the spec's own distinction (4.2), made
syntactic.

### D5 — An implicit lambda takes the arguments its body uses.

Kap 5.2 gives `a`, `b`, `c`. Rust closures have a fixed arity, so the emitter takes the longest
prefix of those names the body actually reaches for: `fn { a.add(m.temp) }` becomes `|a| …`, and
`fn: a + b` becomes `|a, b| …`.

~~**`fn:` does not chain.**~~ **Superseded by [ADR-022](adr-022.md).** `xs.map fn: a.id` ran to
the end of the expression, so a chained `.join(…)` after it landed inside the lambda — silently.
This decision recorded that as a limitation to live with and pointed at the block form. It was
the wrong shape of answer: the form was four characters shorter, could not grow without being
rewritten, and was a second way to say what `fn { … }` already said. It is removed, and with no
expression-bodied lambda there is nothing left that can swallow a chain.

### D6 — An interpolated hole may say how it is written.

`"{a}={s.mean():.1}"`. The first colon that is not inside a call or an index separates the
expression from the format spec, exactly as a format string does elsewhere; `Stats(min: 1)` keeps
its colon, being inside parentheses. `{{` and `}}` are literal braces. Without this, 1BRC's own
output format — one decimal — could not be written at all.

### D7 — Where Stage 0 does not infer, the source says it, and the example was changed to say it.

This is the decision the other six rest on: **the lowering stays syntactic (ADR-011 D2), so where
the example relied on inference the compiler does not have, the example is what changes.** Every
edit to `1brc.nika`, and why:

| Change | Why |
| :--- | :--- |
| `d.to_digit()` → `digit_value(d)` | D1: the method name is unreachable in Rust. |
| `sum: first` → `sum: first as i64`, `self.sum += temp as i64` | Nikaia states no implicit numeric widening, so the conversion is written. |
| `.and_modify fn: …` → `.and_modify fn { … }` (twice) | D5: `fn:` does not chain — and is [removed](adr-022.md), for which this rewrite was the first evidence. |
| `.map fn: { … }` → `.map fn { … }` | D5, same. |
| `merge(&mut self, other: &Summary)` → `other: Summary` | The loop below takes the entries out of it, which a view cannot give. The adapter follows the declaration either way (D2). |
| `fs::map(path)` → `fs::map(&path)` | `path` is read again in the handler, so it is passed as a view. |
| `let s = totals.stations[a]` → `let s = &totals.stations[a]` | The entry is looked at, not taken out of the map. |
| `{s.min / 10.0}` → `{s.min as f64 / 10.0:.1}` | The widening, again, and D6 for the decimal. |
| `println("{{body}}")` → `println("{{{body}}}")` | D6: `{{` is a literal brace, so the original printed `{body}`. |

Each is a sentence about the source, not a workaround: a reader of `1brc.nika` learns that Nikaia
does not widen integers silently and that a value read after a call is passed as a view. The two
that are *not* language statements — `fn:` not chaining, and `to_digit` — are limitations, and
they are named as such here and in the example.

## 3. What this makes of the corpus

```text
$ nikaia --input examples/1brc.nika --backend rust
$ ./brc measurements.txt
{Bulawayo=8.9/15.5/22.1, Hamburg=-3.4/2.9/12.0, Palembang=38.8/38.8/38.8}
```

`crates/nikaia/tests/one_brc.rs` does exactly that on the real example file — lowers it, compiles
the result with the same `rustc` that built the test, runs the binary over an input small enough
to check by hand, and compares the line. It also runs it against a missing file, because the
`catch` in `main` is part of what the example claims.

## 4. What is still not true

* ~~**`fs::map` reads; it does not map.**~~ Closed by [ADR-014](adr-014.md) D2: it is a memory
  mapping now.
* ~~**`Parallelism::Auto` runs the pieces in sequence.**~~ Closed by [ADR-014](adr-014.md) D3:
  the `rayon` feature is on, and the speed-up is measured there.
* ~~**`sync` is still unchecked** (ADR-011 §4).~~ Closed by [ADR-020](adr-020.md): the ledger
  says what a function promises, and `NK2202` is what the compiler says about a call that breaks
  it.
* ~~**No type checker.**~~ Closed by [ADR-024](adr-024.md) — with one half of the prediction here
  deliberately unfulfilled. The Nikaia-level messages arrived: eight `NK1xxx` codes, on the
  `.nika` line, answered from the ledger. The widening did **not**, and will not: D7 says a
  conversion is written, so a checker that quietly widened an integer would be checking a
  different language from the one this ADR describes. What the checker knowing the types bought
  was the diagnostic, not the coercion.
* **`examples/fortunes.nika` still does not compile.** Its gaps (G6, G7) are about `std::http` and
  template escaping, and nothing here touches them.
