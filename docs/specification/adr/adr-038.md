# ADR-038: The Runtime Is Ours, and So Is the HTTP Server

**Status:** Accepted · **Built:** no
**Related:** [ADR-018](adr-018.md) (what an HTTP handler sees — this is the
"runtime binding" it waits on), [ADR-006](adr-006.md) (`Cleanup` parks with the
runtime, so D4 is what makes D3 of that record buildable),
[ADR-033](adr-033.md) §8.4 (the wake-up cost that decided D3),
[ADR-037](adr-037.md) D2 (`user_parallelism` decides what D4 starts),
[ADR-002](adr-002.md) D1 (crates.io, which D7 is about),
[ADR-009](adr-009.md) (the grammar protocol D6 parses HTTP with)

## 1. Context

Three records wait on "the runtime binding" and none of them says what it is.
`tokio` appears in a parenthesis in [ADR-018](adr-018.md) §3 and as a checkbox
in the roadmap — chosen by repetition rather than decided, which is the shape of
dependency this project has spent a cleanup removing.

Two findings make the choice non-obvious and both are ours.

**[ADR-033](adr-033.md) §8.4:** overlapping two operations costs a thread
wake-up, about 46 µs, and that is an operating-system number no user-space
scheduler removes. A runtime we wrote would not beat it.

**But `epoll` cannot read a file at all.** A regular file is always "ready" and
the read blocks in the kernel anyway, which is why every readiness-based runtime
serves file I/O from a thread pool. That pool *is* the 46 µs. `io_uring` removes
it — not by being a faster pool, but because no thread is involved: the kernel
performs the read and reports when it is done.

So the two halves of I/O have different answers, and the HTTP server sits on
exactly the half where the finished libraries are.

## 2. Decisions

### D1 — The HTTP server is Nikaia's own, and `hyper` is not adopted.

A finished server would have to be given I/O it can *ask* for data from, and
`io_uring` reports data instead. Bridging the two costs a copy through an
intermediate buffer, which spends most of what `io_uring` was for. Adopting one
therefore does not postpone the I/O decision — it makes it, for sockets, and
unmaking it later means replacing the HTTP implementation rather than the
plumbing under it.

The positive reason is larger. An HTTP request is a request line, then headers,
then a body, delimited by fixed byte sequences: it is a grammar over bytes with
a frame boundary, which is what [ADR-009](adr-009.md) exists for. And it is the
one program that exercises [ADR-010](adr-010.md) (request bytes are
**Untrusted** by construction, not by a special case) and
[ADR-017](adr-017.md) (escaping is the template's contract) on something real.
A language whose HTTP server is written in it makes a different claim from a
language with a binding to somebody else's.

### D2 — TLS is never ours. `rustls` is bound, as a Rust dependency.

Writing TLS is years of security-critical work where a mistake is not slowness.
`rustls` is bound through [ADR-002](adr-002.md) D1's passthrough like any other
Rust crate.

It constrains nothing here, and that is worth recording: `rustls` takes bytes
and produces bytes, and has no opinion about how they arrive. Unlike a finished
HTTP server, it does not decide D3.

### D3 — I/O is split by kind: completion for files, readiness for sockets.

Files go to `io_uring` where the machine has it, with the thread pool as the
fallback where it does not — an older kernel, a sandbox that forbids the
syscalls, `wasm32` where neither exists. Sockets are readiness-based.

This is where the measurement points: the cost [ADR-033](adr-033.md) measured is
a *file* cost, and the two reads of its own example are two files. What
`io_uring` adds for sockets is mainly batching syscalls, which is worth
double-digit percentages rather than an order of magnitude — and is not
something this project has measured.

Both live behind one `std` surface, for the reason
[ADR-033](adr-033.md) §8.4 gave when it put the overlap behind
`nikaia_std::task::both`: the next change of mechanism must be a `std` change
and not a compiler change.

### D4 — The runtime starts before `main`, and `user_parallelism` says what starts.

An I/O thread that is already running costs nothing per operation; one started
per pair of operations costs a wake-up per pair, which is the whole of §8.4's
finding. So it is running before the first statement the user wrote.

At `user_parallelism = no` that is all that starts: one I/O thread, and
everything the user wrote on the main thread. At `yes` a pool for user code
starts with it. The asymmetry is [ADR-037](adr-037.md) D2's, restated where it
becomes a thread count: the compiler's own threads were never bounded by that
switch, and the I/O thread is one of the compiler's.

### D5 — Tuning is a runtime configuration file, read at startup.

`nikaia.toml` keeps what the **compiler** must know — `target` and
`user_parallelism` ([ADR-037](adr-037.md) D5) — and nothing else. How many I/O
workers, how large the pool for user code, which I/O method, and how long
shutdown drains are read when the program starts, by the person running it on
the machine it runs on. A build-time key cannot be tuned by the operator, who is
not the person who compiled it.

Four settings and no fifth. The I/O method's default is `auto`, and it can be
pinned — the same shape `--ordering strict` has: the default decides, and a
person may overrule it to rule something out in the field.

`cleanup-deadline` moves here from `nikaia.toml`, where Part III 13.3 put it.
How long a program waits at exit for pending cleanup
([ADR-006](adr-006.md) D5) is an operating property, and it was in the wrong
file.

### D6 — HTTP/1.1 first. HTTP/2 is named as unbuilt until it is built.

HTTP/1.1 is the grammar D1 is about. HTTP/2 is header compression, flow control
and stream multiplexing — a different order of work, and the place where
"production-ready" becomes expensive.

Part III's `std::http` promises "a production-ready HTTP/1.1 and HTTP/2 server
and client" with no status note. Until HTTP/2 exists that sentence is the kind
of promise `docs/README.md` calls a defect, and it carries a status note from
here on.

**And the risk is named rather than discovered.** A fresh HTTP/1.1 parser's
failure mode is request smuggling: a `Content-Length` and a `Transfer-Encoding`
that disagree, a header sent twice, a chunked body with an edge case — and two
servers in a chain then see two different requests. It is a test corpus and a
fuzzer written alongside the parser, not an audit afterwards.

### D7 — A Rust crate may bring its own runtime, and two rules keep that sound.

[ADR-002](adr-002.md) D1 promises crates.io, so a program can depend on a crate
that starts threads and an event loop of its own — `hyper` among them. That is
allowed, and two things about it are decided rather than discovered:

* **A value may only cross into a foreign thread if it may cross any thread.**
  At `user_parallelism = no`, `Shared` is `Rc` ([ADR-037](adr-037.md) D3); a
  foreign runtime that moves it to another thread would make that unsound. The
  structural `Send` check [ADR-037](adr-037.md) §3 names is what decides it, and
  it applies at both settings — which is why that section already says a library
  is checked against the rules parallel code needs whatever it was built at.
* **A `Cleanup` may not be owned by a foreign task.** [ADR-006](adr-006.md) D3
  parks a cancelled cleanup with *our* runtime, and a foreign runtime's shutdown
  will not drain that queue. A `Cleanup` handed across is a cleanup that may
  never run, which is the one thing that record exists to prevent.

What needs no rule: the ledger knows nothing about a foreign crate's effects, so
`touches` is absent, so it reaches everything and orders against everything
([ADR-033](adr-033.md) D4). Fail-closed polarity means interop cannot silently
break the ordering guarantee — it only makes programs that use it slower.

## 3. Consequences

Three records stop waiting. [ADR-018](adr-018.md) can be built once D4 and D6
exist; [ADR-006](adr-006.md) D3's parked cleanup has a queue to park in;
[ADR-033](adr-033.md) §8.5's prediction — that the overlap is worth more at
`user_parallelism = no`, because a running I/O thread carries no per-pair
wake-up — becomes measurable rather than predicted.

The dependency surface grows by `rustls` and, on Linux, an `io_uring` binding.
Neither reaches a `.nika` file: D3's `std` surface is what a program sees.

## 4. What is built

Nothing. This is a decision and not a delivery, in the order D1–D6 imply: the
event loop and socket layer first, then a minimal HTTP/1.1 server on it — which
is also what gives [ADR-033](adr-033.md) §7 the real program its debt has been
waiting for — then the parsing moved into Nikaia, then `rustls`, then HTTP/2.

D7's two rules are the exception worth checking early rather than late, because
a program that starts `hyper` is the cheapest test of whether
[ADR-002](adr-002.md) D1's crates.io promise and this record can hold at the
same time.
