# ADR-026: Compile-Time I/O — What a Build May Read, and What May Run While It Reads

**Status:** Open
**Date:** September 10, 2026
**Target Version:** undecided
**Related:** [ADR-007](adr-007.md) D3 (`dsl` is one syntax for compile time and runtime),
[ADR-005](adr-005.md) D8 (byte-determinism as a hard guarantee),
[ADR-010](adr-010.md) (the shipped precedent for Tier 1, §3 — and, on runtime input provenance, a
different question from this one, see §1),
[ADR-021](adr-021.md) D2/D7 (the asset dimension of the cache key),
Tooling Spec [§13.1](../30-nikaia-tooling.md)

---

## 0. What "Open" means here

Every other ADR in this directory is `Accepted` or `Superseded`. This one is neither, and the status
is the point: the design space is staked out, two things in it are settled, and the rest is written
down as questions **because they are not answered yet**. An open ADR that quietly decides something
is worse than no ADR at all — the next reader would take a sketch for a commitment.

Nothing here is implemented. This document exists so that whoever implements it starts from the
constraints rather than rediscovering them.

---

## 1. Context

Compile-time I/O is specified in three places and built in none.

* The **syntax already parses**. `dsl G from <expr>` becomes `Expr::DslFrom`
  (`crates/nikaia/src/parser/mod.rs`, rule `dsl_from_expr`) and lowers to a *runtime* call
  (`crates/nikaia/src/emit/mod.rs`, `fn dsl_from`). Only the runtime half exists.
* [ADR-007](adr-007.md) D3 says one syntax serves both modes and the **context** decides:
  `const CONFIG: Json::Value = dsl Json from "config.json"` fails the build on a malformed file,
  `let data = dsl Json from user_input` throws at runtime. But **`const` does not exist** at item
  level — neither in the parser nor in `ast::Item`. The discriminator ADR-007 D3 rests on has no
  representation.
* [ADR-021](adr-021.md) D2 puts the SHA256 of every compile-time-read file into `nikaia.lock`, and
  D7 makes it a key dimension. That dimension is implemented and tested and **has no producer**:
  nothing in the compiler reads a file at build time, so the map is always empty.

And one fact that shapes every option below: **a grammar is not declarative.** `GrammarAlt` carries
`action: Option<Block>` (`crates/nikaia/src/ast/mod.rs`) — an arbitrary Nikaia block that builds the
alternative's value. Running a grammar at compile time therefore means running arbitrary user code at
compile time. The Phase-2 expander that ADR-003 assigns this to is a 133-line placeholder that walks
`main` and prints (`crates/nikaia/src/interpreter/mod.rs`).

**Not the same question as ADR-010.** That ADR decides how the provenance of *runtime* input picks a
hasher. This one is about what the *build* is allowed to touch. They share the word "input" and
nothing else; conflating them would let a runtime-safety argument stand in for a supply-chain one.

## 2. Decided

### D1 — I/O belongs to the compiler; evaluation belongs to the sandbox.

The compiler opens the file, and hands **bytes** to whatever evaluates the grammar. The evaluator
never receives a path, a handle, or a filesystem.

This is the arrangement the rest of the document depends on, and it is settled first because it
changes what every later question costs. A sandbox that *has* filesystem access and is configured not
to use it is a policy that can be misconfigured; a sandbox that is handed a byte slice cannot reach a
file because there is nothing to reach it with. Capability-free by construction beats capability-free
by settings, and it makes the audit question ("what did this build read?") answerable in one place —
the compiler — rather than distributed across whatever ran.

### D2 — A compile-time path stays inside the project, and `..` is refused rather than resolved.

Paths in `from "…"` resolve relative to the source file that contains them, must land inside the
project root (the directory holding `nikaia.toml`), and **a path containing `..` is rejected outright
as malformed** — not normalised and then checked.

The distinction in that last clause is the whole decision. A check that normalises first is a check
that argues about the result of a normaliser, and normalisers are where path-confinement bugs live:
`a/../../b`, encoded separators, one platform's idea of a root versus another's. Refusing the
component is a rule about the *text the author wrote*, which is a thing with one reading.

Open within this decision: **symlinks**. A link inside the project that points outside it satisfies
D2 as written and defeats its purpose. Resolving links before the check reintroduces exactly the
normaliser argument D2 avoids. This needs an answer before D2 is implementable and does not have one.

## 3. Two tiers, and only the second one is expensive

The single most useful thing to say about this space is that it holds **two features, not one**, and
conflating them forces the harder one's requirements onto the easier one.

**Tier 1 — compiler-side staging.** We write it, in Rust, in the emitter. No new security model, no
determinism problem, no toolchain requirement, no fuel budget. This is where perfect hashing for a
route table lives, where a regex becomes a DFA, where a state machine is flattened.

**Tier 2 — user-visible compile-time execution.** The *user* writes a tool that runs during the
build. Everything in §4 belongs here and only here: the sandbox, the fuel budget, the trust
question, `wasm32`.

Tier 1 does not wait on Tier 2 and does not presuppose it. That is worth stating flatly, because the
applications usually cited as the reason for Tier 2 are Tier 1 work: perfect hashing over a hundred
routes is a few hundred lines in the emitter, with no evaluator of any kind.

**Where Tier 1 actually stands today is surveyed in
[`docs/staging-candidates.md`](../../staging-candidates.md)** — which candidates are real, which look
like candidates and are already closed, what one costs to check, and the constraint that decides how
much of this the compiler *can* choose: byte-determinism (ADR-005 D8) means the emitter may decide
only from source and toolchain, so autotuning is out and a measured threshold is in. Read it before
picking a first change; the obvious one, route hashing, has no target yet.

**The precedent is in this repository.** [ADR-010](adr-010.md) has the compiler choose a map's hasher
from the provenance of its keys — nothing in the `.nika` source mentions hashing, and the CHANGELOG
records the result: 22 % of 1BRC's instructions, `advanced` from 0.15 s to 0.12 s. That is an
abstraction whose cost the compiler removed because it knew something. It needed no sandbox, no JIT
and no comptime, and it shipped.

### 3.1 — Tier 1 must be *able* to emit specialised code

Not "we will build a regex compiler", but: the architecture must not preclude one. This is a real
requirement and it is **already satisfied**, by two mechanisms both in use — recorded here so that
nobody later concludes it needs Tier 2:

* **The compiler chooses, `std` provides.** ADR-010's pattern. Specialised code — SIMD, intrinsics,
  anything target-specific — lives as hand-written Rust in `crates/nikaia-std/`, and the emitter
  emits the call. Checked: the emitter contains no `target_feature`, no `std::arch` and no
  intrinsics today, and on this route it never needs them.
* **The emitter generates specialised code.** The grammar pattern. A DFA as generated code rather
  than a runtime table is precisely what `grammar` already does.

Worked through on the regex example: compile-time analysis picks the strategy — a single literal
takes a `memchr` path in `std`, an alternation of literals a Teddy-style one, and anything else a
DFA. Two caveats belong here rather than in a benchmark six months from now:

* **Table-free is not automatically faster.** A DFA as straight-line code trades a data-dependent
  load for an indirect jump plus instruction-cache pressure, and loses that trade when the state
  count grows. re2c and Ragel generate code; RE2 and rust-regex use lazy DFAs with tables. Both
  approaches exist because neither wins everywhere.
* **"No branch mispredictions" is backwards for the state machine itself** — an indirect jump per
  transition is what a predictor handles worst. The real win is where the analysis *removes* states:
  a fixed literal collapses to a comparison, a bounded pattern unrolls. That is the defensible claim,
  because it says why it is faster.

### 3.2 — Tier 2 pulls against the thing ADR-021 was built for

Compile-time execution makes builds **slow**. [ADR-021](adr-021.md) exists because build speed
matters. These pull directly against each other, and the ADR should say so rather than let a future
reader discover it.

The complaint one hears about Zig — that comptime-heavy code makes its compiler slow and
memory-hungry — is therefore **not a competitor's weakness to exploit. It is a warning about the
feature itself**, and it applies to us on the same terms. What we have that helps is the cache: an
unchanged input skips the whole evaluation (ADR-021 D13), which converts a per-build cost into a
per-change one. That is the mitigation, and it is already built.

## 4. The design space

Everything in this section is **Tier 2** (§3). None of it blocks Tier 1, and none of it should be
treated as a prerequisite for the applications Tier 1 already covers.

### Q1 — A grammar is a closed world, and that is what makes a sandbox affordable.

This is the observation the rest of the space organises around.

A grammar maps bytes to a value of **its own** type. It does not need the surrounding program's AST,
its types, or its symbol table. An external grammar can therefore be translated **in complete
isolation**, and the boundary between it and the compiler is **a layout the host reads out of the
guest's memory** — not a text format that would have to be parsed back:

```
compiler reads the file      (D1: confined by D2, recorded per ADR-021 D2)
        │  bytes
        ▼
isolated grammar artifact    (no imports, no host functions, no ambient anything)
        │  a laid-out value in the guest's linear memory, read with bounds checks
        ▼
compiler emits               (the bytes, plus the code that reads them back)
```

Two consequences worth stating plainly:

* **It dissolves the materialisation problem.** The hard part of "just fold the constant" is that a
  build-time value of an arbitrary user type has to be written back out as Rust source, which needs a
  general value-to-source printer for anything a grammar can construct. A byte boundary gives that
  for free, because the value crosses it as bytes either way. And reading a fixed layout out of the
  guest's own memory costs a bounds-checked copy rather than a parse, so "don't hand back text I have
  to re-parse" is satisfied without giving up isolation.
* **It means DSL-`const` is a different mechanism from general `const`.** A DSL evaluation is closed;
  a general compile-time function call is not — it can name the program's own types and functions.
  Treating them as one feature forces the harder one's requirements onto the easier one. Treating
  them as two lets the closed case ship first.

Open: whether to commit to that split, and whether the serialisation format is an existing one or
ours.

### Q2 — Matching is pure; actions are not. Which of them needs a sandbox?

Splitting the grammar in half changes the answer:

* **Matching** (the PEG itself) is total and effect-free. It could be interpreted directly over the
  `GrammarDef` already in the AST, with no sandbox at all, because a matcher that only matches cannot
  do anything else.
* **Actions** (`GrammarAlt.action`) are arbitrary Nikaia. This is the entire reason a sandbox is
  under discussion.

So there is a cheaper design hiding here: **restrict what an action may do in `const` context** to a
pure, total subset, and the sandbox question disappears along with the dependency it would add. The
cost is a rule authors have to learn, and a second dialect-ish distinction in the language —
precisely the kind of thing ADR-007 D3 was trying to avoid when it insisted one syntax serve both
modes.

Open: restrict-and-interpret, or permit-and-sandbox.

### Q3 — If it is sandboxed, in what?

Named with costs rather than a preference:

| | shape | cost |
| :--- | :--- | :--- |
| **wasmi** | pure-Rust Wasm interpreter | small dependency, easy to embed, slow |
| **wasmtime** | Wasm JIT | fast, large dependency tree and build time |
| **own bytecode VM** | ours | no dependency, no ecosystem either; a VM is a long-lived thing to own |
| **AST interpretation** | Q2's restricted subset | smallest, only viable if Q2 restricts |

**And the direction of that table is not the obvious one.** `wasmi` is an *interpreter*: roughly an
order of magnitude off a JIT, which removes exactly the speed advantage that would justify Tier 2's
machinery over a plain bytecode VM. `wasmtime` has the speed and brings a JIT-sized dependency. Worse
for both: the grammar has to be *translated* to Wasm before anything runs, and for a single
evaluation that translation dominates the execution it was supposed to accelerate.

So the honest form of the claim is conditional: **the Wasm advantage exists for large workloads with
an already-cached module, and is negative otherwise.** ADR-021 supplies the caching half; the
workload half is an assumption nobody here has measured. This session measured an equally plausible
one — Cranelift as the dev backend — and got 25 s against 26 s.

Two further costs specific to Wasm that are easy to discover late:

* **A toolchain requirement.** Producing the module means compiling the isolated grammar to
  `wasm32-unknown-unknown`, so every contributor and every CI job needs that target installed. That
  is a real addition to `rust-toolchain.toml` and to what "clone and build" means.
* **Determinism has an asterisk.** Wasm with no imports is deterministic except for **NaN bit
  patterns**, which are permitted to vary. That matters more here than it usually would:
  [ADR-005](adr-005.md) D8 makes byte-determinism a *hard guarantee* enforced by CI double-builds,
  and a cached compile-time value inherits the same expectation. A grammar whose actions do float
  arithmetic could produce two different builds that are both correct.

### Q4 — What is a program allowed to do in `const`?

The largest open question, and the one that has to be answered before any of Q2/Q3 can be, because it
decides what the evaluator must support. At minimum:

* Pure functions only, or may a `const` call anything?
* **Allocation is a requirement, not an option.** Building a DFA from a regex at compile time needs
  dynamic data structures. Rust's stable `const fn` has no heap, and that is *why* Rust falls back to
  proc-macros and `build.rs` — worth naming precisely, because the usual telling gets it wrong:
  Rust's heavy compile-time mechanism (proc-macros) may allocate freely. The real pain is that it is
  a *separate* mechanism, type-blind because it runs before type checking, and slow because it is a
  second compilation. Not impossibility; a seam.
* Bounded or free is the remaining question here.
* Recursion and iteration — and therefore **a step or fuel budget**, because an infinite loop at
  compile time hangs the build rather than the program. A compiler that can be made to not terminate
  by a dependency's grammar is a supply-chain problem wearing a performance costume.
* Nothing that observes time, environment, randomness or address layout — otherwise the ledger's
  determinism guarantee (ADR-005 D8) and the cache's key (ADR-021 D7) are both wrong, and wrong
  silently.

### Q5 — Confinement is not the same as permission. Does reading need to be enabled?

D2 stops a build reading `/etc/passwd`. It does **not** stop a dependency's grammar reading *your*
`secrets.toml` — that file is inside your project root, which is exactly where D2 says reading is
allowed — and embedding its contents in the binary you ship.

D solved this with an explicit grant: `import("file")` only reaches paths the invocation opened with
`-J`. The options here are the same family:

* asset directories declared in `nikaia.toml`, so the grant is reviewable and versioned;
* a per-invocation flag, closest to D, and the most friction;
* no grant, and rely on the record instead.

The third deserves more credit than it first appears to, because ADR-021 already built the mechanism:
**every file a build reads is recorded in `nikaia.lock` with its hash, and the lockfile is
committed.** A dependency that starts reading something new cannot do it quietly — it shows up as a
lockfile diff in review, next to the change that caused it. That does not *prevent* the read, and it
should not be sold as if it did. It converts an invisible capability into a visible one, which is a
weaker and much cheaper property, and the question is whether it is enough.

Open: which of the three, and whether "enough" is a judgement this project gets to make once or has
to make per-dependency.

### Q6 — Trust changes the default, but not the mechanism. Where does the line go?

Everything above treats Tier 2 code as potentially hostile, and that is wrong as a blanket
assumption: code you wrote runs with your privileges anyway, and sandboxing it buys nothing. The
obvious repair — *local code runs natively with no restrictions, foreign code is sandboxed* — puts
the line in the wrong place, and mistakes two costs for security costs that are not.

* **"Local" is not the boundary.** The dangerous case is your own repository after a `git pull`:
  a pull request adds a local DSL, and it executes natively, with full privileges, on every
  reviewer's machine and in CI. That is the `build.rs` attack surface — the most-criticised security
  property of Rust, and the standard route for supply-chain attacks against it. Adopting that model
  deliberately is a legitimate option; adopting it by accident is not. The boundary that matters is
  *has a human reviewed this*, and it does not follow from where a file sits.
* **Determinism does not hang on trust.** [ADR-005](adr-005.md) D8 is a *hard* guarantee with CI
  double-builds. Native compile-time code can call the clock, read the environment, iterate a hash
  map; an import-free sandbox gets determinism for nothing. A tier of "trusted, therefore
  unrestricted" silently drops a guarantee the project calls hard — for correctness reasons, not
  security ones. Your own code is exactly as capable of producing two different builds as anyone's.
  The same applies to `nikaia.lock`'s promise that a build reproduces elsewhere.
* **The fuel budget is a tool, not a guard.** "An infinite loop is a bug, not a security incident" is
  true and beside the point: a build that hangs with no diagnostic is *worse* for the local developer
  than one that stops with "this exceeded its budget, here is the call path". Zig's
  `@setEvalBranchQuota` does not exist for security.

That leaves exactly one cost that genuinely tracks trust: **memory and filesystem isolation.**

A direction worth considering, recorded as an option and not a decision: **do not split on origin;
declare capabilities.** One mechanism and one rule set; determinism and fuel for everyone; isolation
as the single capability a project may explicitly give up in its manifest. The local developer then
pays the isolation cost only if they choose to — but the choice is a line in a committed file that a
reviewer sees in a diff and CI can refuse, rather than an implicit property of a directory. It is the
same move ADR-021 already makes with the lockfile: turn an invisible capability into a visible one.

## 5. Prior art

The two poles of Q2 and Q4 are both occupied by working languages, which makes this a choice rather
than an excuse:

* **Zig — restrict.** `comptime` cannot do I/O at all; reading a file is `@embedFile`, a separate
  declarative capability where the *compiler* resolves the path. That is D1 plus Q2's restrict branch,
  shipped. Its known cost is the one §3.2 warns about: comptime-heavy code makes the compiler slow
  and memory-hungry. (Precisely: Zig evaluates over ZIR in Sema, not by walking the AST — the
  performance criticism holds, the usual explanation of it does not.)
* **Jai — permit.** Broadly open compile-time execution, including I/O and compiler introspection.
* **Rust — a separate mechanism.** `const fn` restricted and heapless; proc-macros and `build.rs`
  unrestricted, native, and outside the type checker. `phf` does perfect hashing this way, which is a
  useful datum: the Tier 1 application everyone cites is served in Rust by a *library*, not by a
  language feature.
* **Terra, MetaOCaml** — staged programming as the older field this sits in, where "the same program
  in two stages" is the whole subject rather than a feature bolted onto one stage.

## 6. Considered and rejected

Recorded so that they are not reopened as fresh ideas.

* **A raw pointer as the host/guest ABI** — the guest returns a `#[repr(C)]` pointer and length, the
  host casts it in an `unsafe` block. It voids D1 (the guest would be handed a path and do its own
  I/O), voids isolation (an `unsafe` cast over memory the untrusted side laid out is not a sandbox),
  and breaks ADR-005 D8, because anything containing a pointer varies with the allocation address
  under ASLR. Its legitimate core — do not hand back text that has to be re-parsed — is met instead
  by Q1's layout in the guest's linear memory.
* **"DSL as a runtime artifact" as a separate feature.** It is the existing `grammar` path, via Rust
  source instead of an object file. Worth naming as an axis — consumed at runtime versus consumed
  during the build — not as an open question.
* **1BRC as evidence for compile-time execution.** This repository's own CHANGELOG attributes the
  gains to the provenance-chosen hasher (22 % of instructions), the parallel UTF-8 check (11 % of the
  time), `fs::map` and rayon. None of it is compile-time evaluation; 1BRC is dominated by I/O
  strategy, SIMD and threading. The claim is unsupported by our own measurements and should not reach
  a README.
* **"Faster than ripgrep" as a claim.** Not because the architecture forbids it — §3.1 says it
  explicitly does not — but because the sentence invites a benchmark that ripgrep wins on grep-shaped
  workloads after years of tuning, and its speed comes from literal prefilters rather than from
  compilation strategy. The defensible sentence is next to it: *an ordinary regex yields a
  specialised matcher without reaching for a library.*
* **"Typed AST nodes at compile time" as a present-day advantage** over Rust's token-level macros —
  *rejected when this was written, and the ground has since moved.* The objection was ADR-013's "no
  type checker": at expansion time the compiler knew as little about types as a proc-macro does.
  [ADR-024](adr-024.md) has since built one, on the signature store ADR-020 started, and the emitter
  already reads its answers. So the claim is no longer refuted by *absence*. What it still needs
  answering is **ordering** — whether type information exists at the point compile-time evaluation
  would run, or only after it. Until someone establishes that, this is a plausible advantage rather
  than a demonstrated one, and it should be argued from ADR-024's actual reach rather than asserted.

## 7. What answering this buys the cache

The asset dimension in [ADR-021](adr-021.md) D2/D7 finally gets a producer, and the expensive part of
whatever Q2/Q3 decide is paid for at most once per change: an unchanged asset under an unchanged
grammar and an unchanged compiler is a cache hit, and the whole evaluation — sandbox startup,
matching, actions, serialisation — is skipped. ADR-021 D13's rule applies unchanged and is worth
restating in this context, because it is easy to violate here: **every input the evaluation reads
must be a key dimension.** The asset's bytes are. The grammar is, through the source hash. The
evaluator's own version is, through the compiler fingerprint. Anything a future `const` is allowed to
observe has to join that list in the same change that allows it.

## 8. The open questions, collected

All of them are Tier 2 (§3). Tier 1 is blocked by none of them.

1. Symlinks that leave the project root (inside D2, which is otherwise decided).
2. Commit to the DSL-`const` / general-`const` split (Q1)?
3. Restrict actions in `const`, or sandbox them (Q2)?
4. If sandboxed: which runtime, is the `wasm32` toolchain requirement acceptable, and does the
   workload assumption survive measurement (Q3)?
5. What may a `const` do — purity, the fuel budget, and how far allocation is bounded, allocation
   itself now being a requirement rather than an option (Q4)?
6. Is confinement plus the lockfile record enough, or is an explicit grant required (Q5)?
7. Where does the trust line go, and is isolation declared rather than inferred from origin (Q6)?

Question 5 blocks 2, 3 and 4. It is the one to answer first.
