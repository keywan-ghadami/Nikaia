# ADR-121: The Ring's Park Hears the Bell, So Every Worker Operation Can Wake the Executor

**Status:** Accepted · **Built:** no — see §5
**Date:** September 16, 2026
**Target Version:** Nikaia 0.0.8
**Related:** [ADR-038](adr-038.md) D3 and D4 (I/O split by kind; the runtime
runs before the first statement), [ADR-055](adr-055.md) D3 (the executor is
ours and drives the I/O that is already there), [ADR-019](adr-019.md)
(standard input), Part III 13.3b (`io-method`)

## 1. Context

The runtime finishes an operation in one of two ways. On a machine with a
completion queue the kernel does the read and the ring reports it; where the
queue is missing or forbidden, a worker thread does it and rings a **bell** —
a count the executor's park hook watches. The two paths were built for the
same operations and differ in one thing: while the executor parks on the
ring, it waits on the ring's own count of outstanding jobs, and a worker's
reply is not one of them. So a worker's reply cannot wake a ring park, and
no future may be fed from the worker path: `block_on` spins where `main` is
alone and panics otherwise, with its own message about a waker nobody
arranged. A test in `crates/nikaia-std/src/rt/mod.rs` holds this and goes
red the day it stops being true.

Two things rest on it. Standard input is a worker operation, which is why
`io::read`, `io::read_to_string` and `io::lines` are `async fn` whose bodies
block the thread they always did. And `rt::io::wait`, the readiness half of
the runtime built for sockets, can be blocked on and not awaited — which is
the piece an HTTP server needs first.

The entry that proposed wiring standard input to readiness would not have
worked: the defect is the park, not the input.

## 2. Decisions

### D1 — The ring carries an eventfd, always armed, and the bell writes to it.

Where the executor parks on the ring, one file descriptor is registered on
the ring with a read always in flight. `ring_the_bell` writes to it. A
worker's reply therefore completes a ring job, the park returns, and the
executor runs whatever the worker's reply made ready. The two paths stop
differing in what they can feed: **every** worker operation is awaitable —
standard input, socket readiness, and whatever a later operation carries.

### D2 — The bell's completion is not mistaken for an operation's.

The eventfd read carries its own user data, is answered by re-arming it, and
is never handed to a future as a result. The count of outstanding *jobs* the
park consults excludes it, so a park with only the bell armed still sleeps.

### D3 — A hang is the failure this may not have, so it is a panic and a test.

The worst failure a runtime can have is a park nobody wakes. `park`'s own
`false` is already a loud panic rather than a wait; this keeps that standard.
The test that today asserts a worker reply does **not** wake a ring park is
inverted and kept: a worker reply wakes a ring park, and a future fed from a
worker completes under `block_on` with other tasks alive.

### D4 — Standard input stays on the worker path, and becomes awaitable through it.

No second read shape for standard input, no ring path for a stream that has
no size to `stat`. `io::read`, `io::read_to_string` and `io::lines` suspend
because the path they were always on can now wake the executor. The same is
true of `rt::io::wait`, which is what the server's socket layer awaits.

## 3. Consequences

* Standard input suspends, which closes the entry `open-work.md` carried as
  *standard input is `async` and does not suspend*.
* `rt::io::wait` is awaitable, which is the first thing the HTTP server's
  socket layer needs.
* **What it costs:** one file descriptor and one always-armed submission per
  ring, and the care D2 describes. Nothing in the language.
* **Where the ring is absent** — the fallback path, `wasm32` — nothing
  changes: the park there already watches the bell.

## 4. What this does not decide

* The socket layer itself, and the server on it ([ADR-038](adr-038.md) §4.5).
* Whether standard input should ever go to the ring on Linux for throughput;
  nothing measured asks for it.

## 5. What is built

Nothing. The ring park consults its job count and the bell is heard only by
the fallback park. The order of work:

1. the eventfd on the ring, armed at start and re-armed on each completion,
   with its own user data;
2. `ring_the_bell` writing to it where a ring is the park;
3. the test inverted and the `block_on` case added;
4. the three `io::` entries and `rt::io::wait` awaited rather than blocked
   on.

`docs/open-work.md` carries it.
